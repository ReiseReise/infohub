# 信息中枢 V3 顶层架构设计

## 1. 系统定位

信息中枢的本质不是阅读器，也不是问答系统，而是一个**全渠道采集 -> 处理 -> 存储 -> 输出**的上游数据引擎。阅读界面、音频工坊、日报工作台只是这个引擎面向人类的工作台。

当前架构坚持四个原则：

1. 本地优先，默认运行在单仓库 + Docker Compose 环境
2. 管道分层，采集、处理、存储、输出可以独立替换
3. Web-first，不跟随 Electron 或云端中心化架构
4. 输出不止给人看，也要服务知识库、日报、Webhook 和后续消费者系统

## 2. 五层架构

### 2.1 信源层

- RSS / Atom
- RSSHub 桥接源
- 播客 RSS 与音频链接
- 网页快照与变更监控
- 自定义采集器

当前未工程化但保留方向：

- X / Twitter
- Newsletter 稳定链路
- 更多非 RSS 半结构化来源

### 2.2 采集层

- `hub-engine` 负责调度、抓取、去重入库
- 统一支持手动抓取和定时抓取
- 采集器按类型拆分为 RSS、RSSHub、YouTube、网页监控、Custom 等

### 2.3 处理层

- 规则过滤
- AI 评分、摘要、翻译
- 正文补抓与富化
- 音频转写、知识萃取、音频总结
- 日报多代理流水线

### 2.4 存储层

- PostgreSQL 多 schema 持久化业务数据
- 文件系统与 OSS 持久化音频与导出内容
- usage logs 记录 AI / ASR 调用消耗

### 2.5 输出层

- Feed 阅读界面
- Audio Studio
- Insights 日报工作台
- 导出能力
- 推送能力
- 面向未来的结构化知识消费者链路

## 3. 当前运行态架构

当前主干服务为：

- `nginx`：统一入口
- `apps/web`：前端静态资源
- `hub-engine`：核心采集与阅读 AI 引擎
- `audio-service`：音频处理与多模态处理
- `postgres` / `redis`
- `rsshub` / `changedetection` / `ntfy`

默认统一入口是 `http://localhost`，健康检查路径包括：

- `/health`
- `/api/health`
- `/api/audio/health`

## 4. 核心数据流

### 4.1 阅读条目

1. 来源进入采集器
2. 统一入库 `hub.items`
3. 规则过滤、AI 评分、摘要、翻译
4. 打开详情时，如正文缺失可通过 `enrich` 再补抓
5. 最终在 Feed、日报、导出中被消费

### 4.2 音频条目

1. Feed 新音频条目或用户手动上传/贴链接
2. `hub-engine` 或前端创建音频任务
3. `audio-service` 走 `OSS + 远程批量 ASR` 主路径
4. Webhook 回写 transcript / knowledge / duration / 状态
5. Feed 与 Audio Studio 两端都能读取结果

### 4.3 日报链路

1. 从当日条目与近 7 天上下文构造快照
2. 进入多代理流水线：清洗 / 决策 / 研究 / 阅读导航
3. 结构化结果与 Markdown 同时持久化
4. 在 Insights 页面和导出通道中被消费

## 5. 当前与顶层设想的偏差

已经成立的部分：

- 管道分层
- 本地优先
- 主干工作台
- 音频闭环
- 多代理日报

仍偏弱的部分：

- 非 RSS 采集能力不够宽
- 输出层更像“给人看的工作台”，还不够像“给系统消费的数据引擎”
- 垂直专题洞察还没有沉淀成长期资产

## 6. 设计边界

明确不做的方向：

- 不迁移到 Electron 架构
- 不依赖 Folo / Follow 云 API
- 不做“大而全”的架构翻修

继续可借鉴的方向：

- Folo 的交互与信息架构
- 更高密度的阅读工作流
- 更顺手的发现订阅体验
