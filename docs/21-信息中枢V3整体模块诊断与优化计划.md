# 信息中枢 V3 整体模块诊断与优化计划

## 1. 结论先行

信息中枢 V3 当前不是“还没做出来”，而是进入了更危险的阶段：**能力很多，主链路不够可信；数据很多，阅读和日报没有稳定转成可消费的高质量信息产品**。

当前系统已经具备：

- 706 个 active sources。
- 约 19002 条 items。
- 近 24 小时约 7574 条新增 / 更新。
- 近 24 小时约 8608 次 AI usage log。
- RSS、网页监控、网页索引、BestBlogs、邮箱、音频、Dibao 侧车等入口。
- Feed 三栏、日报工作台、日报阅读页、Sources 健康、AI Usage、Reader Lab 等页面。

但真正卡住体验的不是“缺功能”，而是四个根因：

1. **内容层没有成为硬边界**：RSS 正文、网页快照、网页索引摘要、榜单摘要、原站正文都进入同一个阅读流，用户需要自己判断“这到底是不是正文”。
2. **AI 后处理完成率与状态反馈不足**：大量条目还是 pending/skipped，翻译 ready 很少，阅读资产表当前为空，Article Agent 没有形成资产闭环。
3. **日报没有真正变成信息雷达**：日报类型和字段已经扩展，但最新 payload 的 coverage index 仍为空，重点文章和模块叙事没有覆盖足够多候选。
4. **前端仍然把诊断暴露在阅读主路径**：Feed 和日报都能看到大量系统解释、状态和按钮，但正文、目录、重点结论、可点击证据反而不够突出。

下一阶段不应继续“加页面、加按钮、加新入口”。正确方向是：**先立内容可信合同，再收敛阅读主路径，最后把日报做成模块化雷达**。

2026-06-17 追加证据：黄金样本矩阵暴露出 `OpenAI` 来源实际订阅 URL 为 `https://www.v2ex.com/feed/openai.xml`，已有 166 条内容挂在该源下。这说明“内容乱”并不总是正文抽取失败，也可能是**来源命名、URL 和用户预期错配**。因此 Sources 治理必须把 `config_mismatch` 作为一等健康状态，避免官方名义源混入社区讨论后污染 Feed 和日报。

2026-06-17 追加验收：黄金样本矩阵已从 8 类扩展为 12 类，并支持多用户 token 聚合，能同时覆盖 Reise 主账号和 acceptance_admin 下的 BestBlogs、Anthropic、邮箱样本。最新真实刷新结果：12 类样本全部命中，6 通过、6 复核、0 缺样本；复核项集中在 BestBlogs 原站待补、网页快照降级、OpenAI 官方源错配和 OpenAI News 正文债务。

## 3. 重点模块地图

### 3.1 基础设施与运行

主要文件：

- `docker-compose.yml`
- `nginx/nginx.conf`
- `services/hub-engine/src/index.ts`
- `services/hub-engine/src/scheduler/*`

当前能力：

- Docker 全栈已跑通。
- Redis + BullMQ 已用于 fetch worker 和 daily report worker。
- Hub Engine 启动时包含 schema compatibility 修补。
- Nginx 提供统一入口。
- Dibao 侧车已经接入。

主要问题：

- `ensureSchemaCompatibility()` 里承担了大量运行时 DDL 和数据修补，长期会让启动路径变重、失败难定位。
- 当前大 diff 未收口，运行态和代码态之间缺少“已验证版本”标记。
- 有些能力依赖启动时兼容修补，而不是明确迁移版本。

优化方向：

- 把 P0 schema 变更整理成正式 migration 或 init-db 分段记录。
- 保留启动兼容修补，但只做安全补丁，不继续堆业务逻辑。
- 建立“当前 Docker build hash / 前端 dist 更新时间 / 后端 commit 状态”诊断字段。

### 3.2 来源与采集

主要文件：

- `services/hub-engine/src/collectors/rss.ts`
- `services/hub-engine/src/collectors/webpage.ts`
- `services/hub-engine/src/collectors/webpage-index.ts`
- `services/hub-engine/src/scheduler/pipeline.ts`
- `services/hub-engine/src/routes/fetch.ts`
- `services/hub-engine/src/routes/subscriptions.ts`

当前能力：

- RSS / RSSHub / YouTube / changedetection / webpage / webpage_index / custom / email。
- RSS collector 已开始做 `chooseBestFeedContent()`，并纳入 Atom `summary`。
- `webpage_index` 已用于 BestBlogs / Anthropic Newsroom 这类索引页。
- fetch queue 已存在。

主要问题：

- 来源类型过多，但 Feed 里仍容易被混成“都是文章”。
- RSS 的字段选择已有改善，但还需要用真实源持续回归：Simon Willison、John D. Cook、Daring Fireball、OpenAI、Anthropic。
- `webpage` 快照和 `webpage_index` 单篇索引必须严格区分，否则用户会觉得“抓到莫名其妙的东西”。
- 对源质量的策略还不够强：哪些源只信 RSS，哪些源必须全文补抓，哪些源只进监控，不应靠用户猜。

优化方向：

- 建立 source-level `contentStrategy`: `feed_only / smart_readability / force_fulltext / index_only / monitor_only`。
- 对每个 source 输出“抓取真相”：最近抓到的是全文、摘要、索引、快照还是失败。
- 对 `webpage` 快照默认降权，不进 Feed 推荐和日报主线；除非显式在监控页查看。

### 3.3 正文抽取与阅读可信层

主要文件：

- `services/hub-engine/src/lib/content-extractor.ts`
- `services/hub-engine/src/lib/item-enrichment.ts`
- `services/hub-engine/src/lib/reading-context.ts`
- `apps/web/src/lib/readable-content.ts`
- `apps/web/src/components/MarkdownContent.tsx`

当前能力：

- 已接入 Readability、DOMPurify、linkedom。
- 数据库已有 `readability_content / readability_status / readability_reason`。
- `contentReadiness` 已区分全文、摘要、索引、榜单、快照、失败。
- `translate-full` 已有 fetch-then-translate 方向。

主要问题：

- 绝大多数条目 `readability_status=missing`，说明这层还没有成为主路径。
- `items.content` 仍混合 HTML、Markdown、纯文本、摘要、快照。
- 前端还需要判断 `readabilityContent || content || snippet`，容易把不该展示的内容当正文。
- 代码块、公式、表格、脚注、图片、链接间距仍有可读性问题。

优化方向：

- 把 `readabilityContent` 作为 Feed 原文 tab 的第一优先级，并且只有 `readability_status=ready` 才叫“全文可读”。
- 对 RSS feed 自带完整 HTML 的条目也生成 `readabilityContent` 或 `content_html/content_text` 双字段。
- 对存量高价值源跑一次离线 backfill：Simon、John D. Cook、Daring Fireball、BestBlogs、Anthropic、OpenAI、TechCrunch。
- 新增正文质量审计脚本每日输出：全文率、索引摘要率、快照率、疑似噪音率。

### 3.4 AI 评分、摘要、翻译与阅读资产

主要文件：

- `services/hub-engine/src/processors/ai-scorer.ts`
- `services/hub-engine/src/processors/ai-summarizer.ts`
- `services/hub-engine/src/lib/article-assets.ts`
- `services/hub-engine/src/routes/items.ts`
- `services/hub-engine/src/lib/ai-usage.ts`

当前能力：

- 评分、摘要、翻译、质量过滤、AI usage log 都存在。
- 已有 `item_reading_assets` 表和五类 Article Agent prompt。
- `/api/items/:id/assets` 已有生成资产方向。
- `/api/items/:id/translate-full` 已有显式全文翻译接口。

主要问题：

- `item_reading_assets=0`，说明资产生成还没有真实使用或未被用户触发。
- 翻译 ready 数量很少，且失败里有 `translation_truncated_or_empty`、`summary_must_be_chinese` 等机器状态。
- 中文改写、摘要、翻译的边界对用户不清楚，容易看起来“都是一段摘要”。
- AI usage 数量大，但页面上难以看出哪一类调用真的改善了阅读。

优化方向：

- Feed 主 tab 固定为：`摘要 / 原文 / 翻译`。
- `中文改写 / 问文章 / 转写 / 知识 / 诊断` 收入右侧资产抽屉。
- 翻译 tab 永远显示明确主动作：`一键翻译全文 / 补抓原文并翻译 / 打开原文`。
- Article Agent 先做 5 个固定资产生成，并在 Feed / 日报重点文章里引用。
- AI Usage 按阅读、日报、来源修复、音频分场景展示，避免只是 token 账单。

### 3.5 Feed 阅读工作台

主要文件：

- `apps/web/src/features/feed/page.tsx`
- `apps/web/src/lib/feed-layout.ts`
- `apps/web/src/lib/feed-diagnostics.ts`
- `apps/web/src/lib/reading-assets.ts`

当前能力：

- 已经是三栏结构：来源栏 / 文章列表 / 阅读详情。
- 支持推荐、最新、评分筛选、来源筛选、内容状态提示。
- 支持工具、诊断、资产、翻译动作。

主要问题：

- 顶部全局信息、搜索、提醒、工具按钮仍占据过多面积。
- 详情页仍像诊断台，而不是阅读器。
- 很多低频按钮常驻：补抓、重跑 AI、精译、资产、日报解释、阶段修复等。
- 列表卡片的优先信息不够克制，标签仍偏多。
- 用户真正想做的是“读正文、看摘要、翻译、收藏/已读/下一篇”，其他都应低频。

优化方向：

- Feed 顶部压缩：搜索和筛选保留，系统提醒默认一行折叠。
- 详情标题区只保留来源、标题、时间、打开原文、收藏/已读、更多菜单。
- 详情主内容宽度 760-860px，字号 17px，行高 1.8-1.9。
- 主 tab 只保留 `摘要 / 原文 / 翻译`。
- 更多工具菜单承载补抓正文、重跑摘要、重跑翻译、生成文章资产、复制链接、打开原文。
- 右侧轻量栏显示文章资产和问文章，不干扰正文。

### 3.6 日报工作台与日报阅读页

主要文件：

- `services/hub-engine/src/outputs/daily-report.ts`
- `services/hub-engine/src/outputs/daily-report-workflow.ts`
- `services/hub-engine/src/lib/daily-generation-progress.ts`
- `services/hub-engine/src/routes/daily.ts`
- `apps/web/src/pages/Daily.tsx`

当前能力：

- 已有日报工作流配置。
- 已有异步生成 job 和 progress。
- 已有趋势、重点文章、模块叙事、更多动态、覆盖索引等类型。
- 已有日期导航、候选池、工作台、正式阅读页。

主要问题：

- coverage index 没有真实进入已保存日报 payload，最新样本 `coverageItems=0`。
- 模块化日报仍偏“字段存在”，不是稳定内容产品。
- 标题、目录、右侧 sticky nav、Markdown 样式都还不够像正式日报。
- 日报素材引用数量不足，无法承担“信息雷达”。
- 候选分层没有强制验收：精选、模块引用、更多动态、深读、附录各自覆盖多少文章。

优化方向：

- 日报生成前固定产出 `editorialDigest`：
  - `curatedDeepDive` 8-12 篇。
  - `moduleReferences` 20-35 篇。
  - `moreDynamics` 10-20 篇。
  - `coverageIndex` 全池摘要。
- 正式日报结构固定：
  - 今日封面判断。
  - 信息雷达总览。
  - 今日精选。
  - 模块日报。
  - 更多动态。
  - 重点研究/深读。
  - 阅读顺序。
  - 下一步行动。
  - 附录：全池摘要索引。
- 页面右侧目录 sticky，滚动时高亮当前章节。
- 正文 Markdown 使用明确样式：h2/h3、引用、链接卡片、重点文章列表、模块卡片、动态列表。
- 不允许 final report 只有 topItems 而无 coverageIndex。

### 3.7 Sources 治理与来源健康

主要文件：

- `services/hub-engine/src/lib/source-health.ts`
- `services/hub-engine/src/routes/sources.ts`
- `apps/web/src/features/sources/page.tsx`

当前能力：

- 已有抓取、正文、展示、AI、日报五段健康模型。
- 已有 email / curated_index 用户语言区分。
- 已有推荐动作：抓取、检查配置、修复正文、修复 AI、日报覆盖。
- 已新增 `config_mismatch` 健康状态，用于识别“来源名称像官方源，但订阅 URL 指向第三方/社区站点”的情况。

主要问题：

- Sources 页容易变成指标堆叠，主治理动作不够突出。
- 来源级策略没有彻底产品化：只看健康分，不知道应该改成 feed_only 还是 force_fulltext。
- 来源和日报之间的影响关系仍不够清晰：哪些源影响今天日报、哪些只是噪音源。
- 来源命名治理需要进入常规巡检：例如 `OpenAI` 源实际指向 `v2ex.com`，这类问题会让用户误判为抓取/翻译/日报质量问题。

优化方向：

- Sources 首页默认按健康状态分组，不按全量表格展示。
- 每个来源详情只回答五个问题：
  1. 最近抓取成功了吗？
  2. 抓到的是全文还是摘要？
  3. 展示可读吗？
  4. AI 后处理卡在哪里？
  5. 对日报有没有贡献或拖累？
- 增加 `contentStrategy` 可编辑。
- 增加“对今天日报的影响”入口。

优化方向：

## 8. 判断标准

后续每一轮优化都按四个问题验收：

1. **可信**：用户能看懂这个内容从哪里来、是不是正文、为什么缺失。
2. **可读**：默认界面像阅读器，不像后台管理面板。
3. **可行动**：失败状态有明确按钮和结果反馈。
4. **可复利**：阅读、反馈、文章资产、日报能够互相回流。

如果一个改动不能至少改善其中一项，就不应该进入当前收口轮。
