5. 层内排序：数据完整性 > 用户可见正确性 > 一致性 > 结构优化。

## 1. P0：安全与真实性（10 项）

### P0-1 收回端口暴露面

- **问题**：10 个已发布端口全部绑定 `0.0.0.0`，实测局域网可达（`38` §3.1.1）。nginx 统一入口形同虚设。
- **改法**：`docker-compose.yml` 中除 nginx 的 `80` 外，全部端口映射改为 `127.0.0.1:<port>:<port>` 形式。若需保留局域网访问（如手机看 Feed），只保留 nginx 一个出口，其余一律回环。
  - **不要顺手做"把 postgres/redis 放进 internal 网络（不设 ports）"**——实测这会立刻打断三处宿主机直连：`scripts/dev/cleanup-stale-fetch-jobs.sh:14`、`scripts/dev/seed-default-ai-rules.sh:66`（均直连 `127.0.0.1:5432`）以及 `qa/` 下 8 个用 `localhost:3001` 的脚本。网络隔离如要做，须另立条目并同时声明全部 12 个服务的网络归属。
- **不会破坏什么（已核实）**：容器间通信全部走 docker 服务名——`nginx.conf` 的 6 个 `proxy_pass` 指向 `audio-service:8000`/`hub-engine:3001`/`changedetection:5000`/`rsshub:1200`/`ntfy:80`/`dibao-reader:8080`，hub-engine 访问 `scrapling-service:8010`、`audio-service:8000`、`rsshub:1200` 同理。`ports:` 映射只影响宿主机能否访问，**改成回环绑定不影响任何容器间调用**。唯一受影响的是宿主机上的直连调试（如 `psql -h localhost`、Vite dev server 的 `localhost:3001` 代理）——前者改用 `docker exec`，后者若需本地开发可保留 3001 的回环绑定。
- **涉及文件**：`docker-compose.yml`（约 10 处 `ports:` 段）
- **验收标准**：
  ```bash
  docker compose ps --format '{{.Service}}\t{{.Ports}}'   # 除 nginx 外无 0.0.0.0
  # 注意：不能用 nc -z localhost —— 回环永远通，测不出局域网是否收回
  LAN_IP=$(ipconfig getifaddr en0)
  nc -z -G 1 "$LAN_IP" 6379 && echo "❌ 仍暴露" || echo "✅ 已收回"
  nc -z -G 1 127.0.0.1 6379 && echo "✅ 回环仍可达（预期如此）"
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost/api/health  # 期望 200
  ```
  改动前先跑一遍上述命令留基线（当前两条 nc 都会成功）。改完必须回归 `bash scripts/qa/run-regression.sh --full --no-report`——它依赖 `localhost:3001`。
- **工作量**：S
- **依赖**：无。**建议第一个做**——它单独就能把 P0-2、P0-3、P0-4 的现实风险降到最低。

### P0-2 scrapling-service 增加鉴权与内网地址黑名单

- **问题**：`POST /extract/article`、`/extract/snapshot` 无认证、无 URL 校验、回显目标响应正文，构成可回显 SSRF 代理（`38` §3.1.2）。
- **改法**：
  1. 增加内部 API Key：读环境变量 `SCRAPLING_INTERNAL_KEY`，用 FastAPI 依赖校验 `X-Internal-Key` 头；hub-engine 侧在 `lib/scrapling-client.ts` 带上该头。
  2. 增加 URL 校验函数，在 `_extract()` 入口拒绝：私有网段（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`::1`、`fc00::/7`）、非 `http(s)` scheme、以及解析后 IP 落入上述网段的域名（防 DNS 重绑定，需在 fetch 前做一次解析校验）。
  3. **校验函数必须放在 `_extract()` 入口（`main.py:120`）而非各端点内**——两个端点已经都调用同一个 `_extract()`，放在那里天然覆盖两条路径。（初稿写的"合并两个端点"是无效动作，它们本就共用实现。）
- **涉及文件**：`services/scrapling/app/main.py`、`services/hub-engine/src/lib/scrapling-client.ts`、`docker-compose.yml`、`.env.example`
- **验收标准**：
  ```bash
  KEY=$(grep -E '^INTERNAL_API_KEY=' .env | cut -d= -f2-)
  curl -s -o /dev/null -w '无key=%{http_code}\n' -X POST http://127.0.0.1:8010/extract/article \
    -H 'Content-Type: application/json' -d '{"url":"https://example.com"}'       # 期望 401
  curl -s -o /dev/null -w '内网=%{http_code}\n' -X POST http://127.0.0.1:8010/extract/article \
    -H "X-Internal-Key: $KEY" -H 'Content-Type: application/json' \
    -d '{"url":"http://127.0.0.1:5432"}'                                          # 期望 400
  curl -s -o /dev/null -w '外链=%{http_code}\n' -X POST http://127.0.0.1:8010/extract/article \
    -H "X-Internal-Key: $KEY" -H 'Content-Type: application/json' \
    -d '{"url":"https://example.com"}'                                            # 期望 200
  ```
  真实外链抓取链路不回归：在 `/sources` 触发一次动态源抓取，确认正文正常。
- **省一步**：`.env.example:20` 已有 `INTERNAL_API_KEY`，直接复用可免去新增键与 compose 同步。若坚持新增 `SCRAPLING_INTERNAL_KEY`，需同时改 `docker-compose.yml` 的 `scrapling-service`（该服务当前**没有 environment 段，需新建**）与 `hub-engine`（`:125-162`）两处。
- **调用侧确切位置**：`scrapling-client.ts:45` 与 `:77` 两处 fetch 的 headers。
- **工作量**：M

### P0-3 Redis 设置访问口令

- **问题**：`command: redis-server --appendonly yes` 无 `requirepass`（`38` §3.1.3）。BullMQ 与 Celery 共用，可读写全部队列。
- **改法**：compose 中改为 `redis-server --appendonly yes --requirepass ${REDIS_PASSWORD}`，并同步**全部 11 处** Redis 连接串——`:51`（**rsshub，最易漏，漏改会直接打断 RSSHub 的 Redis 缓存**）、`:128`（hub-engine）、`:203/205/206`、`:255/257/258`、`:302/304/305`（audio 三份，见 P2-4 的重复问题），加 `.env.example:13` 共 12 处。
- **必须同时改 healthcheck，否则验收会被假绿灯骗过**：当前 `:37` 是 `["CMD","redis-cli","ping"]`，而 `redis-cli` 对 `NOAUTH` 错误回复**仍返回 exit code 0**——加了口令后 healthcheck 会永远为真，"全部 healthy"就证明不了任何事。改为：
  ```yaml
  test: ["CMD-SHELL", "redis-cli -a \"$$REDIS_PASSWORD\" --no-auth-warning ping | grep -q PONG"]
  ```
  并给 redis 服务加 `environment: REDIS_PASSWORD: ${REDIS_PASSWORD:?required}`。
- **涉及文件**：`docker-compose.yml`、`.env.example`、`services/hub-engine/src/config/index.ts`、`services/audio/app/config.py`
- **验收标准**：`docker exec infohub-redis redis-cli ping` 应**打印** `NOAUTH`（注意其 exit code 仍是 0，需肉眼判读）；`docker exec infohub-redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning ping` 应返回 `PONG`；`docker logs infohub-rsshub --tail 50` 无 Redis 认证错误；`docker compose ps` 全部 healthy；`/audio` 页提交一个任务能正常进入队列。
- **工作量**：S
- **依赖**：与 P0-1 同批做，改完一次重启。

### P0-4 禁用默认种子管理员账号

- **问题**：`auth.users` 中 `admin@example.com`（role=**admin**，创建于 2026-03-03）至今存活未禁用，密码明文记录在 `local-secrets/infohub-credentials.md`。配合 audio 的 8000 端口绑 `0.0.0.0`，等于一个默认凭据的管理员挂在局域网可达的服务上（`38` §3.1.6）。
- **改法**：禁用该账号（`is_active=false`）或改为强随机密码；确认 audio-service 的初始化逻辑不会在下次启动时重建它（检查 `AUDIO_ADMIN_EMAIL`/`AUDIO_ADMIN_PASSWORD` 的使用点）。若音频链路对它有硬依赖（`docs/36` 曾记录"为了不破坏音频链路予以保留"），则改密而非删除，并记录依赖点。
- **涉及文件**：数据库 `auth.users`、`services/audio/app/`（初始化逻辑）、`.env`、`local-secrets/infohub-credentials.md`
- **验收标准**：用旧凭据登录 audio 侧应失败；`docker compose restart audio-service` 后该账号不被重建为默认密码；音频链路提交一个任务正常完成。
- **工作量**：S
- **依赖**：与 P0-1 同批。

### P0-5 QA 账号生成端加回收，堵住僵尸账号再生

- **问题**：2026-07-13 清理 497 个 QA/shadow 用户后，**十一天内重新累积 72 个**（全部建于 07-20～07-24），`quota.user_quotas` 同步涨到 76 行。生成端无回收机制，清理动作必然复发（`38` §2.4、§7 根因 A）。
- **改法**：
  1. 定位 QA 账号创建点（`qa/` 下的 e2e 脚本，`qa_e2e_folo_*` 命名可定位），在测试结束时清理自己创建的账号（teardown）。
  2. 或增加定期清理任务：删除 `email like 'qa\_%'` 且 `created_at < now() - interval '7 days'` 的账号及其关联 quota 记录（注意 `quota.user_quotas_user_id_fkey` 外键，先删子表）。
  3. **两者都做更好**：teardown 防新增，定期清理兜底。
- **涉及文件**：`qa/p0/*.sh`、`qa/helpers/auth.sh`、可选新增清理脚本
- **验收标准**：跑一轮 `make qa-verify` 前后对比 `select count(*) from auth.users where email like 'qa\_%'`，数量应回到基线而非净增；清理脚本在 dryRun 下输出预期删除数。
- **工作量**：M
- **依赖**：**这条是 D-1（削减多租户）的前置**——生成端不堵，砍存量没有意义。

### P0-6 SPA 会话中途 401 的统一处理

- **问题**：`lib/api/shared.ts:99-102` 对 401 无特殊处理。刷新路径靠 `RequireAuth` 兜底正常，但 SPA 会话中途 token 失效时不跳登录、不清 token、页面继续显示旧数据，仅弹一条裸英文 `Unauthorized`（`38` §4.2，截图 W07b）。
- **改法**：在 `request<T>()` 中拦截 401：清除 `infohub_v3_access_token`、清空 auth context 的 user、跳转 `/login` 并带 `state.from`（复用 `App.tsx:44-46` 已有的回跳约定）。注意避免登录接口自身的 401 触发跳转循环。同时把裸英文错误消息本地化。
- **设计陷阱（不写清楚执行者会卡住）**：`shared.ts` 是纯模块，**不是 React 组件，拿不到 `useNavigate`/`useLocation`**。两条路只能选第一条：
  - ✅ **(a) 回调注册**：在 `auth.tsx` 暴露 `registerUnauthorizedHandler(cb)`，`shared.ts` 收到 401 时调用它；`cb` 内部用 router 的 `navigate('/login', { state: { from: location } })`。
  - ❌ (b) 在 `shared.ts` 里 `window.location.assign('/login')`：整页刷新，**无法携带 router state**，回跳约定会与 `RequireAuth` 分叉。
  **必须选 (a)。**
- **涉及文件**：`apps/web/src/lib/api/shared.ts`、`apps/web/src/lib/auth.tsx`、`apps/web/src/lib/auth-storage.ts`
- **验收标准**：登录后在 `/sources` 页面用 devtools 把 localStorage 的 token 改成无效值（不刷新），点击任一操作 → 应自动跳转 `/login`，且 localStorage 中 token 已清除。
- **工作量**：M

### P0-7 retention 删除加事务、分批与真实计数

- **问题**：四条裸 DELETE 无事务无分批；`summary.deleted` 复制删除前 `count(*)` 而非 rowCount；`status` 恒为 `success`；DELETE 中途抛错时 `retention_runs` 无任何记录（`38` §3.2.2）。
- **改法**（注意 1/2/5 三者的相互约束，初稿写法自相矛盾，已修正）：
  1. **事务只包 DELETE，不包 `retention_runs` 的写入**——否则改法 5 的 `failed` 记录会跟着一起回滚，等于没记。
  2. **分批删除时每批一个独立事务**（每批约 1000 行循环至无剩余）。若把整个循环包进一个大事务，锁照样持到最后，分批就失去意义。
  3. `summary.deleted` 改为读取每条 DELETE 的真实 `rowCount`。
  4. `status` 按 `summary.errors` 与 `storageDeleteFailed` 真实判定（`success`/`partial`/`failed`）。`retention_runs.status` 是裸 `text` 列（`schema.ts:374`）无 check 约束，写新值安全。
  5. 用 `finally`（或 catch 之后、事务之外）保证异常路径也写入 `retention_runs`。
  6. 30 天改为可配置：`config` 增加 `RETENTION_DAYS`，`cron.ts:142` 读取之。
  7. **顺手修一个真 Bug**：`retention.ts:115` 的删除条件用 `generated_at < ${cutoffIso}::date`，而 `countOlderThan`（`:42`）用的是 `::timestamptz`。`::date` 会把时间戳截断到当天 00:00，**导致 DELETE 范围严格窄于 COUNT**——这正是"统计数字与实际不符"的根源之一。不改这行，即使换成真实 rowCount，dry-run 预览仍会虚高。
- **涉及文件**：`services/hub-engine/src/lib/retention.ts`（`:108-145` 为主）、`services/hub-engine/src/scheduler/cron.ts:142`、`services/hub-engine/src/config/index.ts`
- **验收标准**：`runRetention()` 是 TS 函数，shell 跑不了；实际入口是 `routes/admin-retention.ts` 的 `POST /run`（需 admin JWT，nginx 已有 `/api/admin/retention/` 转发）：
  ```bash
  TOKEN=<admin JWT>
  curl -s -X POST http://localhost/api/admin/retention/run \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"retentionDays":30,"dryRun":true}' | jq .
  ```
  （`runRetention` 的 `dryRun` 默认为 true——`retention.ts:76` 是 `options?.dryRun !== false`，误删风险低。）
  然后在测试库上跑一次真实清理，核对 `retention_runs.deleted` 与 `select count(*)` 前后差值**完全一致**；人为制造一次失败（如临时改错表名），确认写入 `failed` 记录而非无记录。
- **工作量**：M
- **依赖**：**必须先做 P1-1 的库快照**，这是唯一直接删数据的条目。

### P0-8 修复 audio worker 连接池泄漏

- **问题**：`_make_session()` 每次调用新建 engine，13 处调用点，全仓 0 处 `dispose`。实测 31 条连接中 **24 条泄漏**（`audio-worker` 15 + `audio-worker-asr` 9，后者以 `--pool=solo --concurrency=1` 运行却持有 9 条并发连接），`backend_start` 与音频任务创建时刻逐分钟吻合，任务停止两天后一条未释放（`38` §3.3）。
- **紧迫性说明**：`max_connections=100`，当前约 1.7 条/任务，约 50 个任务后耗尽连接槽，worker 重启即清零。**属慢速累积的潜在风险，不是正在燃烧的故障**——列 P0 是"防患"，可排在 P0-1~P0-5 之后。
- **改法**：**不要先试模块级单例——代码里已有明确约束否掉了它**。`audio_pipeline.py:25-26` 的注释写着"每次调用创建新 engine，避免跨 event loop 复用连接池"，而 `_run_async()`（`:32-38`）每次都 `asyncio.new_event_loop()` 并在结束时关闭；asyncpg 连接绑定在创建它的 loop 上，单例 engine 会在第二次调用时炸。
  **正确改法**：保持"每次新建 engine"，但在 `_run_async()` 的 `finally` 里 `loop.run_until_complete(engine.dispose())` **再**关闭 loop——即把 engine 生命周期与 loop 生命周期对齐。或者更彻底：改用 `asyncio.run()` 并在协程内部用 `async with` 管理 engine。
- **涉及文件**：`services/audio/app/tasks/audio_pipeline.py:27-38` 及 12 处调用点
