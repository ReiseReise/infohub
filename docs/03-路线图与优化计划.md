# 路线图与优化计划

## 1. 这一轮路线图的判断标准

接下来不再继续围绕“文档治理”推进，而是回到影响系统长期价值的三个判断标准：

1. 是否让系统更接近“数据引擎”，而不是只像阅读器
2. 是否让高频工作流更稳、更省判断成本
3. 是否能沉淀出专题型长期资产

所以路线图的优先级，不按“哪个功能听起来更大”排，而按下面这个顺序排：

1. 先收口真会造成混乱的运行与治理问题
2. 再补足输入与输出这两端
3. 最后深化垂直专题能力

## 2. 三层推进路线

### 第一层：把运行与治理做扎实

这是最近一轮最该做完的事情，目的不是“更炫”，而是减少误判和隐藏成本。

#### P0-1 数据新鲜度与手动启动治理

- 目标：启动即补抓到期来源，Feed / Sources / Settings 都能解释“为什么现在看到的是旧数据”
- 结果：本地手动启动模式下的数据过期不再是黑箱

#### P0-2 AI 管理中心重构为场景控制台

- 目标：把 AI 中心固定成 `场景控制台 / 模型仓库 / 评分 Skills / 使用日志`
- 结果：管理员能直接回答“哪个功能正在用哪个模型、这个模型的别名是什么、Skills 在哪里管理”

#### P0-3 动态网页模板与非 RSS 第一批模板

- 目标：基于原生 + Scrapling 分层抓取，补 1 到 2 个高价值来源模板
- 结果：输入面开始真正覆盖“最有价值但最不规整”的来源

### 第二层：回到数据引擎定位

这是系统从“好用工作台”继续长成“上游数据引擎”的关键阶段。

#### P1-1 结构化输出消费者链路

- 目标：补强 Webhook / API / 知识库导出合同
- 结果：系统输出不只给人读，也能给系统消费

#### P1-2 Feed 到专题的串联能力

- 目标：让高价值条目不只停在列表里，而能更自然流向专题洞察
- 结果：用户从“读一条”过渡到“管理一个主题”

#### P1-3 豆包标准字段彻底收口

- 目标：运行态与认知层只强调 `DEFAULT_LLM_ENDPOINT_ID`
- 结果：Provider 配置不再保持双轨制

### 第三层：深化垂直专题洞察

这是让系统产生真正长期价值的部分。

#### P2-1 AI / 头部舆论专题洞察深化

- 目标：把 AI 产业、头部舆论、资本与产品信号做成长期专题资产
- 建议分组：
  - AI 基础设施 / 模型层
  - 产品落地 / Agent 应用
  - 头部舆论 / 监管 / 资本定价

#### P2-2 专题知识输出与复盘

- 目标：把专题结果从日报升级成可复用的知识资产
- 结果：系统开始拥有“累积理解”，而不是每天重新写一遍

## 3. 对顶层设想的真正差距

当前系统已经符合顶层设想中的：

- 管道分层
- 本地优先
- 24/7 基础运行
- 采集、处理、输出闭环

但还不够强的地方，已经可以明确压缩成三句：

1. 输入面还不够宽
2. 输出面还不够结构化
3. 专题面还不够深

所以接下来真正该继续做的，不是再拆更多页面，而是：

- 更强采集
- 更强输出
- 更深专题

## 4. Folo 借鉴边界

继续借鉴的部分：

- Discovery 结果排序与反馈
- 重度阅读效率
- Settings / Feed 的信息架构组织

明确不借的部分：

- Electron 架构
- 云端中心化 API 依赖
- monorepo + 全局 store 的组织方式

判断标准固定为：

1. 是否显著提升使用效率
2. 是否不破坏 Web-first 和本地可控
3. 是否不引入新的架构耦合

## 5. 建议的推进节奏

### 第 1 轮：动态抓取与历史治理收口

- Scrapling 抓取诊断透到前端
- Retention 安全边界收口
- 动态网页模板与非 RSS 第一批模板

### 第 2 轮：回到数据引擎定位

- 结构化输出合同
- Feed 到专题的串联能力
- 豆包标准字段退兼容

### 第 3 轮：垂直专题深化

- AI / 头部舆论专题日报模板
- 专题场景配置
- 专题知识输出与复盘资产
