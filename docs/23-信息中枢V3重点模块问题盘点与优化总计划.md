# 信息中枢 V3 重点模块问题盘点与优化总计划

## 1. 结论

信息中枢 V3 现在的真实阶段，不是“功能缺失”，而是“底层链路不够收敛”。

系统已经具备完整的产品骨架：

- 输入：RSS、网页监控、网页索引、BestBlogs、邮箱、音频、Dibao 对照侧车。
- 处理中台：去重、过滤、评分、摘要、翻译、优先级、日报生成、来源健康。
- 输出：Feed、Sources、日报工作台、日报阅读页、AI 用量、Reader Lab。

但用户感知仍然不稳定，核心不是按钮不够多，而是下面四件事没有形成硬合同：

1. **内容合同不清楚**：全文、索引摘要、榜单摘要、网页快照、RSS 片段都进了同一阅读流。
2. **阅读主路径不够克制**：正文不是绝对主角，诊断和动作暴露过多。
3. **日报还不是“信息雷达”**：有生成能力，但没有稳定形成趋势、模块叙事、重点文章和全池覆盖。
4. **来源治理没有完全前置**：不少问题不是 AI 问题，而是来源配置错配、源类型误用、原文层缺失。

所以后面的正确方向不是继续铺新页面，而是收口成一个闭环：

**可信来源 -> 可读正文 -> 克制阅读 -> 文章资产 -> 模块化日报 -> 来源健康反哺**

## 2. 当前项目态快照

基于当前本地仓库和最近验收结果，项目处于“大功能已齐，但质量债务集中暴露”的阶段。

### 2.1 已经具备的核心能力

- 多源采集框架已跑通。
- Docker 栈和 Nginx 统一入口稳定。
- Feed 三栏阅读台已经成型。
- 日报异步生成、工作台、阅读页和日期导航已经存在。
- 来源健康、AI 用量、黄金样本矩阵都已经有基础设施。
- Dibao 对照侧车已接入，具备同源对照能力。

### 2.2 已确认的数据证据

- 约 `706` 个 active sources。
- 约 `19002` 条 items。
- `readability_status=ready` 仅约 `519` 条，主链路正文层仍然偏薄。
- `item_reading_assets` 当前仍接近空层，读后资产闭环没有真正跑起来。
- 黄金样本矩阵已扩展到 `12` 类，最新是真实 `7 通过 / 5 复核 / 0 缺样本`。

### 2.3 当前最重要的定性判断

- **不是没抓到数据，而是抓到的数据没有稳定进入“可读层”。**
- **不是没做日报，而是日报仍在用“候选融合页”思维，而不是“编辑型雷达”思维。**
- **不是没做来源治理，而是治理结果没有真正影响阅读和日报权重。**

## 3. 重点模块全景

下面按“影响用户价值”的优先级来划分重点模块，而不是按代码目录。

| 模块 | 当前定位 | 当前判断 | 优先级 |
|---|---|---|---|
| 来源治理与采集 | 决定抓什么、抓得对不对 | 是一切问题的输入源头 | P0 |
| 正文抽取与内容可信层 | 决定看到的是不是正文 | 当前是最大系统债务 | P0 |
| Feed 阅读台 | 决定日常是否愿意使用 | 已有骨架，但阅读体验不够成熟 | P0 |
| AI 后处理与阅读资产 | 决定内容是否被进一步消化 | 有能力，未形成稳定资产闭环 | P1 |
| 日报雷达 | 决定是否形成“高质量输出” | 已能生成，但还不够像正式产品 | P0/P1 |
| Sources 健康中心 | 决定问题能否被解释与治理 | 已有基础，需升级为主治理面 | P1 |
| 外部源与对照体系 | 决定输入面能否扩宽且可校验 | 已有 BestBlogs/邮箱/Dibao 入口，仍是早期 | P2 |
| 运维与质量门禁 | 决定系统是否可持续维护 | 已有门禁，但需要从“测试存在”升级到“测试驱动治理” | P1 |

## 4. 分模块问题盘点

## 4.1 来源治理与采集

### 当前作用

这个模块决定三件事：

- 抓到什么。
- 这条数据应该当全文、线索还是监控。
- 这条数据后续有没有资格进入 Feed 推荐和日报主线。

### 当前主要问题

1. **来源命名与实际 URL 错配**
   - 已确认 `OpenAI` 源实际订阅了 `v2ex.com/feed/openai.xml`。
   - 这类问题会直接污染 Feed、评分、日报和黄金样本。

2. **来源类型已经丰富，但语义还没真正落到产品层**
   - `rss`、`curated_index`、`webpage`、`email` 已并存。
   - 但用户在阅读时仍容易把它们当成一样的“文章”。

3. **原文补抓策略不够按源分级**
   - 一些源应该 `feed-only`。
   - 一些源应该 `index-first then fetch original`。
   - 一些源应该只是 `monitor-only`。
   - 现在大多还靠运行时猜。

### 根因

- 缺少 source-level 的“正文策略合同”。
- 缺少配置错配的强告警和降权策略。
- 采集后的 item 路由和阅读层没有完全打通。

### 优化目标

- 让每个来源都有明确的 `contentStrategy`。
- 让来源错配从“隐藏 bug”变成一等健康状态。
- 让来源类型直接影响 Feed、翻译和日报资格。

## 4.2 正文抽取与内容可信层

### 当前作用

这是项目的真正底座。它决定：

- 用户看到的是原文还是伪原文。
- AI 摘要/翻译/评分基于什么内容。
- 日报拿到的是深读素材还是索引摘要。

### 当前主要问题

1. **正文层还没有成为绝对主路径**
   - `readability_status=ready` 数量偏低。
   - 很多条目仍只能回退到 `content/snippet/title`。

2. **不同内容形态混在一个字段里**
   - HTML、纯文本、RSS 摘要、榜单摘要、网页快照都可能在 `items.content` 里。

3. **一些 RSS 长文源没有充分利用 feed 原始字段**
   - 典型经验已经显示：某些 Atom/RSS 源的 `summary`/`description` 比网页补抓更干净。

4. **原文格式保真度不足**
   - 段落、列表、代码块、链接、脚注、图片仍会丢结构。

### 根因

- 缺少稳定的 `content_html / content_text / readabilityContent` 分层合同。
- 历史数据还没有完成高价值回填。
- 前端仍容忍“猜内容层”，而不是只吃可信正文层。

### 优化目标

- 让“原文”只代表可信正文，不再代表任何字符串。
- 让摘要、翻译、改写都明确标注基于哪一层生成。
- 让历史高价值源逐步完成正文回填。

## 4.3 Feed 阅读台

### 当前作用

这是系统最高频的日常使用入口。

### 当前主要问题

1. **阅读首屏仍过于像操作后台**
   - 顶部统计、到期抓取提醒、诊断条、资产条、工具条同时出现，正文被压缩。

2. **主标签过多**
   - 摘要、原文、翻译之外，改写、转写、知识、问文章等都和主阅读抢位置。

3. **正文占比和排版仍不够成熟**
   - 虽然三栏结构对了，但正文区还不够像阅读器。
   - 相比 Dibao/Folo/QMReader，正文没有形成绝对视觉中心。

4. **错误/缺失状态干扰阅读**
   - `translation_truncated_or_empty`、`content_unavailable` 这类技术状态不该暴露在正文主路径。

### 根因

- 产品目标混杂：既想展示治理信息，又想做阅读器。
- 工具和诊断没有被降频。
- 没有严格区分“高频阅读操作”和“低频修复操作”。

### 优化目标

- 首屏只留：标题、来源、时间、打开原文、摘要/原文/翻译三主标签。
- 其他能力进入右侧抽屉或“更多工具”。
- 正文区成为绝对主角。

## 4.4 AI 后处理与阅读资产

### 当前作用

它决定系统是不是只会“抓来给你看”，还是会“帮你沉淀可复用资产”。

### 当前主要问题

1. **摘要、翻译、改写、问文章还没有形成稳定资产层**
   - 有按钮、有流程，但沉淀层还弱。

2. **摘要和中文改写边界不清**
   - 当前用户感知里，二者容易变成重复内容。

3. **一键翻译和补抓原文链路不够稳定**
   - 没翻译时有时不报错、不触发、不解释。

4. **Article Agent 已开始落地，但还没成为日报素材层**
   - 问文章的结果没有真正反哺重点文章或模块叙事。

### 根因

- 资产类型和主阅读流程还没彻底分层。
- 旧 AI 结果字段和新资产表处于并存期。
- UI 还没有把资产能力明确放到“次级但重要”的位置。

### 优化目标

- 将 `摘要 / 原文 / 翻译` 作为主阅读层。
- 将 `改写 / 问文章 / 知识 / 转写` 收敛到资产层。
- 让文章资产真正进入日报引用层。

## 4.5 日报雷达

### 当前作用

这是项目最重要的输出产品。它不只是总结，而是你判断“今天发生了什么、为什么重要、该怎么读”的雷达。

### 当前主要问题

1. **日报还偏“系统生成结果展示页”**
   - 有生成、有结构，但离正式读物还差一步。

2. **模块叙事不够厚**
   - 候选很多，但实际正文仍只围绕少量 top items 融合。

3. **全池覆盖索引没有稳定进入 payload**
   - `coverageItems` 为空是当前最明显的结构性缺口。

4. **目录、导航、Markdown 结构和 sticky 阅读辅助还不成熟**
   - 目录滚走、右侧导航不稳、结构块不够明确。

5. **缺少真正的“信息雷达总览”**
   - 还没有形成“今日判断 + 模块雷达 + 更多动态 + 深读建议”的完整阅读心智。

### 根因

- 日报仍更多依赖一次性 final prompt 融合。
- 候选池分层和编辑型结构之间没有增加中间层。
- 页面渲染虽然用了 Markdown，但阅读导向还不够强。

### 优化目标

- 让日报成为“编辑型长报”，而不是“候选池摘要拼接”。
- 建立 `editorialDigest` 中间层。
- 稳定产出：封面判断、雷达总览、模块日报、更多动态、深读、全池索引。

## 4.6 Sources 健康中心

### 当前作用

这里应该是“系统调试页”升级后的主治理面，而不是附属页面。

### 当前主要问题

1. **健康指标有了，但还不够面向决策**
   - 用户需要知道：这个源值不值得保留、补抓、降权或改配置。

2. **五段诊断还没有完全成为统一语言**
   - 抓取、正文、展示、AI、日报覆盖这五段逻辑是对的，但需要更稳定、更像产品。

3. **治理动作和诊断结果还不够闭环**
   - 看到了问题，不一定能直接触发正确修复动作。

### 根因

- 健康快照仍更多服务内部调试。
- 结果虽丰富，但推荐动作和影响等级还不够直接。

### 优化目标

- 把 Sources 变成“输入层总控台”。
- 让每个来源都有：状态、为什么、影响、下一步动作。

## 4.7 外部源与对照体系

### 当前作用

它承担两个任务：

- 扩宽输入面。
- 为现有抓取与阅读问题建立对照样本。

### 当前主要问题

1. **BestBlogs 仍处于“榜单可读，原文待补”阶段**
2. **邮箱入口有后端基础，但前端消费心智还弱**
3. **Dibao 已接进来，但还没有形成长期对照机制**

### 根因

- 当前重点仍在修主链路。
- 外部源接入已开始，但没有完全进入统一治理节奏。

### 优化目标

- 保留这些入口，但不要让它们打断主线。
- 用它们辅助判断：问题到底来自源、来自正文抽取，还是来自 UI 呈现。

## 4.8 运维与质量门禁

### 当前作用

这个模块决定项目能不能越改越稳，而不是越改越脆。

### 当前主要问题

1. **测试存在，但仍需进一步产品化**
   - 有 phase 测试、有黄金样本、有前端 E2E，但还没有完全成为迭代门槛。

2. **仓库当前改动面很大**
   - 大量未提交改动说明系统正在大收口阶段，风险和回归面都很大。

3. **“真实用户样本”与“技术测试样本”仍要继续绑定**
   - 目前黄金矩阵是很好的起点，但还需要扩展到日报和阅读器长期回归。

### 根因

- 当前阶段已经不是“缺测试”，而是“缺稳定的验收框架”。

### 优化目标

- 把黄金样本矩阵、日报验收、来源健康验收，变成每次迭代都刷新的固定对照面。

## 5. 优化优先级

## 5.1 P0：必须先做

这些不解决，其他优化都会继续漂。

### P0-1 内容可信合同

- 建立并统一 `contentReadiness / readabilityStatus / content kind`。
- 让“全文可读”和“只有摘要”不再混淆。
- 为高价值源做正文回填。

### P0-2 来源真相治理

- 把 `config_mismatch` 升级为强告警和来源降权规则。
- 给来源增加 `contentStrategy`。
- 让 `webpage` 快照退出普通文章阅读流。

### P0-3 Feed 阅读降噪

- 主标签只保留 `摘要 / 原文 / 翻译`。
- 扩展内容统一右侧抽屉化。
- 顶部信息块压缩成阅读器工具栏。

### P0-4 日报从“生成页”升级为“雷达页”

- 稳定目录、sticky 导航、结构化 Markdown 样式。
- 增加趋势总览和模块叙事中间层。
- 确保全池索引真的进入 payload。

## 5.2 P1：在 P0 稳定后推进

### P1-1 文章资产闭环

- 真实生成并保存 QA/Rewriting 资产。
- 让日报重点文章引用这些资产。

### P1-2 Sources 主治理面

- 五段诊断统一产品语言。
- 增加来源级修复动作和影响说明。

### P1-3 日报编辑型深写

- 重点文章深写。
- 更多动态用确定性模板补全。
- 深读来源单独出模块。

### P1-4 质量门禁产品化

- 黄金样本矩阵固定化。
- 日报和 Feed 的视觉/内容验收自动化。

## 5.3 P2：扩宽能力边界

### P2-1 外部源二阶段

- BestBlogs 原站全文补抓更稳。
- 邮箱前端导入和私密治理更成熟。

### P2-2 对照驱动迭代

- Dibao 长期作为阅读底座对照。
- 不迁移整套，只借鉴成功机制。

### P2-3 偏好与推荐解释

- 把用户反馈沉淀成长期排序信号。
- 让推荐/最新双队列更稳定。

## 6. 推荐执行顺序

不建议“全线同时动”。正确顺序是：

1. **来源真相 + 正文可信合同**
2. **Feed 阅读台降噪**
3. **日报结构重建**
4. **文章资产闭环**
5. **Sources 主治理面**
6. **外部源与长期对照**

原因很简单：

- 没有可信正文，Feed 再漂亮也是假阅读。
- Feed 不克制，日报做再长也会继续像后台页面。
- 日报结构不重建，AI 资产和来源治理都很难体现出价值。

## 7. 我建议你现在就锁定的执行原则

1. **不再继续加新页面作为第一优先级。**
2. **不再让技术诊断暴露在阅读主路径。**
3. **不再把任何字符串都叫“原文”。**
4. **不再把日报当成候选池展示页。**
5. **不直接整体迁移 Dibao/Folo/QMReader 代码，只迁移已验证有效的机制。**

## 8. 后续落地建议

如果按“投入产出比”排序，我建议后续实施分三轮：

### 第一轮：阅读底座修正

- 来源配置错配治理。
- 正文可信层回填。
- Feed 详情降噪。
- 一键翻译和补正文动作稳定化。

### 第二轮：日报产品化

- 编辑型结构。
- 模块化叙事。
- 趋势、更多动态、全池索引。
- sticky 目录和阅读导航。

### 第三轮：治理与复利

- 阅读资产。
- 来源健康中心。
- 对照体系。
- 推荐和偏好反馈。

## 9. 最终判断

信息中枢 V3 当前最大的风险，不是“技术做不到”，而是**系统已经做得很多，但没有强制把自己收敛成一个清晰产品**。

你现在最需要的不是更多点状修复，而是按模块重建优先级：

- 先让输入可信。
- 再让阅读克制。
- 再让日报成为真正输出。
- 最后才谈更复杂的偏好、Agent 和长期资产。

一句话概括：

**下一阶段的主题，不是继续扩功能，而是让信息中枢从“能力集合”变成“可信产品”。**

## 10. 模块与代码映射

为了避免后续优化继续停留在页面层，这里把重点模块直接映射到当前仓库里的主要责任文件。

| 模块 | 后端主文件 | 前端主文件 | 当前判断 |

## 11. 当前最值得优先清理的结构债

下面这些不是“体验小问题”，而是会持续放大系统不可信感的结构债。

### 11.1 一个 item 同时承担了太多语义

当前 `items` 同时可能承载：

- RSS 原始摘要
- 站点正文
- 榜单摘要
- 网页监控快照
- 目录索引项
- AI 生成结果的派生依据

这意味着如果不把 `content kind / basis / readiness` 彻底拆干净，前端永远会继续误把线索当正文。

### 11.2 阅读器和调试器混在一起

现在 Feed 和日报都存在同一个问题：

- 用户要读内容；
- 系统想解释自己为什么这样做；
- 工具和诊断就都挤在首屏。

这会让真正需要的正文、目录、重点文章反而退到次要位置。

### 11.3 来源治理还没有真正决定展示权重

现在 Sources 页已经能看出很多问题，但这些问题还没有稳定反映为：

- Feed 默认是否展示
- 默认走摘要还是走全文
- 是否允许进入日报主线
- 是否触发自动补抓、自动补摘要、自动复核

这会让“治理信息存在”和“产品行为改变”脱节。

### 11.4 日报缺少真正的中间编辑层

目前日报最大的问题不是模型不够强，而是链路没有真正分三层：

1. 候选整理层  
2. 编辑组织层  
3. 正式成文层

如果没有 `editorialDigest / moduleNarratives / moreDynamics / deepReads` 这类稳定中间层，final agent 就只能继续在候选池上临场拼装。

## 12. 三阶段优化计划

这里按“先救可信度，再救阅读，再救高质量输出”的顺序排。

### 阶段一：可信底座收口（P0，1-3 天集中收口）

目标：让系统不再把错内容当正文，不再把快照和索引项混入默认阅读主链路。

#### 核心动作

1. 来源治理
   - 清理官方名但 URL 错配的来源
   - 给主要来源补 `contentStrategy`
   - 给 `webpage` / `webpage_index` / `curated_index` 明确阅读资格

2. 正文层治理
   - 补齐 `readabilityContent` 的优先使用链路
   - 高价值源批量回填正文
   - 把 legacy snapshot 从默认 Feed 中降级隐藏

3. 翻译动作治理
   - 一键翻译必须变成明确可触发动作
   - `fetch_then_translate` 必须先补正文，再翻译
   - 缺翻译时必须告诉用户卡在哪一阶段

#### 验收标准

- 默认 Feed 不再被 `snapshot/index-only` 条目主导
- 任意一条高价值 RSS 长文能稳定落到结构化原文展示
- 翻译不可用时有清晰解释和明确动作，不再无反应

### 阶段二：阅读体验收口（P1，3-5 天）

目标：把 Feed 从后台面板收口为长期阅读工作台。

#### 核心动作

1. 阅读主路径极简化
   - 首屏只保留 `摘要 / 原文 / 翻译`
   - 扩展内容进入右侧抽屉或折叠菜单
   - 顶部统计和动作区进一步压缩

2. 正文排版强化
   - 统一正文容器宽度
   - 提升段落、列表、代码块、引用、图片的排版质量
   - 清掉技术状态文案对正文的打断

3. 文章资产层收敛
   - 区分摘要 vs 中文改写
   - 问文章、知识、转写只保留在扩展层
   - 资产状态对用户说人话，而不是说内部枚举

#### 验收标准

- 详情首屏正文占比明显高于当前版本
- 主路径只剩三大阅读标签
- 任意样本页不存在大面积诊断条遮挡正文

### 阶段三：日报雷达产品化（P1/P2，5-7 天）

目标：让日报从“系统生成页”变成“真的值得读的编辑型长报”。

#### 核心动作

1. 日报结构重建
   - 增加 `封面判断 / 雷达总览 / 模块日报 / 更多动态 / 深读 / 全池索引`
   - 固定右侧 sticky 导航
   - 目录不随正文滚丢

2. 中间编辑层
   - 引入 `editorialDigest`
   - 每个模块先分组再生成，而不是 final prompt 一次吞完
   - `moreDynamics` 用确定性模板补齐覆盖

3. 重点文章资产引用
   - 摘要、证据、行动建议优先引用已生成的文章资产
   - 让深读模块真正变成“为什么值得读”

#### 验收标准

- 日报正文不是候选摘要拼接
- 模块章节有自己的判断和证据
- 目录 sticky 可用，模块导航稳定
- 一份日报至少能覆盖 35+ 篇条目，且正文仍可读

## 13. 建议的项目管理方式

后面这个项目不适合再用“页面点状修修补补”的方式推进。建议直接按下面的管理视角推进：

### 13.1 任务看板按模块，不按页面

建议只保留这 5 条主线：

1. 来源治理  
2. 正文可信层  
3. Feed 阅读台  
4. 日报雷达  
5. 质量门禁

所有页面需求都必须挂靠到这 5 条主线上，避免“加一个按钮”“换一段文案”又把节奏带散。

### 13.2 每轮只接受两类验收

1. **真实样本验收**  
   例如：Anthropic、OpenAI News、TechCrunch AI、BestBlogs、John D. Cook、36kr。

2. **产品路径验收**  
   例如：默认 Feed 是否可读、翻译是否可触发、日报目录是否 sticky、重点文章是否可信。

没有通过这两类验收的改动，不算真正完成。

### 13.3 现在不建议优先做的事

以下内容不是不能做，而是不该排在当前前面：

- 继续扩大量新来源类型
- 继续增加新的日常页面
- 过早引入更复杂 embedding 推荐
- 继续堆更多可见按钮和诊断块
- 直接整仓迁移 Dibao/Folo 代码

这些事情在当前阶段都会放大系统复杂度，而不是优先提升可信度。

## 14. 最后的项目级判断

如果只看“有没有功能”，信息中枢 V3 已经很大了。  
如果只看“能不能作为我每天真的依赖的产品”，它现在最缺的是四个词：

- **真相**
- **克制**
- **分层**
- **收口**

所以后面的总原则应该非常简单：

> **先让内容是真的，再让阅读是顺的，最后让输出是有判断的。**
