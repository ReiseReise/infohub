# 信息中枢 V3 项目总控分析与优化计划

## 1. 总结判断

信息中枢 V3 当前不是“没做出来”，而是进入了更难的阶段：**系统能力已经铺开，但主链路还没有收敛成可信产品**。

运行态已经证明采集、AI、日报和前端都在工作：

- Docker 栈健康：`hub-engine / nginx / postgres / redis / rsshub / scrapling / changedetection / dibao-reader` 都在线。
- 数据池不小：当前来源 706 个，总条目 19,336，近 24 小时新增抓取 718 条。
- AI 链路活跃：近 24 小时 AI 调用 4,676 次，约 2,317,406 tokens。
- 页面与接口丰富：Feed、Sources、Daily、Reports、AI Usage、Reader Lab 等页面和接口都已铺开。

但用户感知仍然不可信，原因不是单点 UI，而是四个核心矛盾：

1. **抓到了，不等于可读**  
   `content_status=ready` 有 18,922 条，但 `readability_status=ready` 只有 1,523 条。大量内容在数据库里“有内容”，但不一定是适合阅读、翻译、日报引用的正文。

2. **AI 跑了，不等于结果可用**  
   近 24 小时 4,676 次 AI 调用中，`skipped` 有 2,527 次，远高于硬错误 18 次。很多任务不是模型崩了，而是在内容不足、状态误判、策略跳过中没有形成用户可见结果。

3. **日报生成了，不等于日报可读**  
   最新日报记录存在，但 2026-06-18 和 2026-06-17 的 `moduleSections / topItems / coverageItems` 都是 0，summary 只有约 630 字。系统确实写了日报记录，但没有稳定落成“信息雷达”。

4. **页面很多，不等于主体验清楚**  
   Feed、Sources、Daily 三个核心页面都超过 2,000 行；后端 `daily-report.ts` 超过 3,400 行。能力、诊断、修复、资产、阅读被揉在一起，导致用户看到的是系统流水线，而不是内容本身。

一句话概括当前状态：

> 信息中枢 V3 已经具备产品骨架，但还没有完成“内容可信层、阅读主路径、日报编辑层、来源治理反控”四条主链路的硬收口。

## 4. 模块级问题分析

### 4.1 来源与采集

当前系统已经支持 RSS、RSSHub、网页监控、网页索引、BestBlogs、邮箱、音频、Dibao 侧车等多入口。问题不是“源少”，而是“源进入同一个阅读流时语义不清”。

主要问题：

- `rss / webpage / webpage_index / curated_index / email` 在 Feed 中常被看成同一种文章。
- `webpage` 快照、新闻索引、榜单摘要会被用户误认为是单篇正文。
- Anthropic Newsroom、BestBlogs 这类索引源需要先拆条目，再补原站正文；当前补抓失败或未补抓时提示仍不够克制。
- 来源健康仍偏“抓取任务成功”，还不够“阅读质量成功”。

优化方向：

- 为每个来源固化 `sourceType / collectorType / itemKind / contentStrategy`。
- 将来源策略分成：`feed_only / smart / full / monitor_only / index_then_fetch`。
- Sources 健康中心输出五段漏斗：抓取、正文、展示、AI、日报。
- Reader Lab/Dibao 只作为质量对照，不直接替代信息中枢日报和资产链路。

### 4.2 正文可信层

这是当前全项目第一瓶颈。

主要问题：

- `content_status=ready` 高达 18,922，但 `readability_status=ready` 只有 1,523。
- `items.content` 仍承载多种形态：RSS HTML、RSS 摘要、网页快照、索引摘要、榜单摘要、纯文本。
- John D. Cook、Simon Willison、Anthropic、OpenAI、BestBlogs 等黄金样本暴露出格式、源码块、列表、链接、长文翻译等问题。
- 旧数据没有统一回填，导致新逻辑修好后，旧条目仍会污染 Feed 和日报。

优化方向：

- 固化内容合同：`全文可读 / RSS 摘要 / 索引摘要 / 榜单摘要 / 网页快照 / 片段 / 标题`。
- 拆分内容层：`content_html / content_text / readability_html / readability_text / extraction_status`。
- RSS 优先 feed 内正文，网页补抓只在必要时触发。
- 建立黄金样本矩阵，覆盖博客、技术长文、新闻短讯、中文资讯、网页索引、榜单源。

### 4.3 Feed 阅读台

三栏结构方向正确，但当前阅读页仍像系统诊断面板。

主要问题：

- 顶部全局标题、搜索、筛选、过期源提醒、状态条占用过多。
- 详情页中阅读提示、资产、工具、诊断、日报解释仍在主路径抢位置。
- 主标签应只有 `摘要 / 原文 / 翻译`，现在仍容易混入改写、问文章、知识、转写等低频能力。
- 翻译按钮或补抓按钮经常藏在诊断区，用户无法理解“为什么不能翻译”。

优化方向：

- Feed 顶部压缩：搜索和筛选一行，过期源提醒默认收窄。
- 详情首屏只保留标题、来源、时间、评分/等级、打开原文、三大标签。
- 工具入口 Folo 化：复制、收藏、已读、打开原文、补抓、翻译、重跑 AI 都进工具菜单。
- 右侧/折叠资产区承载：改写、问文章、知识、转写、日报引用、人类反馈。
- 正文容器居中，760-860px，17px 字号，1.8-1.9 行高，底部留安全区。

### 4.4 翻译、摘要与阅读资产

用户反复指出“翻译没反应”“中文改写和摘要像一回事”，这是产品语义问题，也是后端状态问题。

主要问题：

- 翻译覆盖只有 421 条，不能支撑跨语言阅读。
- 长文短译文容易显示成“已翻译”，缺少完整性检查。
- 没有全文时，翻译按钮应该变成“补抓原文并翻译”，而不是隐藏或静默。
- 摘要是判断要不要读，中文改写是把长文重写成中文文章，两者不能混。
- `item_reading_assets` 还没稳定进入用户主流程。

优化方向：

- 翻译接口返回阶段：`content / translation / model / skipped / done`。
- 翻译完整性字段：`sourceLength / translatedLength / chunkCount / complete / reason`。
- 主阅读只放摘要、原文、翻译；改写和问文章放资产抽屉。
- Article Agent 固定 5 问：总结要点、证据清单、前提拆解、行动建议、选题角度。
- 资产可被日报重点文章引用，但不默认把整段 QA 塞进日报。

### 4.5 日报雷达

日报当前是用户最关心的成品形态，但现在不够像“信息雷达”。

主要问题：

- 最近两天正式记录里 `moduleSections/topItems/coverageItems` 为 0。
- 有时日报像调试快照，有时像长文，有时像候选池拼接。
- 模块叙事不够厚，观点容易单薄。
- 标题、目录、Markdown 层级、右侧导航都不够像正式阅读产品。
- 候选池与正式日报之间缺少稳定的编辑中间层。

优化方向：

- 日报结构固定为：
  1. 今日封面判断
  2. 目录
  3. 信息雷达总览
  4. 今日精选
  5. 模块日报
  6. 更多动态
  7. 重点研究/深读
  8. 阅读顺序
  9. 下一步行动
  10. 附录：全池摘要索引
- 新增或强化 `editorialDigest`：先把候选池分成精选展开、模块引用、更多动态、深读、附录索引。
- 目标覆盖：精选深写 8-12 篇，模块引用 20-35 篇，更多动态覆盖 10-20 篇。
- 正文目标：日更高质量版 6,000-9,000 中文字；候选不足时明确展示素材缺口，不硬凑。
- 页面目录 sticky，正文 Markdown 有明确视觉层级，链接可读，不显示裸 URL。

### 4.6 Sources 健康中心

Sources 应该是治理中心，而不是统计页。

主要问题：

- 当前健康判断容易过于乐观：RSS 抓取成功不代表正文可读。
- 诊断项和修复动作已经存在，但还没有完全反控 Feed 推荐和日报入选。
- 用户需要知道：这个源值得保留吗？应该补抓吗？应该降权吗？是不是噪声源？

优化方向：

- 每个源展示五段状态：抓取、正文、展示、AI、日报覆盖。
- 给出明确动作：保留、观察、补正文、重跑 AI、降权、停用建议。
- 引入源级阅读质量：全文率、摘要率、翻译率、日报引用率、噪声率。
- 来源策略变更必须人工确认，自动修复只做补抓和补 AI。

### 4.7 Reader Lab 与 Dibao 对照

Dibao 的优势已被截图和对照证据证明：阅读更克制，RSS feed-first 更稳定，内容分层更清楚。

但不建议直接“把 Dibao 当主系统替换”：

- Dibao 主要解决 RSS 阅读，不负责日报、Article Agent、来源健康、邮箱、BestBlogs、AI 用量。
- 信息中枢的问题有相当一部分是内容合同和产品分层问题，套壳不能自动修日报。

正确用法：

- 保留 Dibao 侧车作为同源质量基准。
- 迁移思想，不搬运业务边界：feed-first、content_html/content_text、reader layout、推荐/最新双队列。
- 每轮修复用同一批黄金样本对照 Dibao，判断是源问题还是信息中枢问题。

## 5. 优化计划

### Phase 0：变更收口与验收底座

目标：先让当前大 diff 可控。

任务：

1. 冻结新功能扩张，停止继续加新页面。
2. 将当前 91 个已跟踪变更按模块分组：内容可信、Feed、日报、Sources、外部源、测试。
3. 为每组确认状态：保留、待验、暂缓、撤出本轮。
4. 建立黄金样本矩阵：
   - John D. Cook 技术长文
   - Simon Willison 长文
   - Anthropic Newsroom 索引源
   - OpenAI News
   - BestBlogs 榜单
   - 36kr 中文短讯
   - 邮箱 newsletter
5. 每个黄金样本固定检查：原文、摘要、翻译、正文状态、日报引用、页面遮挡。

验收：

- `services/hub-engine npm run build`
- `apps/web npm run build`
- 关键单测：content、reading-context、rss、daily-report-workflow、feed-layout
- Playwright 抽测 Feed 与日报核心页面

### Phase 1：内容可信层 P0

目标：让系统先知道“这到底是什么内容”。

任务：

1. 固化 `ContentReadiness` 合同，并让前端只显示用户语言。
2. RSS collector 优先读取 feed 内高质量正文，补齐 Atom `summary`、RSS `description`、`content:encoded` 的质量选择。
3. 对 `webpage_index/curated_index` 强制区分索引摘要和原站正文。
4. 原文渲染基于可读 HTML/Markdown，不再把技术长文压成难读纯文本。
5. 对高价值历史条目跑正文回填。

验收：

- 7 类黄金样本中，内容状态必须和实际阅读层一致。
- “索引摘要”不能再被标为“全文可读”。
- 技术长文代码块、列表、链接可读。

### Phase 2：Feed 阅读台 P0/P1

目标：让 Feed 变成真正的阅读工作台。

任务：

1. 主标签固定为：摘要、原文、翻译。
2. 改写、问文章、知识、转写、日报引用、反馈、诊断全部进入右侧资产/工具抽屉。
3. 顶部提醒和全局工具条压缩，避免红框区域长期占据阅读空间。
4. 翻译页签必须永远给明确动作：
   - 一键翻译全文
   - 补抓原文并翻译
   - 打开原文
   - 显示失败原因
5. 正文视觉参考 Dibao/Folo：克制、留白、正文优先。

验收：

- 10 条真实 Feed 抽测，默认首屏不再被诊断淹没。
- 翻译按钮点击后有 loading、成功或明确失败阶段。
- 页面无横向溢出、右下角不遮挡正文按钮和标签。

### Phase 3：日报雷达 P0/P1

目标：日报从“生成结果”变成“高质量日更信息雷达”。

任务：

1. 修复空壳日报：`moduleSections/topItems/coverageItems` 不得在有候选时为 0。
2. 引入 `editorialDigest`，先确定哪些文章深写、哪些模块引用、哪些进入更多动态。
3. 模块日报分开生成，最后统一编辑融合。
4. 更多动态用确定性模板生成，保证大池覆盖，不让模型漏掉。
5. 阅读页重排：
   - 左侧正文主栏
   - 右侧 sticky 目录
   - 模块折叠/展开
   - 日期快速切换
   - 运行分析默认折叠

验收：

- 单日报覆盖 35+ 篇文章。
- `今日精选` 8-12 篇，模块引用 20+ 篇，更多动态 10+ 条。
- 正文 6,000-9,000 中文字，Markdown 结构清晰。
- 用户能回答：今天发生了什么、为什么重要、先读什么、怎么行动。

### Phase 4：Sources 治理反控 P1

目标：让 Sources 成为输入质量控制中心。

任务：

1. 来源健康五段漏斗常态化。
2. 源级内容策略可编辑。
3. 健康状态影响 Feed 推荐与日报候选：
   - 全文率低：降低深读权重
   - AI 卡住：进入处理债
   - 噪声高：进入观察或降权
   - 日报未覆盖：显示原因

验收：

- Anthropic、BestBlogs、TechCrunch、36kr、邮箱、低质源各能给不同健康结论。

## 7. 暂不优先做的事

1. 不继续盲目扩新来源。当前 706 个源已经够多。
2. 不把 Dibao 直接硬并入主系统。先学内容模型和阅读体验。
3. 不先做复杂 embedding 推荐。当前瓶颈是正文可信和日报编辑，不是推荐算法花哨。
4. 不继续堆诊断卡片。诊断要进入 Sources、工具抽屉、运行分析，不在阅读首屏抢位置。
5. 不把所有 AI 任务都自动重跑。先按高价值源、热点关键词、日报候选做有限追赶。

## 8. 完成标准

信息中枢 V3 到“日常可信可用”的标准不是页面能打开，而是：

- **内容可信**：每条内容能说清是全文、摘要、索引、榜单还是快照。
- **阅读顺畅**：默认阅读不被诊断、按钮、状态淹没。
- **翻译可控**：知道为什么没翻译，点击后有结果或明确错误。
- **日报有厚度**：像日更信息雷达，不像调试快照。
- **来源能治理**：知道哪些源值得保留、补抓、降权或观察。
- **验证可复现**：每次修复都能在黄金样本和 Docker 运行态验证。

最终路线：

> 先让内容真，再让阅读顺，再让日报深，最后再做个性化推荐和外部源扩展。

### 10.1 第一优先级：先修“内容是真是假”

如果只修 UI，用户仍会看到错误正文；如果只修日报 Prompt，日报仍会引用错误素材。因此第一优先级不是继续堆页面，而是把内容状态变成硬合同。

最小闭环：

1. `ContentReadiness` 不再只是标签，而是后端和前端共同遵守的合同。
2. 每条内容必须能落到一种状态：全文、RSS 摘要、索引摘要、榜单摘要、网页快照、片段、标题。
3. 翻译、摘要、日报候选必须声明依据的是哪一层内容。
4. 黄金样本必须覆盖：John D. Cook 技术长文、Anthropic Newsroom、OpenAI News、BestBlogs、36kr、邮箱 newsletter、低质普通源。

成功标准：

- 用户打开任一条 Feed，能在一行内看懂“我现在读到的是什么”。
- 任何索引页、榜单页、网页快照都不能再伪装成全文。
- 翻译和日报不再基于错误内容静默生成。

### 10.2 第二优先级：再修“阅读是否顺”

Feed 的三栏方向已经成立，问题是视觉和交互还没有收敛。后续不再把每个诊断都展示给用户，而是以阅读为中心。

最小闭环：

1. 页面顶部压缩，只保留搜索、主要筛选和低干扰状态提示。
2. 详情首屏只保留标题、来源、时间、内容状态、打开原文。
3. 主标签固定为：`摘要 / 原文 / 翻译`。
4. `中文改写 / 问文章 / 转写 / 知识 / 日报引用 / 反馈 / 评分拆解 / 阶段修复` 全部进入“资产与工具”抽屉。
5. 翻译页签始终有主动作：一键翻译、补抓并翻译、打开原文、查看失败原因。

成功标准：

- 首屏正文占比明显提升，用户不是先看到系统诊断。
- 真实抽测 10 条 Feed，没有 raw enum、长条诊断、无效按钮打断阅读。
- Folo/Dibao 作为对照：阅读主区域应接近它们的克制程度，而不是继续像运维面板。

### 10.3 第三优先级：把日报升级成“信息雷达”

日报现在最大问题不是字数，而是编辑结构。它需要先把材料分层，再写成报告，而不是把候选池交给 final prompt 一次性吞掉。

最小闭环：

1. 候选池先生成 `editorialDigest`：精选展开、模块引用、更多动态、深读研究、附录索引。
2. 模块独立生成，每个模块都有：发生了什么、为什么重要、相关链接、判断与建议。
3. 更多动态使用确定性模板，确保大量短讯不被模型漏掉。
4. 正式日报页面保留 sticky 目录、日期切换、Markdown 层级、模块展开/折叠。
5. 工作台显示生成进度和阶段错误，不再只让按钮转圈。

成功标准：

- 每份高质量日报至少覆盖 35 篇文章。
- 正文有目录、模块、重点文章、更多动态、深读和下一步行动。
- 如果素材不足，页面明确显示缺口；如果生成失败，显示失败阶段。

### 10.4 第四优先级：让 Sources 反控系统

来源健康不是一个报表，而是输入治理的控制台。后续 Feed 推荐、日报候选和自动修复都要被来源质量影响。

最小闭环：

1. 每个源给出五段状态：抓取、正文、展示、AI、日报覆盖。
2. 每段都有用户语言解释和建议动作。
3. 源级策略可人工设置：仅 RSS、智能补抓、强制全文、仅监控、停用观察。
4. 系统可自动排队补抓/补 AI，但不能自动停用或擅自改配置。

成功标准：

- 用户能判断一个来源应该保留、降权、补抓还是观察。
- 来源健康会影响 Feed 排序和日报候选，而不是只在 Sources 页面展示。

## 11. 下一轮建议执行顺序

建议下一轮不要再扩大功能面，而是按下面顺序做硬收口：

1. **黄金样本验收矩阵**：先把 7 类样本固定下来，作为所有修复的判定尺。
2. **正文可信层**：修 RSS/网页/索引/榜单/快照的内容合同和展示口径。
3. **Feed 阅读降噪**：主标签收敛，工具抽屉，翻译按钮阶段化。
4. **日报编辑层**：`editorialDigest + moduleNarratives + moreDynamics`。
5. **Sources 反控**：来源健康影响 Feed 和日报，不再只做观察面板。
6. **Reader Lab 对照复盘**：同源对比 Dibao，保留可迁移的内容模型和阅读体验。

停止线：

- 在 Feed 和日报主链路验收通过前，不继续新增大入口。
- 在 `ContentReadiness` 没有稳定前，不继续扩大自动翻译和日报深写范围。
- 在黄金样本没有自动/半自动验收前，不把“看起来正常”当作完成。
