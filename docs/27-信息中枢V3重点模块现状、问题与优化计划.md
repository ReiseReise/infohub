# 信息中枢 V3 重点模块现状、问题与优化计划

## 1. 结论先行

信息中枢 V3 当前不是“功能不够”，而是“主链路不够可信、不够收敛”。

从仓库现状看，系统已经具备完整骨架：

- 后端有独立采集、处理中间层、Sources 治理、日报工作流、AI 用量、外部集成。
- 前端有 Feed、日报、Sources、Settings、AI 用量、Reader Lab、Monitor、Audio 等完整页面。
- QA 和 Docker 基线已经具备，不是原型状态。

但真正影响日常可用性的主问题仍集中在四条主链：

1. **内容可信层不够统一**：同一条内容到底是全文、索引摘要、榜单摘要还是网页快照，还没有彻底成为全链路公共合同。
2. **Feed 阅读层不够收敛**：三栏结构成立，但阅读器气质还不够强，诊断、资产、工具仍侵入主路径。
3. **日报层不够深**：能生成，但离“每日信息雷达 + 编辑型长报”还有明显差距。
4. **Sources 治理层还没完全反控产品行为**：知道哪些源差、哪些内容不完整，但这些诊断还没有完全决定 Feed 推荐和日报覆盖。

后续路线不应该继续扩页面，而应该按这个顺序推进：

**先做真 → 再做顺 → 再做深 → 最后再做个性化与扩展源。**

## 3. 各重点模块的真实判断

### 3.1 采集与信源输入

**现状**

- 系统已经覆盖 RSS、网页监控、网页索引、榜单源、邮箱、Dibao 对照。
- `source_role`、`collectorType`、`sourceType`、`processingProfile` 已经开始承担更细的语义。
- `webpage_index`、`curated_index`、`monitor` 这些更细的来源角色已经进入系统。

**问题**

1. 来源类型和条目类型仍会混用。
2. 同样是“网页源”，有的是单篇文章，有的是索引页，有的是监控快照，产品层没有完全区分。
3. 高价值来源抓到了，但进入正文/评分/日报的推进链不稳定。

**判断**

这层不是“采不到”，而是“采进来后语义合同不够硬”。

---

### 3.2 正文可信与富化

**现状**

- 仓库里已经有 `content-extractor`、`content-status`、`content-upgrade-policy`、`reading-context`、`item-enrichment`。
- `source-content-strategy`、`contentReadiness`、`readabilityContent` 方向已经开始成形。
- 已经开始区分：全文可读、摘要可读、榜单摘要、索引摘要、网页快照。

**问题**

1. `items.content` 仍承担了过多混合语义。
2. 摘要、翻译、日报引用不一定都基于同一内容层。
3. 对于 `webpage_index / curated_index`，即使只有摘要，也容易被误认为“全文可读”。
4. 翻译动作与正文补抓没有完全合并成统一用户动作。

**判断**

这是整个项目的 P0 底座。这里不统一，Feed、日报、Sources 都会出现“表面正确，实际不可信”。

---

### 3.3 Feed 阅读台

**现状**

- 三栏布局已经成立：来源栏 / 文章列表 / 阅读详情。
- 已有推荐流、来源聚焦、内容 tabs、更多诊断与资产层。
- 已经开始向 Dibao / QMReader / Folo 的阅读器方向靠近。

**问题**

1. 详情页仍残留太多系统提示、状态条、工具入口、资产入口。
2. 主阅读标签还没有收敛成真正的三件事：摘要、原文、翻译。
3. 资产、问文章、知识、重写、诊断等还在主视觉层抢位置。
4. 正文容器的视觉优先级还不够极致，像控制台多过像阅读器。

**判断**

Feed 的根问题已经不是布局结构，而是**信息密度的层级治理**。

---

### 3.4 阅读资产与 Article Agent

**现状**

- `article-assets.ts`、`reading-assets.ts`、`reading-context.ts` 已经在把摘要、翻译、日报引用、反馈、问文章资产聚合起来。
- 方向上已经从“一次性摘要”走向“文章级资产”。

**问题**

1. 摘要、中文改写、翻译三者的边界不够清楚。
2. 用户会自然问：“中文改写是不是就是摘要？”
3. 资产虽然存在，但还没有真正反哺日报重点文章和后续阅读判断。

**判断**

这层很重要，但应放在 P1。前提是正文可信层先稳定，否则资产只是在加工脏输入。

---

### 3.5 日报工作台与正式日报

**现状**

- 已有日报工作台、候选池、生成进度、正式日报页、日期切换、模块稿件、全池索引。
- 路由、AI 场景、模板、候选准备和 final 生成链路都已经存在。

**问题**

1. 正式日报仍偏像“系统输出结果页”，不是“编辑型成稿”。
2. 观点密度、信息量、模块叙事厚度仍偏薄。
3. 重点文章覆盖不够，很多候选只存在于索引，不进入正文层。
4. 目录、右侧阅读导航、模块结构、Markdown 排版还有明显产品化缺口。

**判断**

日报已经从 0 到 1 了，但离你要的“高质量信息雷达”至少还差一个中间编辑层：`editorialDigest`。

---

### 3.6 Sources 治理中心

**现状**

- `source-health.ts`、`sources.ts`、Sources 页面已经开始做抓取、正文、AI、日报覆盖的五段诊断。
- 正文策略、来源健康、推荐动作已经在后端和前端出现雏形。

**问题**

1. 诊断有了，但它还没完全变成产品约束。
2. 一个来源如果是“索引摘要为主”或“正文经常缺失”，Feed 和日报还不一定足够降权。
3. 来源质量策略还没真正成为全局行为控制器。

**判断**

这层要从“后台诊断”升级为“上游闸门”。

---

### 3.7 模型治理与 AI 用量

**现状**

- 路由、前端页、场景配置、prompt 模板、usage summary 已经形成体系。
- 这是系统管理层，不再是空白。

**问题**

1. 运行监控、系统用量、日报用量的口径仍要更彻底分开。
2. 有些诊断信息还会误入阅读主链路。

**判断**

这层不用重做。重点是把它守在诊断与治理层，不再污染阅读体验。

---

### 3.8 外部源接入与 Reader Lab

**现状**

- BestBlogs、邮箱、Dibao 对照、OPML 桥接已经进仓库。
- 说明项目已经不只是 RSS 阅读器，而是真想做输入面扩展。

**问题**

1. 外部源质量依赖不同，语义层还不够统一。
2. Reader Lab 的价值现在主要是对照，不是主产品。
3. 邮箱、榜单、网页索引类内容，需要更强的 provenance 展示。

**判断**

这层现在不应继续扩很多新源，而应先把现有源的可信语义做扎实。

---

## 4. 当前最核心的问题清单

### P0 问题

1. **内容层不够真**
   - 全文 / 摘要 / 索引 / 快照 / 榜单没有彻底统一成全链路合同。
2. **Feed 主阅读链路仍太吵**
   - 诊断、工具、资产暴露过多，正文不够绝对主角。
3. **日报仍偏浅**
   - 有流程，没有足够强的编辑判断和模块叙事。
4. **翻译与补抓动作不够闭环**
   - 用户点击翻译时，不应该自己猜是“没原文”“无需翻译”还是“模型失败”。

### P1 问题

5. **阅读资产层边界不清**
   - 摘要 / 改写 / 问文章 / 日报引用 之间重复感强。
6. **Sources 诊断还未完全反控 Feed / 日报**
   - 来源质量低时，系统应该更明确地改变行为。
7. **日报缺少稳定的中间编辑层**
   - 还没有把候选系统化地整理成精选、模块、更多动态、附录。

### P2 问题

8. **外部源接入还停在桥接阶段**
   - 可导入，但未完全形成标准化生产路径。
9. **个性化排序与长期偏好还不够强**
   - 反馈已有基础，但尚未成为真正可解释的推荐系统。

## 5. 优化计划

## 5.1 第一阶段：P0 收口，先把主链路做真

### 目标

让用户先重新信任内容本身。

### 要做的事

1. **统一内容可信合同**
   - 强化 `contentReadiness`、`readabilityStatus`、`originalTextStatus`
   - 让摘要、翻译、日报明确标注“基于哪一层内容”
   - `webpage_index / curated_index / monitor` 全部做清晰区分

2. **统一翻译与补抓动作**
   - 有全文：直接一键翻译全文
   - 只有摘要但有原站：补抓原文并翻译
   - 没原站或补抓失败：明确给出失败原因和打开原文

3. **Feed 首屏降噪**
   - 主阅读只保留：摘要 / 原文 / 翻译
   - 改写 / 问文章 / 转写 / 知识 / 诊断进侧抽屉或折叠层
   - 正文容器做成真正长文阅读器

4. **日报页先做结构和排版收口**
   - 先把目录、右侧导航、章节粘性、Markdown 结构、模块可读性做对
   - 不要先追求更多 fancy 功能

### 完成标准

- 用户能分清当前看到的是全文、摘要、索引还是快照
- Feed 主路径只围绕阅读，不像控制台
- 翻译按钮不再静默失效
- 日报阅读页具备基本成稿气质

---

## 5.2 第二阶段：P1 产品化，把阅读结果变成资产，把日报变成雷达

### 目标

从“能读”升级到“能复用、能判断、能沉淀”。

### 要做的事

1. **阅读资产层收口**
   - 明确：
     - 摘要 = 快速理解
     - 中文改写 = 更适合连续阅读的重写版
     - 翻译 = 尽量忠实的中文全文/节译
     - 问文章 = 固定问题资产
   - 让日报重点文章优先引用这些资产，而不是重复生写

2. **Article Agent 真正落地**
   - 总结要点、证据清单、前提拆解、行动建议、选题角度保存为持久资产
   - 允许被日报、专题、后续阅读引用

3. **Sources 治理中心升格**
   - 来源健康不仅展示，还要真正影响：
     - Feed 推荐
     - 日报候选
     - 默认正文策略

4. **日报增加中间编辑层**
   - 建立 `editorialDigest`
   - 先把候选整理为：
     - 精选展开
     - 模块引用
     - 更多动态
     - 附录索引
   - 再做最终成稿融合

### 完成标准

- 摘要、改写、翻译、问文章的角色清楚
- 日报正文引用数和证据密度明显提升
- 来源治理真正改变用户看到的内容排序和深度

---

## 5.3 第三阶段：P2 扩展推荐与外部源闭环

### 目标

让系统从稳定工作台继续长成“有长期偏好和多源输入能力的信息引擎”。

### 要做的事

1. **外部源标准化**
   - 邮箱、BestBlogs、Reader Lab、OPML 导入形成稳定桥接与 provenance 展示

2. **偏好与推荐解释**
   - 短期反馈、长期主题偏好、长期来源偏好分层
   - 推荐解释只说人话，不再暴露机器话术

3. **Reader Lab 对照体系**
   - 持续对比当前正文抽取质量与 Dibao / Folo 路径
   - 明确哪些问题来自信号源，哪些来自抓取策略，哪些来自展示层

### 完成标准

- 外部源不再是“补丁接入”
- 推荐解释真正可读
- 系统能持续通过对照提升抓取和阅读质量

---

## 6. 推荐的执行顺序

### Sprint 1

- 内容可信合同
- 翻译/补抓动作统一
- Feed 首屏降噪

### Sprint 2

- 日报页阅读结构收口
- `editorialDigest` 中间层
- 模块叙事增强

### Sprint 3

- 阅读资产边界收口
- Article Agent 资产持久化
- 日报重点文章资产引用

### Sprint 4

- Sources 治理真正反控 Feed / 日报
- 外部源 provenance 与对照面板深化

---

## 7. 最后判断

信息中枢 V3 现在最需要的不是“大重构”，而是**围绕主链路做收口式工程**。

真正要稳住的只有三件事：

1. **我现在看到的内容到底是不是真的正文**
2. **我阅读时会不会被系统噪音打断**
3. **日报能不能真正代替我完成当天的信息雷达工作**

只要这三件事收口，剩下的 Sources 健康、Article Agent、外部源、推荐系统都会顺势变成增量，而不是继续堆复杂度。
