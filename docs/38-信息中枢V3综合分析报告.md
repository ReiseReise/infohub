# 信息中枢 V3 综合分析报告

> 本报告只做判断与归因，不承担执行跟踪。可执行条目见 `39-信息中枢V3优化设计与执行方案.md`；当前执行真源仍是 `36-信息中枢V3可信可用收口任务跟踪.md`。

## 0. 摘要

**一句话定位判断**：信息中枢 V3 是一个工程完成度真实很高、产品判断力也在线的系统，它当前的主要风险不在功能缺失，而在三处结构性错配——安全边界按"个人本机玩具"设计却按"局域网常驻服务"运行、质量保证机制的成本已超过被保证的对象、以及项目对外的完成度门面（97%）与它自己已如实记录的运行健康度（近 24h 65 成功/240 失败）之间存在层级倒置：前者被当作"总体进度"，后者被归入"风险备注"。**`36` 号的披露是诚实且完整的，问题出在两个数字的排序，不在隐瞒。**

**三个必须先看的结论**：

1. **安全暴露面与部署现实不匹配（P0）**。9 个服务端口全部绑定 `0.0.0.0` 而非 `127.0.0.1`，实测全部可达。其中 `scrapling-service:8010` 是一个无鉴权、无内网地址过滤、且回显目标响应正文的 SSRF 代理；`redis:6379` 无 `requirepass`。这不是"代码里有个漏洞"，而是整台机器所在局域网内任何设备都能直接触达系统内脏。

2. **"只清存量、不改生成端"这个模式，在文档和账号两条线上各复发了一次（P0/P1）**。
   - **账号线**：`auth.users` 全表 77 行，真人只有 3 个，72 个是 QA 夹具账号——而它们**全部创建于 2026-07-20～07-24，即 07-13 那次"清理 497 个僵尸账号"之后重新长出来的**。生成端没动，清理就白做。
   - **文档线**：`docs/` 根 44 份活跃 md，其中 11 份标题高度同质的"审计与优化计划"（287 KB）集中产生于 06-17～06-20 四天内，现被 `00-文档总导航.md` 统一降级为"背景材料"却不删除。`memory.md` 早在 2026-03-10 就三次反思文档膨胀，三个月后爆发了更大一轮。
   - **本报告有义务不成为第 12 份**——它的处理方式写在 `39` 号第 0 章。

3. **诊断中心向管理员展示虚构的业务实体（P1）**。管理后台 4 张图表全部渲染假数据："信源新鲜度"列出的 Hacker News / RSS Feed A / Twitter List / Reddit 等六个信源，**在真实系统的 21 个信源里一个都不存在**；"AI 模型用量"列出的 GPT-4o / Claude 3.5 / Deepseek，与实际使用的 qwen / 豆包完全无关。它们与同屏真实 KPI 卡混排，标注只有一行 10px 灰字。
   （定为 P1 而非 P0 的理由见 §4.1——曝光面仅限 admin，而唯一真人账号是 role=user。但**最小修复只需十分钟**：把九个虚构专名换成无歧义占位。）

**同样重要的结论：这个系统的产品判断力被低估了。** 日报在 0 素材时明确拒绝发布并说明"只有 0 篇可核验证据，至少需要 5 篇"、"事实草稿已保留，但不会冒充正式日报"；信源页把链路健康、正文率、AI 完成率、噪声率、入报率逐列摊开并给出"修复"入口；`memory.md` 记录的"AI 只做判断、代码做决策"和"不做假策略"是真正的好原则。**问题几乎全部出在这些原则没有被一致地执行到每个角落，而不是原则本身有误。**

## 1. 分析方法与证据规范

本报告由四路独立调查合并而成：

| 路径 | 方法 | 覆盖 |
|---|---|---|
| 理念与产品 | 静态阅读 `docs/01/02/03/36`、`memory.md`、`qa/reports/` | 设计原则、进度真实性、文档治理 |

**证据规范**：代码引用一律 `文件路径:行号`；运行态结论附命令与输出；界面结论附截图编号（存 `qa/reports/20260726-ui-walkthrough/`）。

**关于本报告的自我纠错**：静态分析先行提出的若干论断在实测与交叉核验中被推翻或需要降级，这些**全部保留在报告中并标注修正**（见 §5.5）。原因很简单——一份把误判悄悄删掉的分析报告，读者无法判断其余结论的可信度。

本报告完稿后又经过一轮独立对抗性复核，**其中查出了一条本报告自己犯的、且是最高证据等级的错误**：初稿称"数据库实测 `auth.users` 仅存 2 个用户"，实际全表 77 行——执行的查询带了 `where email like` 过滤条件，却把过滤结果当作全表事实陈述。该错误连带影响 §2.4 与根因 B，已全部重写（正确数据见 §2.4）。

由此立下一条自律，也建议项目采纳：**凡在文档中写"数据库实测"，必须附上原始 SQL**。`select count(*)` 与 `select ... where` 之间的差别，就是这次 2 与 77 的差别。

**只读边界**：走查全程未点击任何删除/生成/发布按钮，未触发付费 AI 调用；安全验证仅做端口连通性与 `GET /health`，**未发送任何 SSRF 测试请求、Redis 命令或写 SQL**。

## 2. 理念与产品层

### 2.1 定位是清晰的，断裂发生在"沉淀"这一段

`docs/01-顶层架构设计.md` 的定位表述相当准确：

> 本质不是阅读器，也不是问答系统，而是一个全渠道采集 → 处理 → 存储 → 输出的上游数据引擎。

四条架构原则（本地优先 / 管道分层 / Web-first / 输出不止给人看）互相自洽，也确实指导了实现。问题在于三段闭环的完成度严重不均：

- **采集**：最成熟，也最分散（RSS/RSSHub/YouTube/网页监控/Scrapling 兜底/OPML/Capture Inbox）。
- **阅读**：较成熟，`POST /api/items/:id/enrich` 的富化状态机是真正的设计亮点。
- **沉淀**：**闭环在此断裂**。日报是当前唯一的沉淀形态，但它是流式产出而非资产累积——`docs/03` 自己的话是"系统开始拥有'累积理解'，而不是每天重新写一遍"，说明现在就是每天重新写一遍。而这唯一的沉淀出口，恰好是当前故障率最高的模块。

三份主文档（`01` §5、`02` §1、`03` §3）对差距的表述完全一致：输入面不够宽、输出面不够结构化、专题面不够深。`02` 的"顶级设想对照总表"直接把"可被系统消费的结构化输出"标为**偏弱**。也就是说，**立项时的核心理念，在项目自己的状态文档里被判定为未达成**。这是一个诚实的自我认知，但它已经维持了很久没有被转化为行动。

### 2.2 进度悖论：97% 与 65 成功/240 失败并存

`docs/36` 状态胶囊（updated 2026-07-26）显示总体进度 **111/115（97%）**。同一份文件的阻塞记录写着：

- 近 24 小时抓取 **65 成功 / 240 失败**，主因广泛 TLS 中断 + `pluralistic.net` DNS 失败，且明确判定"不是 QA 污染，是真实运行故障"
- 07-25 主日报 `degraded`、07-26 `degraded + draft` 且 0 条素材，最新可发布日报停在 07-24
- 5 个候选源仍全部为 shadow，**正式启用 0**

对照 `qa/reports/runtime-observation-20260715.md` 的首尾快照，劣化轨迹很清楚：活跃来源 21→40、抓取 333成功/5失败 → 72/398、健康异常 0→14、处理债务 15→56。**来源数翻倍后运行质量断崖式下滑**——这恰恰是"输入面还不够宽"这条理念在实践中撞墙的直接证据：宽度增加了，但没有配套的质量吸收能力。

剩余 4 项未完成任务中，`EXT-021`/`EXT-022`/`ENG-009` 是时间不可压缩的观察类任务（其中两项自 2026-07-15 起已跨越 11 天未闭合）；`ENG-010`（`docs/36:380` 完成交付审计）**不是**观察类，它随时可做，卡住的真实原因是 §5.5 提到的 369 个未提交变更。

**必须先把话说公道**：`docs/36` 的状态胶囊主动、完整、无保留地披露了全部阻塞——65 成功/240 失败、TLS 中断、DNS 失败、日报连续 degraded、正式启用 0 全在"阻塞与风险"栏里，并且自行判定"这是需要修复的真实运行故障，不是单纯 QA 污染"。"总体进度"栏本身也列出了还差哪四项。**本报告上面那三条运行故障证据，全部抄自 `36` 号自己。** 这份自我披露的质量应当计入项目优点。

**归因**：所以问题不是"健康度没有指标"，也不是隐瞒，而是**指标的层级排序**——111/115（97%）被放在"总体进度"的位置，运行故障被放在"风险备注"的位置。两者并列时，读者的注意力被百分比锚定。而由于剩余任务多为观察类，这个百分比还会长期冻结在 97% 附近，进一步强化"即将完成"的印象。这不是造假，是**指标选错了位置**。

### 2.3 治理机制的精细度远超实际吞吐

三个例子指向同一个模式：

| 机制 | 精细度 | 实际吞吐 |
|---|---|---|
| 外部源准入 | 254 条候选档案、shadow/active/paused/removed 四态生命周期、5 active 上限 + 26 总上限、人工选择与正式采纳双账本 | 正式采纳 **0** |
| AI 治理 | 一个设置页下的四个 tab（`AiCenterTab.tsx` 内 `scenes`/`models`/`skills`/`logs` 四个条件分支，由 `:37` 单个 state 切换） | 服务 **1** 个真实用户 |
| 质量证据 | 115 项任务、每项需记录日期+命令+数据+截图 | 产生 749 行跟踪文档 + `qa/reports/` **224 个文件**（178 个 `.log` / 23 个 `.md` / 20 个 `.png` / 3 个 `.json`；`index.md` 实际只引用 17 个文件名，且 178 个 `.log` 中有 62 个（约三分之一）是 126–212 字节的近空文件，中位数 976 字节） |

**一条必要的判据**：上表三行中，"外部源准入"与"质量证据"两行是**成本已经发生**的存量投入（254 条候选已录入、四态生命周期已实现、224 个证据文件已产生），判其 ROI 为负是公允的。而 AI 管理中心那一行需要打折看待——把配置从代码挪到页面本身是**降低**而非提高治理成本，`docs/03:32` 原文写的目的正是"减少误判和隐藏成本"。它列在此处只是提示"服务对象规模与界面投入不匹配"，不构成过度设计的指控。

区分这两类很重要，否则 §8.2 的"该砍"清单会误伤那些**留着不花钱的可选性**（如 `quota.plans` 这类几行配置表）。判据是：**这项复杂度的成本是已经发生，还是仅仅预留？** 已发生的才值得砍。

### 2.4 单用户系统承担着多租户复杂度

这是全项目最明显的架构-场景错配，而且它**不是一笔已付清的历史代价，是一个仍在增长的存量**。

`auth.users` 全表实测 **77 行**（`select count(*) from auth.users`）：

| 类别 | role | 数量 |
|---|---|---:|
| `qa_*@example.com` / `qa_e2e_folo_*` | user | **72** |
| `ref-shadow-*` / `ref-dedupe-*@example.local` | user | 2 |
| `reise@infohub.local` | user | 1 |
| `acceptance.admin@infohub.local` | admin | 1 |
| `admin@example.com` | **admin** | 1 |

即：**真人账号 3 个，机器生成 74 个**；`quota.user_quotas` 同步为 **76 行**。

系统为此维护着：独立 `quota` schema、邀请码机制、per-user 自动日报开关与迁移（SCHED-001~004）、per-user 配额、多用户 token 聚合的 QA 矩阵。日报调度被迫做成"按启用自动日报且拥有活跃来源的用户生成"并"严格绑定来源所属用户"。

**因此准确的判断不是"为 2 个用户维护多租户"，而是：多租户机制的实际服务对象约 96% 是 QA 夹具——系统在为自己的测试基础设施供养一套多租户模型。**

**更关键的是清理并未生效**：2026-07-13 的数据重置清理掉 497 个 QA/shadow 用户和 495 条 quota 记录，且第一次执行因 `quota.user_quotas_user_id_fkey` 外键在事务内回滚失败（`docs/36` line 130）。但实测这 72 个 `qa_*` 账号**全部创建于 2026-07-20 至 07-24**，最新一个是 `qa_e2e_folo_*`，建于 07-24 02:56——**清理后十一天内重新长回 72 个，配额记录同步再生**。QA 账号生成器仍在运行且无回收机制。

这与 §7 根因 A 是同一个病：**不改生成端、只清存量，必然复发**。文档如此，账号也如此。

**顺带一个安全项**（见 §3.1.6）：`admin@example.com` 是 role=admin 的默认种子账号，创建于 2026-03-03，至今存活。

**最尖锐的一点**：`docs/dibao功能调研报告.md` 第 48 行已经记录了正确答案——Dibao 的设计选择是"不做多用户团队协作 → 降低权限、协同和数据边界复杂度"；同文件第 390 行还明确对比过"单用户单实例全部假设 | 信息中枢有 admin/acceptance 等验收账号和权限场景"。**调研做了，结论写下了，但没有被采纳。**

## 3. 架构与后端

### 3.1 安全：暴露面与部署现实不匹配（P0）

**这一节的所有结论都基于实测，不是代码推断。**

#### 3.1.1 端口全部暴露到局域网

`docker compose ps` 实测输出：10 个已发布端口**全部绑定 `0.0.0.0`**（含 IPv6 `[::]`），而非 `127.0.0.1`：

```
8000 audio-service   5555 changedetection   8082 dibao-reader
3001 hub-engine      80   nginx             8081 ntfy
5432 postgres        6379 redis             1200 rsshub      8010 scrapling
```

端口连通性实测：以上全部 OPEN。（9 个后端服务 + nginx 的 80）这意味着同一局域网内的任何设备（含访客手机、IoT 设备、被入侵的邻机）都能直接访问，nginx 那层统一入口形同虚设——因为所有后端都另有直达通路。

#### 3.1.2 scrapling-service 是无鉴权的可回显 SSRF 代理

`services/scrapling/app/main.py:141-148`：

- `POST /extract/article` 与 `POST /extract/snapshot` 的函数签名只有 `req: ExtractRequest`，**无任何 `Depends()` 认证依赖**，全文件也无认证中间件。
- `_extract()` → `_resolve_mode()` → `_run_fetch()` 全链路对 `req.url` **无任何内网地址校验**（无 `127.0.0.1`/`10.x`/`172.16-31`/`192.168`/`169.254`/`localhost` 黑名单）；`_resolve_mode` 只用 `urlparse` 取 hostname 做已知动态域名匹配。
- `ExtractResponse` 含 `content` 与 `html` 字段 → 目标响应正文**原样回显**给调用方。

组合结论：任何能访问 8010 的人，都能让这个服务代为请求 `http://postgres:5432`、`http://hub-engine:3001/api/*`、`http://changedetection:5000` 或云元数据端点，并拿回响应正文。且它基于 Playwright，具备完整浏览器能力。

调用方 `services/hub-engine/src/lib/scrapling-client.ts` 同样不做 URL 校验。

**风险等级：高。** 即使按"个人本机系统"打折，`0.0.0.0` 绑定 + 可回显 + 无鉴权这三者同时成立，已经超出"本机玩具"的容错范围；恶意网页通过 DNS rebinding 驱动浏览器访问 `localhost:8010` 也是现实路径。

#### 3.1.3 Redis 无密码且暴露

`docker-compose.yml` redis 段：`command: redis-server --appendonly yes`，**无 `requirepass`**；`ports: ["6379:6379"]` 即 `0.0.0.0`。`REDIS_URL: redis://redis:6379` 也不含口令。BullMQ 与 Celery 共用这一实例，可读写全部队列数据。Postgres 的 `5432:5432` 同理暴露（有密码，但把数据库端口摆在局域网上没有必要）。

**风险等级：高。**

#### 3.1.4 CORS 全开且无法配置

`services/hub-engine/src/index.ts:63`：`app.use('*', cors())` —— Hono 的无参数默认值等价于 `Access-Control-Allow-Origin: *`。`services/hub-engine/src/config/index.ts` 中 grep 不到任何 CORS 配置项，**即无环境变量可以收紧**。对照之下 audio-service 反而做对了（`main.py:33-39` 读 `settings.cors_origins_list`）。

#### 3.1.5 nginx 无鉴权透传运维后台，且无 TLS / 无限流 / 无安全头

`nginx/nginx.conf:115-125`：`/rsshub/`、`/cd/`、`/ntfy/` 三个 location **只有 `proxy_pass`，无 `auth_basic`、无 `allow/deny`**。其中 `/cd/` 是 changedetection.io 的完整管理界面（可增删监控、执行抓取）。

全文件实测：`listen 80` 是唯一监听（无 TLS）；`add_header` 全文仅出现 1 次，且是 `/health` 的 `Content-Type`（写在 `return` 之后，nginx 中实际不生效）；`limit_req`/`limit_conn`/`auth_basic` 出现 **0 次**。即 HSTS / CSP / X-Frame-Options / X-Content-Type-Options 全缺，登录端点可无限次爆破。

#### 3.1.6 默认种子管理员账号仍存活

`auth.users` 中 `admin@example.com`（role=**admin**，创建于 2026-03-03）至今存在且未禁用。它是 audio-service 首次启动时由 `AUDIO_ADMIN_EMAIL`/`AUDIO_ADMIN_PASSWORD` 初始化的种子账号，密码明文记录在 `local-secrets/infohub-credentials.md`。

配合 §3.1.1 的端口暴露面（audio 的 8000 直接绑 `0.0.0.0`），一个 `@example.com` 域名的默认管理员账号挂在局域网可达的服务上，风险等级不低于本节其他条目。

**处理建议**：禁用或改密，并从初始化脚本中移除默认凭据路径。

#### 3.1.7 audio 自动建号：需要降级表述的一条

静态分析最初判定 `services/audio/app/api/deps.py:39-61` 构成"admin 提权路径"。**交叉核验后应当降级**，理由如下：

- 代码事实成立：JWT 验签通过但用户不存在时自动 INSERT（`password_hash="external_auth"`），且 `role = UserRole.admin if payload.get("role") == UserRole.admin.value else UserRole.user` 直接采信 payload 的 role 声明；`docker-compose.yml:135/204/256/303` 确认 audio 三个进程的 `SECRET_KEY` 均引用与 hub 相同的 `${JWT_SECRET}`。
- **但 `services/hub-engine/src/lib/auth.ts:59-65` 的 `signAccessToken()` 中 `role: user.role` 取自数据库用户对象，普通用户无法影响自己 token 里的 role**。因此不存在"普通用户自行提权"的可利用链。
- 准确表述应是：这是**同信任域内的账号同步机制**，其风险不在于可被普通用户利用，而在于 (a) 单一密钥泄露的后果被放大到"可在 audio 侧凭空创建 admin"，(b) 自动建号无审计日志，(c) 它正是 497 个 shadow 僵尸账号的生成机制之一（默认邮箱格式 `shadow+{key}@local.invalid` 与清理记录吻合）。

**风险等级：中**（原判高，已降级）。这条修正记录在此，是为了让读者能校准本报告其余安全结论的尺度。

### 3.2 数据层：三套迁移机制并存，且业务写路径无事务

#### 3.2.1 启动时重放 600 行 DDL

`services/hub-engine/src/index.ts:231-835`：`ensureSchemaCompatibility()` 约 605 行，全是 `db.execute(sql...)` 形式的 DDL 与回填 UPDATE，**每次进程启动无条件重放**，且 `bootstrap()` 在 `index.ts:877` 先 `await` 它，HTTP 服务到 `index.ts:919` 才 `serve()`——串行阻塞启动。

其中 `index.ts:611-622` 的 `update hub.items as item set source_tier=..., processing_profile=..., growth_axes=... from hub.sources src where src.id = item.source_id` **没有任何"值已变化"守卫**，每次启动都实质重写全部关联 items 行，随数据量线性变慢。（其余对 items 的 UPDATE 带 `where ... is null` 守卫，属条件回填，此处不算。）

它还跨服务改表：`index.ts:232` `alter table public.prompt_templates` 动的是 audio 的表。

三套机制并存且都不规范：
1. `scripts/init-db.sql` 仅在 Postgres 首次初始化时经 `docker-entrypoint-initdb.d` 执行，对已有库无效；
2. 上述启动时重放；
3. `services/audio/app/database.py:31-43` 的 `create_all` + 10 条硬编码 `alter table ... add column if not exists`。

而**两套正规迁移工具都是空壳**：`services/audio/migrations/versions/` 只有 `.gitkeep`（Alembic 零版本）；`apps`/hub-engine 有 `db:generate/db:migrate/db:push` 脚本但**仓库无 `drizzle.config.ts`**，脚本无法运行。

#### 3.2.2 业务写路径 0 事务，retention 的统计数字是伪造的

grep 全部 TS 业务代码，`db.transaction` / `.transaction(` **0 命中**（Python 侧 `database.py:32` 的 `engine.begin()` 是建表 DDL，非业务路径）。

`services/hub-engine/src/lib/retention.ts` 逐点核验：

- **无事务无分批**：`:109-117` 四条裸 DELETE（items / insights / fetch_logs / ai_usage_logs）顺序执行，中途抛错即部分删除且不可回滚；且是一次性删除全部过期行，大表上长时间持锁。
- **统计数字伪造**：`:118-124` 的 `summary.deleted = { items: summary.items, ... }` 直接复制 `:82-85` **删除前**的 `count(*)::int` 结果，四条 DELETE 的真实 rowCount 全部被丢弃。报表数字与现实无关。
- **status 恒为 success**：`:145` 硬编码 `status: 'success'`，即使 `summary.errors` 非空、`storageDeleteFailed > 0`（`:128-131`）也写 success。
- **更隐蔽的一点**：若 DELETE 中途抛异常，`:142` 的 insert 根本不会执行——即"部分删除已发生，但 `retention_runs` 表里没有任何记录"。落盘的记录永远只有成功。
- 保护逻辑本身是对的：`is_favorite`/`is_later` 豁免，被 items 引用的 audio task 跳过（`:49-72`）。
- 30 天是硬编码在 `scheduler/cron.ts:142`，`config` 中无对应环境变量。

### 3.3 audio worker 连接池泄漏（有运行态证据）

`services/audio/app/tasks/audio_pipeline.py:27-29`：`_make_session()` **每次调用都 `create_async_engine(...)` 新建引擎与连接池**；调用点共 12 处（43/55/80/109/155/212/300/353/444/732/871/980 行），单条流水线会多次触发。全部 Python 代码（排除 `.venv`）grep `dispose` **0 命中**。

`async with` 只关闭 session、把连接还给那个临时池，池本身从未 dispose；且 `_run_async`（`:32-38`）用完即 `loop.close()`，asyncpg 连接绑定的事件循环已关闭，之后只能靠 GC terminate 兜底。

**运行态证据**（只读 `pg_stat_activity` + `docker network inspect` 容器 IP 反查）。当前 31 条 client backend 的完整归属：

| 来源容器 | app_name | 连接数 | state |
|---|---|---:|---|
| `infohub-audio-worker`（celery prefork `--concurrency=4`） | 空 | **15** | idle |
| `infohub-audio-worker-asr`（celery `--pool=solo --concurrency=1`） | 空 | **9** | idle |
| `infohub-audio`（FastAPI 常驻） | 空 | 5 | idle |
| `infohub-engine` | `postgres.js` | 1 | idle |

**可归因于泄漏的是 24 条**（两个 worker），不含 FastAPI 那 5 条——后者恰好等于其 `pool_size=5` 且 `backend_start` 晚于最后一个音频任务，属正常池化。changedetection / rsshub / dibao 在 `pg_stat_activity` 中零连接（dibao 用 sqlite，另两者不配 Postgres），已排除为替代解释。

**决定性证据是时序吻合**：24 条连接的 `backend_start` 与 `public.audio_tasks.created_at` **逐分钟一一对应**，最新一条精确到同一秒（07-24 02:29:31）；任务停止两天后连接一条未释放。常驻连接池会**复用**已有连接，而这里是每批任务**新增**连接且永不回收。

**最强的单条反证**：`audio-worker-asr` 以 `--pool=solo --concurrency=1` 运行（单进程、单任务串行），却持有 **9 条并发连接**——这个数字无法用任何池化模型解释。

**量级校准**：`max_connections=100`，当前 14 个任务产生 24 条泄漏连接（约 1.7 条/任务），照此约 50 个任务后耗尽连接槽；worker 重启即清零。**这是真实缺陷，但属慢速累积的潜在风险，不是当前正在燃烧的故障**——修复定级是"防患"而非"止血"。

## 7. 根因分析

上述问题不是一堆孤立缺陷，它们收敛到三条根因。**这也是本报告与 `21`–`32` 那 11 份审计文档的核心区别：它们罗列问题，这里解释问题为什么反复产生。**

### 根因 A：验收驱动的文档增殖循环

**机制**：项目采用"证据齐备才能勾选"的高标准纪律（正确）→ 每项任务产出验收文档与截图 → 任务多了之后需要一份"总览"来管理 → 总览本身变成需要维护的文档 → 发现总览过时，于是写一份新的总览 → 循环。

**证据**：11 份同质审计文档在 4 天内产生；`qa/reports/` 224 个文件而 `index.md` 实际只引用 17 个；`00-文档总导航.md` 需要用第 5 条规则宣布其中 10 份失效。

**为什么两次治理都失败**：`memory.md` 两次反思的结论都是"降低文档治理优先级"——即**把症状（文档太多）当成了问题，把治理动作（删文件）当成了解药**。但真正的驱动力是"每完成一项就要留一份证据"这条纪律没有配套的**证据生命周期**（何时归档、何时可删、什么级别的任务不需要独立文档）。不改变生成机制，只清理存量，必然复发。

**这条根因不止作用于文档——账号也犯了同一个错**（见 §2.4）：2026-07-13 清理掉 497 个 QA/shadow 用户，但生成端没动，十一天后重新累积 72 个，`quota` 记录同步再生。**同一个"只清存量不改生成端"的模式，在文档和数据两条线上各复发了一次。** 这使根因 A 从"文档治理问题"升格为"清理动作缺少生成端配套"的一般性问题，也意味着 §8.2 里所有"该砍"条目都必须先回答一个问题：砍完之后，它会不会自己长回来？

### 根因 B：单人项目继承了企业级模板的复杂度

**机制**：多租户、配额、邀请码、四态源生命周期——这些都是正确的企业级设计，但它们的**收益与真实用户数成正比，成本与代码量成正比**。在真人 N=3 时，收益趋近于零，成本照常发生。

**证据链**：`auth.users` 77 行中真人只有 3 个，其余 74 个为机器生成（72 个 QA 夹具账号）；`quota.user_quotas` 76 行；2026-07-13 清理 497 个僵尸账号时因外键在事务内回滚失败；`docs/dibao功能调研报告.md` 里已写下正确答案（单用户单实例）却未采纳。

**精确表述**：不是"多租户机制无人使用"，而是**它的实际服务对象约 96% 是 QA 夹具**——系统在为自己的测试基础设施供养一套多租户模型。这个表述比"为 2 个用户维护多租户"更准确，也更有说服力：它解释了为什么这套机制看起来"在被使用"却产不出价值。

**这条根因的隐蔽之处**：它不会产生任何一个"看起来像 bug"的现象。它表现为**所有事情都比应该的更慢一点、更容易出错一点**——迁移要多考虑一层用户隔离、清理要多处理一批外键、调度要多绑定一次归属。

### 根因 C：进度指标与系统健康度脱钩

**机制**：`36` 号文件的 111/115 统计的是任务勾选率，而系统健康度是抓取成功率、日报可发布率、AI 处理完成率。两者都被记录了，但**层级不同**：勾选率占据"总体进度"，健康度归入"阻塞与风险"。由于剩余任务多为"观察 7 天"这类时间不可压缩项，勾选率会长期冻结在 97%，而读者的注意力被这个百分比锚定。

**这不是披露缺失**（`36` 号写得很清楚，见 §2.2 的更正），**是指标排序问题**。

**证据**：97% 与"近 24h 65 成功/240 失败"、"最新可发布日报停在 07-24"、"正式采纳 0"在同一份文件里并存；`qa/reports/index.md` 的 conditional-pass 基线已持续 11 天未更新，而目录里最新文件是 07-26。

**与根因 A 的联动**：正因为健康度没有单一可信指标，每次想搞清"现在到底怎么样"就只能再做一次全面审计——于是产生第 12 份审计文档。**根因 C 是根因 A 的燃料。**

---

## 8. 结论：该修、该砍、该接受

### 8.1 必须修（进 `39` 号 P0/P1）

- 端口暴露面（绑定 `127.0.0.1` + scrapling 鉴权与内网黑名单 + Redis 口令）
- 默认种子管理员 `admin@example.com` 禁用或改密（§3.1.6）
- 诊断中心的九个虚构专名必须消失（最小修复十分钟，§4.1）
- SPA 会话中途 401 的统一处理
- QA 账号生成端的回收缺口（否则清理必然复发，§2.4）
- 启动时 600 行 DDL 重放 → 正规迁移
- retention 的事务、分批与真实 rowCount
- audio worker 连接池泄漏
- `make gate` 纳入 `npm test` 与 `pytest`
- 日报工作台的口径矛盾
- 重建 `acceptance.user` 并修正凭据文档

### 8.2 该砍（需 Reise 拍板，进 `39` 号决策建议区）

- **多租户复杂度**：`quota` schema、邀请码、per-user 调度绑定。真人 N=3 的系统不需要这些。**但砍之前必须先关掉 QA 账号的生成/回收缺口**——否则会和 2026-07-13 那次一样复发（§2.4、§7 根因 A）。
- **254 条候选源的四态准入体系**：跑了一周，采纳 0。要么降低准入成本，要么承认这条产品线暂缓。
- **`21`、`23`–`32` 共 11 份同质审计文档**：应整体移入 `docs/归档/`。
- **约 1200 行前端死代码**与未使用依赖（`zustand`、6 个未用 Radix 包）。
- **设计 token 二选一**：要么把 2385 处 `zinc-*` 迁到 token，要么删掉没人用的 token 体系。目前"两套都在"是最差状态。

### 8.3 该接受（不建议现在动）

- **hub-engine 单进程不可水平扩容**：单机个人系统不需要水平扩容，`stop_grace_period: 15m` 才是要缩短的。
- **超大文件拆分**（`daily-report.ts` 4785 行等）：是真债，但收益递延、风险不低，应排在功能真实性与安全之后。
- **完整 i18n**：全站中文硬编码在当前场景下不是问题，只需修掉零星的裸英文报错（`Unauthorized`、`Invalid email or password`、`Failed to fetch`）。
- **文档编号体系重构**：会引发新一轮文档工作，与根因 A 相悖。只做归档，不做重编号。

### 8.4 对根因的处方（比单个修复更重要）

1. **给证据设生命周期**（对治根因 A）：明确哪些任务需要独立文档、验收证据保留多久、`qa/reports/` 的近空日志与中间截图何时清理。不设生命周期，删多少次都会长回来。
2. **把 N=2 写进架构假设**（对治根因 B）：在 `AGENTS.md` 或 `01` 号文档中明确"本系统按单用户单实例设计"，让后续所有设计决策有据可依，而不是每次都默认按多租户实现。
3. **换一个进度指标**（对治根因 C）：用"抓取成功率 / 日报可发布率 / AI 处理完成率"三个运行指标替代任务勾选率作为项目健康度门面。`36` 号的任务勾选继续保留，但不再作为"项目完成度"对外表述。
