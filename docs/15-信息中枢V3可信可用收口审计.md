## 需要再验的风险点

### 1. 启动自迁移必须在真实库验证

`services/hub-engine/src/db/schema.ts` 新增 `summaryReason`，`services/hub-engine/src/index.ts` 已加入启动时 `alter table hub.items add column if not exists summary_reason text` 和旧数据回填。风险不在代码意图，而在真实环境是否一定走到 `ensureSchemaCompatibility()`，以及旧库权限是否允许 alter。

验收方式：本地真实栈启动后，查询 `hub.items.summary_reason` 是否存在；打开 1 条 summary failed/skipped 条目，确认 Feed 能显示摘要诊断。

### 2. 日报候选逻辑改动大，必须用真实当天数据闭环

日报工作流同时改了范围词、自然日窗口、泛商业噪声、fallback scored、聚合源降权、事件去重、生成模式和未入报诊断。单测能证明规则局部正确，但不能证明真实日报“读起来可信”。

验收方式：生成当天日报，人工抽查 10 条入报/未入报证据，要求 Insights 漏斗、TOP 入报理由、未入报解释、最终 Markdown 四者一致。

### 3. 评分 fallback 不能变成“假可信”

`processors/ai-scorer.ts` 增加 deterministic fallback、retry recovered、model circuit breaker。方向正确，但 fallback 分数必须在 UI 和日报里带风险标记，不能让用户误以为是正常 AI 评分。

验收方式：制造或选取模型空响应/失败样本，确认 Settings 能显示模型健康，Feed/Insights 能看到 fallback 风险，日报不把 fallback scored 当作高可信主候选。

### 4. 批量 reprocess 要验证权限和状态守恒

`/api/items/reprocess` 是强力修复入口。它必须只处理当前用户条目，且不能把硬过滤噪声误恢复到主流程。

验收方式：按 `itemId/sourceId/date/stage` 四种筛选跑 API，确认 matched/itemIds 都属于当前用户；对硬过滤条目重跑后仍保持过滤边界。

### 5. 前端移动端可用性仍需截图验收

Feed/Sources/Insights 都补了很多状态块和按钮。桌面端信息密度提升，但移动端最容易出现卡片挤压、按钮换行不稳、日报 Markdown 横向溢出。

验收方式：用 Playwright 或浏览器在 390px 宽度验收 `/sources`、`/feed/:id`、`/insights` 三条主链路。

## D2-D3 真实数据验收清单

选择 3-5 个代表性信源：

- 高价值全文 RSS：验证正文率和摘要质量。
- 片段型 RSS：验证 content degraded 和 Feed 诊断。
- 高频聚合源：验证噪声率、日报聚合源降权。
- 英文 AI/技术源：验证翻译与中文摘要。
- 泛商业/财经噪声源：验证 business_noise 未入报。

每个源执行：

1. `POST /api/fetch/source/:id?contentLimit=...&aiLimit=...&translationLimit=...`
2. 查看返回 `qualityFunnel`。
3. 打开 `/sources`，确认该源的质量分、正文率、AI 完成率、噪声率。
4. 打开 `/feed/:itemId`，确认内容依据、评分拆解、摘要/翻译状态、失败原因。
5. 对至少 1 条失败或降级条目跑 `/api/items/reprocess`。
6. 生成当天日报，核对 `/insights` 漏斗和最终 Markdown。

需要保存的证据：

- sourceId、itemId、report date。
- 抓取返回摘要。
- 3 个页面截图或 Playwright 断言结果。
- 日报 Markdown 片段和 TOP 入报/未入报抽查表。
