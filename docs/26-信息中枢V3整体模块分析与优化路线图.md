# 信息中枢 V3 整体模块分析与优化路线图

## 1. 结论先行

信息中枢 V3 现在的真实状态是：

- **系统骨架已经完整**，不是从 0 到 1 问题。
- **用户主体验还不可信**，尤其是 Feed 阅读和日报输出。
- **问题集中在收口，不在继续扩功能**。

从代码结构看，项目已经具备完整的信息处理中枢能力：

- 多源采集：RSS、网页监控、网页索引、榜单源、邮箱、音频、Dibao 对照侧车。
- 中间处理：正文抽取、去重、质量过滤、评分、摘要、翻译、健康诊断、日报工作流、文章资产。
- 输出产品：Feed、Sources、日报工作台、正式日报、AI 用量、Reader Lab、导出。

但当前用户仍会感觉“抓到了很多，读起来乱，日报也浅”，原因不是缺一个页面，而是下面四层没有彻底收口：

1. **内容可信层**没有完全统一。
2. **阅读层**仍像系统面板，不像阅读器。
3. **日报层**还是系统生成结果，不是编辑型雷达。
4. **来源治理层**知道问题，但没有完全反控 Feed 和日报。

后续优化路线应该固定为：

**先把内容层做真，再把阅读层做顺，然后把日报层做深，最后再扩推荐和外部源。**

## 2. 项目重点模块总图

### 2.1 输入与采集层

主要代码：

- `services/hub-engine/src/collectors/`
- `services/hub-engine/src/routes/fetch.ts`
- `services/hub-engine/src/scheduler/pipeline.ts`
- `services/hub-engine/src/routes/integrations.ts`

负责内容进入系统的第一步，包括：

- RSS / Atom
- 网页快照监控
- 网页索引页拆条
- BestBlogs 榜单源
- 邮箱投递
- Dibao Reader Lab 对照

当前判断：

- 能力面够广。
- 但“源类型”和“条目类型”仍会混用。
- 已经不是采不到，而是采进来的内容语义边界不清。

### 2.2 正文可信层

主要代码：

- `services/hub-engine/src/lib/content-extractor.ts`
- `services/hub-engine/src/lib/content-status.ts`
- `services/hub-engine/src/lib/reading-context.ts`
- `services/hub-engine/src/lib/item-enrichment.ts`
- `services/hub-engine/src/lib/content-upgrade-policy.ts`

这是整个系统的底座，决定：

- 当前内容到底是全文、片段、索引摘要还是榜单摘要
- 是否允许补抓原文
- 摘要、翻译、日报到底基于什么内容层生成

当前判断：

- 这是当前最关键的 P0 模块。
- 它不稳定，后面所有模块都会假稳定。

### 2.3 Feed 阅读台

主要代码：

- `apps/web/src/features/feed/page.tsx`
- `apps/web/src/pages/Feed.tsx`
- `apps/web/src/lib/feed-layout.ts`
- `apps/web/src/components/MarkdownContent.tsx`
- `apps/web/src/lib/api/contracts.ts`

当前已经形成三栏工作台：

- 左侧来源上下文
- 中间文章列表
- 右侧阅读详情

当前判断：

- 方向是对的。
- 但详情页仍然暴露太多系统解释、资产入口和诊断状态。
- 正文虽然已经变大，但还不是绝对主角。

### 2.4 阅读资产层

主要代码：

- `services/hub-engine/src/lib/article-assets.ts`
- `services/hub-engine/src/routes/items.ts`
- `apps/web/src/lib/reading-assets.ts`

这层本来应该承载“读后沉淀”，包括：

- 摘要
- 翻译
- 中文改写
- 问文章
- 重写
- 知识沉淀
- 日报引用

当前判断：

- 结构已经开始出现。
- 但资产边界还不清楚。
- 摘要、改写、翻译、问文章之间仍有重复感。
- 资产没有真正成为日报和长期阅读的复用层。

### 2.5 Sources 健康与治理中心

主要代码：

- `services/hub-engine/src/lib/source-health.ts`
- `services/hub-engine/src/routes/sources.ts`
- `apps/web/src/features/sources/page.tsx`

当前已经能诊断：

- 抓取是否成功
- 正文可读率
- AI 完成率
- 日报覆盖情况

当前判断：

- 已经具备治理雏形。
- 但还不够强势。
- 它知道问题，却没有完全决定 Feed 和日报的行为。

### 2.6 日报工作流与日报阅读页

主要代码：

- `services/hub-engine/src/routes/daily.ts`
- `services/hub-engine/src/outputs/daily-report*.ts`
- `apps/web/src/pages/Insights.tsx`
- `apps/web/src/pages/Reports.tsx`

当前能力已经包括：

- 候选池
- 工作台
- 异步生成
- 正式日报页
- 日期切换
- 模块稿件
- 全池索引

当前判断：

- 已经不是“没有日报”。
- 而是“日报仍像系统输出，而不是高质量成稿”。

### 2.7 AI 用量与模型观测

主要代码：

- `services/hub-engine/src/routes/admin-ai-usage.ts`
- `apps/web/src/pages/AIUsage.tsx`

当前判断：

- 这个模块基础已经可用。
- 但它属于诊断层，不应该再侵入 Feed 和日报主阅读路径。

### 2.8 Reader Lab / Dibao 对照

主要代码：

- `apps/web/src/pages/ReaderLab.tsx`
- `services/hub-engine/src/lib/dibao-integration.ts`
- `services/hub-engine/src/routes/integrations.ts`

当前判断：

- 这不是主产品，而是非常重要的对照底座。
- 它的价值不在“替代信息中枢”，而在“帮我们判断问题是源、抽取、还是展示”。

## 3. 当前存在的核心问题

## 3.1 P0：内容层不够真

这是当前最核心的问题。

### 现象

- 索引页条目有时被当成普通文章。
- 榜单摘要有时被当成全文可读。
- 网页快照条目会进入阅读主链路。
- 摘要、翻译和日报可能并不是基于同一层内容生成。
- 用户看到“已翻译”“可读”“可引用日报”，但底层其实只是摘要或片段。

### 根因

- `items.content` 仍承载了太多混合语义。
- “内容类型”和“来源类型”没有完全形成统一合同。
- `feed_only / smart / full / monitor_only` 这一层来源正文策略还没有在全链路完全生效。

### 风险

- 用户直接失去信任。
- 翻译按钮可能无效或静默。
- 日报会把线索当证据。

## 3.2 P0：阅读体验不够收敛

### 现象

- Feed 详情页首屏还是能看到过多状态条、资产条、诊断条、操作条。
- 主阅读标签之外的能力还在主路径抢位置。
- 正文视觉层级不够极致，工具噪音仍在打断阅读。

### 根因

- 产品逻辑里把“可诊断”和“可阅读”同时放在第一层。
- UI 已经开始参考 QMReader / Folo 的思路，但还没有真正压住杂音。

### 风险

- 用户默认视角仍然是“系统控制台”，不是“阅读器”。

## 3.3 P0/P1：日报不够深、不够像编辑成稿

### 现象

- 能生成，但文章覆盖仍偏少。
- 有模块，但叙事容易像候选池改写。
- 目录、模块、重点文章、更多动态、深读之间层级还不够清楚。
- 有时看起来像一个技术工作台，而不是“今天的信息雷达”。

### 根因

- final report 仍承担了过多一次性融合任务。
- 中间缺少稳定的 `editorialDigest` / 模块编辑层。
- 大量候选没有先被整理成“精选展开 / 模块引用 / 更多动态 / 附录索引”。

### 风险

- 用户会持续觉得“信息很多，但日报很浅”。

## 3.4 P1：来源治理层没有完全反控输出

### 现象

- Sources 能看到很多问题。
- 但问题来源仍可进入推荐阅读、原文主 tab、翻译动作和日报候选。

### 根因

- 目前治理更多是“诊断页告警”，还不是“主产品调度规则”。

### 风险

- 系统知道问题，但主界面继续消费问题数据。

## 3.5 P1：阅读资产层边界不清

### 现象

- 中文改写和摘要容易被认为是一回事。
- 问文章、重写、知识都暴露得太早。
- 资产生成后不够稳定地反哺日报和后续阅读。

### 根因

- 资产模型还没有完全按“主阅读资产 / 扩展资产 / 编辑资产”分层。

### 风险

- 功能变多，但用户理解成本也变高。

## 3.6 P1/P2：历史数据债还在污染结果

### 现象

- 新代码已经开始修正文策略，但老条目仍停留在旧内容层。
- 老的网页快照条目、旧 RSS 内容、旧摘要、旧翻译仍在系统里继续参与展示。

### 根因

- 缺少针对高价值来源和高价值条目的补回填计划。

### 风险

- 明明代码修了，用户仍看到旧问题。

## 4. 优先级判断

## 4.1 现在最该做的不是继续扩功能

当前系统不缺这些能力：

- 接更多信源
- 增加更多按钮
- 增加更多 Agent
- 再做一套新页面

现在真正缺的是：

- **明确内容层边界**
- **让阅读主路径更干净**
- **让日报更像正式产物**

## 4.2 优先级排序

### 第一优先级：P0 可信底座

必须先做：

1. 内容合同统一
2. 来源正文策略完全生效
3. 原文抽取/渲染保真
4. 翻译动作真实可解释
5. 高价值历史条目回填

### 第二优先级：P1 阅读产品化

随后做：

1. Feed 首屏降噪
2. 扩展资产后移
3. 正文排版升级
4. 摘要/改写/翻译边界重新定义
5. 文章资产真实保存与复用

### 第三优先级：P1/P2 日报产品化

再做：

1. editorialDigest 中间层
2. 模块稿件生成
3. 更多动态确定性输出
4. 重点文章与深读增强
5. 正式日报页结构升级

### 第四优先级：P2 治理闭环

最后做：

1. Sources 真正控制 Feed / 日报资格
2. Reader Lab 对照结果反哺来源策略
3. 历史来源清理、降权和修复常态化

## 5. 分阶段优化计划

## Phase A：可信底座收口

目标：

让系统做到“展示什么，就真的是什么”。

### A1. 统一内容合同

固定内容状态：

- 全文可读
- RSS 正文
- 索引摘要
- 榜单摘要
- 网页快照
- 片段
- 标题

要求：

- Feed、翻译、摘要、日报都引用同一套状态。
- 不允许再用模糊状态混过去。

### A2. 固化来源正文策略

每个来源明确：

- `feed_only`
- `smart`
- `full`
- `monitor_only`

策略必须直接影响：

- 自动补抓
- 翻译动作
- 原文 tab
- 日报候选权重

### A3. 修正文抽取与保真

重点动作：

- RSS 已给出完整正文时，优先用干净 feed 内容。
- 原站正文补抓走 `readabilityContent` 独立层。
- 原文渲染保留段落、列表、引用、链接、代码块。

### A4. 修翻译动作

动作逻辑要改成：

- 有全文无译文：`一键翻译全文`
- 只有索引摘要但有原站链接：`补抓原文并翻译`
- 无法补抓：显示失败原因 + 打开原文

### A5. 补高价值历史数据

优先补这些源：

- Anthropic Newsroom
- TechCrunch AI
- The Verge AI
- Daring Fireball
- BestBlogs 高价值条目
- OpenAI News

### Phase A 验收

- 抽测 20 条内容，提示文案与真实内容层一致。
- 原文 tab 不再把索引摘要或网页快照误标为全文。
- 翻译动作不再静默失败。

## Phase B：阅读产品化

目标：

让 Feed 成为一个真正能连续使用的阅读工作台。

### B1. 主阅读区只保留三类主标签

- 摘要
- 原文
- 翻译

其他全部后移：

- 中文改写
- 问文章
- 转写
- 知识
- 日报引用
- 阅读资产
- 工具与诊断

### B2. 首屏降噪

首屏只保留：

- 来源
- 标题
- 时间
- 评分/等级
- 打开原文
- 一行阅读提示

不再把大面积诊断说明铺在主阅读流。

### B3. 正文视觉升级

目标风格：

- 类 Folo / QMReader 的克制阅读器
- 宽度 760-860px
- 字号约 17px
- 行高 1.8-1.9
- 图片、列表、代码块、引用分层明确

### B4. 资产层重新分层

把资产分成三类：

1. 主阅读资产：摘要、翻译
2. 扩展理解资产：中文改写、问文章
3. 编辑资产：日报引用、证据、行动建议

### B5. 文章资产反哺主系统

要求：

- 问文章生成结果可保存
- 重点文章可引用文章资产
- 文章资产可成为日报证据层

### Phase B 验收

- 10 条真实长文抽测，默认首屏不再被系统信息淹没。
- 用户可以快速区分“正文”“线索摘要”“榜单摘要”。

## Phase C：日报产品化

目标：

把日报从“生成结果页”升级为“编辑型信息雷达”。

### C1. 引入 editorialDigest 中间层

先把候选池整理成：

- 精选展开
- 模块引用
- 更多动态
- 深读
- 附录索引

不要再让 final prompt 一次吞全部原料。

### C2. 固定正式日报结构

建议结构：

1. 今日封面判断
2. 目录
3. 信息雷达总览
4. 今日精选
5. 模块日报
6. 更多动态
7. 重点研究/深读
8. 阅读顺序
9. 下一步行动
10. 附录：全池摘要索引

### C3. 模块稿件化

每个模块不再只是文章列表，而是：

- 本模块今天发生了什么
- 为什么重要
- 哪几篇最值得读
- 共同信号是什么
- 噪声和不确定性是什么
- 你的建议动作是什么

### C4. 覆盖提升

目标：

- 重点展开 8-12 篇
- 模块引用 20-35 篇
- 更多动态覆盖 10-20 篇
- 总覆盖 35-60 篇

### C5. 阅读页结构升级

要求：

- 目录 sticky
- 章节锚点稳定
- Markdown 层级清晰
- 右侧导航不丢
- 不再像系统面板

### Phase C 验收

- 一份日报能回答：今天发生了什么、最重要的趋势是什么、先读哪几篇、哪些只是噪声。
- 正文厚度稳定，不再只像浅层摘要拼接。

## Phase D：治理闭环与长期演进

目标：

让 Sources 真正成为主治理面。

### D1. 让来源治理反控输出

来源健康直接影响：

- Feed 推荐资格
- 自动补抓
- 翻译动作
- 日报候选资格

### D2. 建立 Reader Lab 对照节奏

对固定样本源长期做 InfoHub vs Dibao 对照，判断问题来源：

- 是源本身差
- 是抽取差
- 还是展示差

### D3. 历史清理与常态修复

建立周期性任务：

- 高价值来源回填
- 旧快照降级
- 错误摘要/翻译重跑
- 失真条目回查

---

## 6. 现在不应该优先做的事

以下事项短期都不该排到前面：

1. 再扩大量新信源  
2. 再加更多阅读按钮  
3. 先上 embedding 个性化推荐  
4. 推倒重做整个前端视觉系统  
5. 继续在日报里暴露更多运行态和调试态  

这些都不是当前卡点。

---

## 7. 建议的执行顺序

### 第一周

- 收口内容合同
- 收口来源正文策略
- 修翻译动作
- 修高价值来源的原文可信层

### 第二周

- Feed 首屏降噪
- 正文排版升级
- 扩展资产后移
- 文章资产可保存可复用

### 第三周

- 日报 editorialDigest
- 模块稿件生成
- 更多动态确定性输出
- 正式日报阅读页升级

### 第四周

- Sources 真正反控 Feed / 日报
- Reader Lab 质量对照常态化
- 高价值历史数据补债

---

## 8. 一句话判断

信息中枢 V3 现在最需要的不是“再做更多”，而是把已经做出来的能力压成一条清晰主线：

**真内容 -> 顺阅读 -> 深日报 -> 强治理。**

只有这四步收口，系统才会从“功能很多”真正变成“日常可信可用”。
