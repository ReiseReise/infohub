系统主链路

这是“项目为什么已经可用”的主因，重点在于从采集到阅读再到输出已经闭环。

信源接入

RSS、RSSHub、播客订阅、网页快照、变更监控、自定义 API。

采集队列

Cron 和手动触发并存，统一进入 fetch 队列。

处理层

去重、规则、评分、摘要、翻译、音频任务联动。

输出层

Feed、日报、导出、播客/音频结果、监控结果查看。

沉淀与运维

知识库、Obsidian、门禁、文档、统一入口。

自动转写策略

本轮只做保守策略，目标是先把规则闭环做真，再谈更多策略维度。

新音频条目

仅对本次采集新入库的音频条目评估，不回填历史。

Source 开关

必须开启 `source.autoTranscribe`。

用户总开关

必须开启 `quota.autoTranscribeEnabled`。

每日上限

当前只真正执行 `maxAutoPerDay`。

创建任务

调用 audio-service 创建任务并回写 `audioTaskId`。

Webhook 回写

完成后回写 transcript / knowledge / duration。

预留但未执行：`maxEpisodeMinutes`、`monthlyBudgetLimit`。这两项在页面和文档中必须明确写成“预留策略”，不能伪装成已生效。

AI 治理方式

这轮的关键变化不是“又多了几个模型字段”，而是把模型、提示词和场景绑定收回到管理员统一治理。

模型库

统一维护 LLM / ASR / 多模态模型配置。

模板库

统一维护评分、摘要、翻译、日报总览等提示词模板。

场景绑定

把模型和模板绑定到 `scoring / summary / translation / daily_report`。

阅读 AI

普通用户在 Feed 里只消费已生效能力，不再自填 provider。

日报总览

日报保留确定性骨架，再拼上可编辑的 AI 总览段落。

管理员控制

配置入口统一在 Settings 的 AI 管理中心。

网页监控结果落点

网页监控以前最大的问题不是能不能抓，而是“抓完去哪看”。现在用双层视图把语义拆清楚。

新建来源

在 Monitor 里选择模式：网页快照或变更监控。

网页快照

一次性抓取网页内容，适合人工触发的采集任务。

变更监控

持续监听变化，适合 changedetection 类 watch。

统一入 Feed

两类结果都进入 Feed，不额外造第二套内容库。

Monitor 时间线

右侧时间线专门看结果和最近变化。

回到阅读器

点击结果可跳转 Feed 详情阅读。

User Acceptance

普通用户验收路径

  • 登录
  • 进入 Feed 阅读与详情，切换摘要 / 原文 / 翻译 / 转写 / 知识
  • 在 Sources 新增信源并开启自动转写
  • 在 Monitor 验证网页快照与变更监控的结果时间线
  • 在 Audio 查看真实 URL 任务详情与失败码 / 策略信息
  • 在 Rules 验证个人规则
  • 在 Settings 检查全局自动转写与“阅读 AI”状态
Admin Acceptance

管理员验收路径

  • 登录
  • 进入 Settings 的 AI 管理中心，验证模型库 / 模板库 / 场景绑定
  • 在 Rules 切换到全局规则并验证生效边界
  • 进入 Settings 的 Diagnostics
  • 查看 Admin Dashboard / Tasks / Users / Invites
  • 验证权限边界：普通用户不可见后台页签
  • 确认队列、代理测试与邀请管理正常
