# 当前状态与功能地图

## 1. 当前判断

信息中枢 V3 现在最准确的定位，不是“信息阅读器”，也不是“万能情报平台”，而是一个已经跑通主链路的**个人 / 小团队信息加工台**：

- 上游能持续接入内容
- 中间能做 AI 清洗、评分、翻译、转写、摘要
- 下游能让人读、让人判断、让人导出

但它距离顶层设想里那个更强的“数据引擎”还有一段路。当前最核心的矛盾不是页面不够多，而是：

1. 输入面还不够宽
2. 输出面还不够结构化
3. 专题面还不够深

一句话结论：

- 作为日常信息工作台，已经可用
- 作为可复利的专题情报引擎，还在第二阶段

## 2. 页面验收地图

| 页面 | 当前角色 | 当前判断 | 主要短板 |
|---|---|---|---|
| `/feed` | 阅读与理解主入口 | 可验收 | 已有正文补抓与诊断，但专题串联还不够强 |
| `/sources` | 输入面治理中心 | 可验收 | 非 RSS 来源模板还少 |
| `/monitor` | 网页监控与变化提醒 | 可验收 | 已支持监控源与结果拆看，下一步是更强专题联动 |
| `/rules` | 规则过滤与优先级治理 | 可验收 | 规则解释性还可继续增强 |
| `/podcast` | 播客聚合与跳转页 | 可验收 | 仍更像入口，不是完整工作台 |
| `/audio` | 音频处理与阅读工作台 | 可验收 | 自动策略仍有“未知时长”盲区 |
| `/insights` | 日报与专题洞察工作台 | 可验收 | 专题模板还没沉淀成长期资产 |
| `/settings` | AI 治理、日志、诊断后台 | 可验收 | 趋势已具备，下一步是把 retention / 动态抓取治理做深 |

## 3. 按用户旅程看的功能地图

### 3.1 发现与采集

当前已经具备：

- RSS、RSSHub、YouTube 基础采集
- 网页快照与变更监控
- 原生网页提取 + Scrapling 动态兜底
- 自定义采集器与 OPML 导入

这意味着“把稳定来源拉进系统”已经不是问题。真正的问题是：**系统还不够覆盖那些最有价值但最不规整的来源**。

当前判断：

- 已成熟：RSS 类输入
- 已有基础：Newsletter、网页监控、动态网页兜底
- 待推进：X / Twitter、公众号、非标准站点专题模板

### 3.2 阅读与理解

当前已经具备：

- 正文补抓
- AI 评分、摘要、翻译
- 规则过滤与优先级
- `POST /api/items/:id/enrich` 驱动的富化状态机

这条链路现在的价值，不只是“有 AI 功能”，而是它开始形成一个**会补全、会重算、会解释状态**的阅读对象。

当前判断：

- 已成熟：条目级阅读、富化、翻译、摘要、抓取诊断
- 待推进：专题串联、阅读后的长期资产沉淀

### 3.3 音频与转写

当前已经具备：

- 上传与 URL 音频处理
- `OSS + 远程批量 ASR` 主路径
- 摘要、转写、Markdown、多 tab 阅读
- 自动转写的四段判定

当前判断：

- 已成熟：音频主路径与可读性工作台
- 待推进：未知时长预判、预算策略更前置

### 3.4 洞察与专题

当前已经具备：

- 日报工作台
- 多代理结构化生成
- preset 化输出
- Markdown 导出

这意味着系统已经能做“日报”，但还没有真正形成“专题研究操作系统”。

当前判断：

- 已成熟：通用日报生成
- 待推进：AI / 头部舆论新闻的长期专题模板、专题知识输出、长期复盘闭环

### 3.5 配置与治理

当前已经具备：

- 模型配置
- 提示词模板
- 场景绑定
- AI 调用日志
- 失败诊断与错误聚合
- 30 天历史裁剪

当前判断：

- 已成熟：基本治理闭环、数据新鲜度可见化、手动启动后的到期来源补抓
- 待推进：豆包标准字段彻底收口、成本与热点分析、场景配置更细粒度的运行说明

### 3.6 数据新鲜度与运行态

当前已经具备：

- 启动后一轮 `startup catch-up`
- `/api/fetch/status` 新鲜度状态
- Feed / Sources / Settings 的新鲜度提示
- “立即补抓到期来源”动作

当前判断：

- 已成熟：手动启动模式下的数据过期原因可见、可解释、可恢复
- 待推进：更细的来源级模板策略和更稳的非 RSS 输入

## 4. 顶级设想对照总表

| 自动清洗与优先级判断 | 评分、摘要、翻译、规则过滤、正文补抓已跑通 | 已完成第一阶段 | 把专题规则和跨条目判断做得更强 |
| 音频自动处理与低摩擦阅读 | 音频主路径、转写、总结、工作台已跑通 | 已完成第一阶段 | 补未知时长预判与预算前置控制 |
| 每日 / 专题洞察引擎 | 日报多代理与 preset 已上线 | 部分完成 | 做 AI / 头部舆论专题模板、专题复盘资产 |

## 5. 现在真正该做的，不该做的

### 5.1 现在真正该做的

#### P0

1. **动态网页模板与非 RSS 输入继续前推**  
   在原生 + Scrapling 的基础上，补 1 到 2 个最有价值的非标准来源模板。

2. **AI 管理中心继续细化场景控制台**  
   现在已经有场景控制台、模型仓库、评分 Skills、使用日志四层，下一步该补“不同功能到底为什么用这套模型”的运行说明。

3. **评分 Skills 与显式反馈闭环继续长成长期偏好系统**  
   当前入口已独立，但还需要更自然的反馈回流和偏好迭代节奏。

#### P1

1. **结构化输出消费者链路**
2. **Feed 到专题的串联能力**
3. **AI / 头部舆论专题模板与长期资产化**

#### P2

1. **跨条目专题关系图**
2. **更强的自动化输出编排**
3. **更稳定的小范围共享能力**

### 5.2 现在不该做的

1. 不该继续扩大量新页面
2. 不该同时追很多 provider 接入
3. 不该把当前阶段误包装成公网产品
4. 不该用更多零碎文档代替产品判断

## 6. 关键流程说明

### 6.1 Feed 富化

打开详情后，如正文缺失，系统会走 `POST /api/items/:id/enrich`，尝试补抓正文，并在需要时重跑评分、摘要和翻译。对于动态网页，系统现在会先走原生提取，再在失败或命中已知动态域名时回退到 Scrapling。

### 6.2 自动转写

新音频条目当前会经过四段判定：

1. Source 是否开启自动转写
2. 用户总开关是否开启
3. 今日自动次数是否超限
4. 单集时长与月预算是否允许

如果被跳过，条目会进入 `audioStatus=skipped`，而不是假装“没处理过”。

### 6.3 AI 日志

管理员当前已经可以直接判断：

- 哪些调用来自 Hub，哪些来自 Audio
- 哪个场景最耗钱
- 哪个 Provider / Endpoint 在承担调用
- 高频失败原因是什么
- 最近一次 30 天历史裁剪的结果是什么

下一阶段不是继续补字段，而是把这些日志变成**能管理趋势、成本和故障热点**的决策面板。
