# 信息中枢 V3 整体重点模块分析与优化计划

## 0. 结论

信息中枢 V3 当前不是“没做起来”，而是已经进入更危险的阶段：**能力很多，但主链路没有足够收敛**。从运行态看，系统在持续采集、持续调用模型、持续生成日报；但从用户体验看，正文、翻译、日报、来源健康和阅读界面仍然不能让人完全信任。

本次复核的核心判断：

1. **采集量不是第一瓶颈**
   当前有 706 个 active 来源，24 小时内抓取约 712 条，总条目约 19,275。数据池并不小。问题在于抓到之后没有稳定进入“可读正文层、可用翻译层、日报证据层”。

2. **正文可信层是全系统第一瓶颈**
   `content_status=ready` 有 18,799 条，但 `readability_status=ready` 只有 1,439 条。也就是说，大量条目在数据库里看似有内容，实际未必是用户可读正文。Feed 读不顺、翻译不完整、日报浅，都和这一层直接相关。

3. **翻译层覆盖和反馈都不足**
   已翻译条目只有 417 条。并且真实样本中存在“长文只有短译文”“点击翻译无明显反馈”“系统误判中文摘要导致没有翻译入口”等问题。

4. **日报不是没有生成，而是正式产品形态不稳定**
   `hub.insights` 中最近多天都有 daily 记录，但最新记录里 `coverageItems / priorityArticles / moduleSections` 都是 0。说明日报页面和后端已经有很多设计字段，但正式保存结果没有稳定落入这些结构，用户看到的自然像浅层摘要或调试输出。

5. **Sources 健康分数当前过于乐观**
   来源表里 RSS 平均健康分约 96，几乎全都显示 active/成功。但这只能证明“抓取任务成功”，不能证明“抓到的正文可读、AI 已处理、日报能覆盖”。健康中心必须从抓取成功升级为全链路质量诊断。

6. **Feed 阅读台已经有三栏基础，但阅读主视觉仍被系统信息挤占**
   页面结构已经开始向阅读器靠近，但首屏仍暴露太多状态、工具、诊断、资产、日报解释。用户要的是“先读懂文章”，不是先理解系统流水线。

7. **工程复杂度已经到了必须拆边界的程度**
   `Feed page` 2603 行、`Sources page` 2305 行、`daily-report.ts` 3406 行、`items.ts` 1780 行。继续在这些文件里堆逻辑，会让每次修复都变成“修一个点、冒出三个副作用”。

一句话概括：

> 当前信息中枢 V3 已经有系统雏形，但还不是可信产品。下一阶段必须停止扩散式加功能，优先把“内容可信、阅读可用、日报有深度、来源能治理、生成有反馈”五条主链路收口。

## 2. 重点模块分析

## 2.1 来源与采集模块

### 当前能力

- RSS / RSSHub / podcast / webpage / webpage_index / curated_index / email / custom 都已经存在。
- 706 个 active 来源，705 个自动抓取。
- `fetch_logs` 有基础结果：found/new/duplicate/filtered/queuedAi。
- Dibao 侧车已跑，可做同源质量对照。

### 主要问题

1. **抓取成功不等于内容成功**
   当前来源健康更多反映任务是否跑过，而不是文章是否可读。RSS 源健康分高，但大量文章没有 readability 正文。

2. **来源类型与条目类型混杂**
   来源表有 `rsshub/podcast/custom`，条目表主要是 `rss/curated_index/webpage/email/custom`。这会导致前端和日报只看一个 type 时误判。

3. **索引页与单篇文章边界不硬**
   Anthropic Newsroom、BestBlogs 这类源应当是“索引条目 + 原站补抓”，不能直接当全文文章展示。

4. **重复调度噪声偏大**
   24 小时 7,823 次 all_duplicate，说明调度可用但效率不高。短期不是灾难，但会干扰“今天到底新抓到了什么”的判断。

### 优化方向

- 来源健康从“抓取是否成功”升级为五段漏斗：抓取、去重、正文、AI、日报覆盖。
- 每个来源明确 `source_type / collector_type / item_kind / content_strategy`。
- 对 `webpage_index / curated_index` 默认显示“索引摘要”，只有补抓成功才进入全文阅读。
- 用 Dibao 侧车做 5-10 个源的长期对照，归因是源问题还是信息中枢解析问题。

## 2.2 内容可信与正文解析模块

### 当前能力

- 已引入 `@mozilla/readability`、`dompurify`、`linkedom`、`chardet`。
- `items` 表已有 `readability_content / readability_status / readability_reason`。
- `reading-context.ts` 已经能区分全文、索引摘要、榜单摘要、网页快照等状态。
- 已有 golden sample 与 reading-context 测试。

### 主要问题

1. **readability 覆盖率偏低**
   1,439 / 19,275 的可读正文覆盖率无法支撑高质量阅读和日报。

2. **`content_ready` 容易制造假安全感**
   `content_status=ready` 可能只是 RSS 摘要、网页快照、榜单摘要，用户却会以为正文完整。

3. **HTML/Markdown 渲染仍不稳定**
   John D. Cook 这类技术长文暴露了代码块、Lean 片段、分隔线、列表格式的问题。原文需要更像阅读器，不是纯文本大段堆放。

4. **来源正文策略没有反控采集器**
   有些源适合 feed-only，有些必须 full readability，有些索引源要先解析 originalUrl。现在策略还没有完全变成来源级配置。

### 优化方向

- 统一内容状态：`全文可读 / RSS 摘要可读 / 索引摘要 / 榜单摘要 / 网页快照 / 原文待补抓 / 原文抓取失败`。
- RSS collector 补齐 Atom `summary`、RSS `description`、`content:encoded` 等字段优选逻辑。
- 保存双层内容：`content_html/readability_html` 用于阅读，`content_text/readability_text` 用于 AI。
- 对黄金样本建立强回归：John D. Cook、Simon Willison、Anthropic Newsroom、OpenAI News、BestBlogs、36kr。

## 2.3 AI 处理模块：评分、摘要、翻译、资产

### 当前能力

- 评分覆盖 16,568 条。
- 摘要覆盖 8,374 条。
- AI usage 日志完整，24 小时约 4,745 次调用。
- 已有 `item_reading_assets` 表和 `article-assets.ts`，但当前库内资产记录为 0。
- `translate-full` 接口已存在，并设计了“先补正文再翻译”的方向。

### 主要问题

1. **翻译覆盖极低且质量状态不可信**
   417 条翻译对于 19,275 条内容明显不足。更关键的是，长文短译文会显示成“已翻译”，用户会认为系统坏了。

2. **翻译按钮反馈不够明确**
   用户多次反馈点击无效、不知道为何没翻译。接口应该返回阶段：正文补抓、翻译、模型失败、跳过原因。

3. **摘要、中文改写、翻译边界不清**
   当前页面上“中文改写”和“摘要”经常看起来一样。产品上应该明确：
   - 摘要：帮助快速判断要不要读。
   - 中文翻译：忠实翻译原文。
   - 中文改写：把英文长文重写成中文文章风格，可选低频资产。

4. **Article Agent 资产没有真实沉淀**
   表存在但当前无记录。说明能力还没有进入用户主链路。

### 优化方向

- 翻译状态增加完整性字段：sourceLength、translatedLength、chunkCount、complete、reason。
- 主阅读标签只保留：摘要、原文、翻译。
- 改写、问文章、知识、转写放入右侧“资产/工具”抽屉，不再占主标签。
- Article Agent 先做固定 5 问并保存资产：总结要点、证据清单、前提拆解、行动建议、选题角度。

## 2.4 Feed 阅读台

### 当前能力

- 三栏结构已经存在：来源栏、文章队列、阅读详情。
- `feed-layout.ts` 已经有主标签排序、次级标签、翻译动作和阅读提示逻辑。
- 页面能展示内容状态、阅读资产、诊断、修复动作。

### 主要问题

1. **阅读首屏被系统信息挤占**
   顶部标题、搜索、到期源提醒、状态条、资产条、工具条、诊断条过多。正文不是绝对主角。

2. **按钮和状态过度暴露**
   用户不需要在阅读前看到所有系统动作。补抓、重跑、评分拆解、人类反馈、日报解释都应该默认收起。

3. **右下角悬浮控件仍可能遮挡正文**
   多次截图显示底部和右下角存在遮挡风险。长文阅读必须有安全区。

4. **列表卡片还不够像“阅读队列”**
   应只常驻标题、来源、时间、两行摘要、评分/等级/内容状态、缩略图。raw enum 和处理状态不应常驻。

### 优化方向

- 顶部全局搜索与筛选压缩成一行，过期源提醒默认收起为窄条。
- 阅读详情首屏只保留：来源、标题、时间、评分/等级、打开原文、内容状态一行。
- 正文容器居中，宽 760-860px，字号 17px，行高 1.8-1.9。
- 工具菜单仿 Folo：复制链接、打开原文、收藏、已读、补抓、翻译、重跑 AI 全部进菜单。
- 诊断信息只在右侧抽屉或折叠区显示。

## 2.5 日报模块

### 当前能力

- `daily-report.ts` 已有清洗、决策、研究、阅读、final 多阶段。
- `dailyReportQueue` 和生成进度已经接入。
- `/daily` 页面已有工作台、候选、报告、运行分析等能力。
- `Daily.tsx` 已有 `moduleSections / coverageItems / priorityArticles` 的展示代码。

### 主要问题

1. **正式日报数据结构没有稳定落库**
   最新多条日报中 `coverageItems / priorityArticles / moduleSections` 为 0。前端有展示，后端也有构建函数，但正式 payload 里没稳定保存。

2. **日报不像信息雷达**
   用户需要的是“今天发生了什么、趋势是什么、哪些文章重要、下一步怎么读”。现在仍容易变成候选池摘要或浅层结论。

3. **日报口径混乱**
   工作台容易混合候选预览、正式日报快照、日报 Agent 用量和全系统 24h 用量。

4. **标题和 Markdown 阅读性不足**
   正式日报需要像 AIGC Weekly 那样有目录、模块标题、重点条目、链接和编辑判断，而不是长段普通文本。

### 优化方向

- 日报结构固定为：
  1. 今日封面判断
  2. 信息雷达总览
  3. 今日精选
  4. 模块日报
  5. 更多动态
  6. 重点研究/深读
  7. 阅读顺序
  8. 下一步行动
  9. 附录：全池摘要索引
- 模块日报按主题拆分：模型与实验室、Agent/产品、基础设施与算力、应用商业化、政策安全、深读博客、国内产业动态。
- 每个模块必须有 400-900 字编辑型小节，而不是仅列文章。
- 默认引用 35-60 篇候选，其中精选深写 8-12 篇。
- 工作台必须显示生成进度、当前阶段、失败阶段、完成入口。

## 2.6 Sources 健康治理中心

### 当前能力

- `source-health.ts` 已有不少测试和阶段诊断能力。
- `/sources` 页面已有健康筛选和来源配置。
- source 表已经有 health_score、last_success、outcome、trust/noise/growth 等字段。

### 主要问题

1. **健康分没有覆盖全链路**
   RSS 平均健康分 96，但不代表正文、翻译、日报覆盖健康。

2. **来源治理还没有反控 Feed 和日报**
   低质量源、索引摘要源、翻译失败源应影响推荐、日报采样和修复优先级。

3. **来源页过重**
   `sources/page.tsx` 2305 行，列表、表单、健康、动作、面板耦合。

### 优化方向

- 健康分拆成 5 段：抓取、正文、展示、AI、日报。
- 增加来源级内容策略：仅 RSS、智能补抓、强制全文、禁用全文。
- Sources 详情抽屉显示“为什么”和“下一步动作”，不暴露 raw enum。
- Feed 和 Daily 引入来源健康权重：健康差的源不直接进精选，但可进入待复核。

## 2.7 外部源与 Reader Lab

### 当前能力

- Dibao 侧车已运行。
- `ReaderLab` 页面、Dibao OPML/status/compare 相关代码已存在。
- BestBlogs、email ingest、webpage_index 已经接入一部分。

### 主要问题

1. **Dibao 对照还没有变成持续验收机制**
   现在它更多是“能打开的 sidecar”，还没有固定对照报告和黄金样本矩阵。

2. **BestBlogs 原站补抓不稳定**

3. **邮箱入口应保持私密边界**
   邮箱内容默认不应进入公开日报主线，除非用户明确标记或评分足够高。

### 优化方向

- 每周或每次大改后跑 Dibao vs InfoHub 对照：同源 7 个源，每源 5 篇。
- Reader Lab 只做质量对照和借鉴，不作为主数据源。
- BestBlogs/邮箱/网页监控统一进入来源健康模型。

## 2.8 AI 用量与模型治理

### 当前能力

- `ai_usage_logs` 已经很完整。
- 24 小时有 4,745 次调用，token 约 241 万。
- `/ai-usage` 页面已存在未跟踪文件。

### 主要问题

1. **用量大，但用户主路径不该看到太多模型细节**
   模型、token、错误热点应该在模型用量页，而不是 Feed 阅读首屏。

2. **日报 Agent 用量和全系统用量要分开**
   工作台截图中的不可信感，本质就是口径混杂。

3. **错误日志很多，但可恢复策略不够用户化**
   错误应转成“摘要失败、翻译失败、评分熔断、模型配置缺失”等用户动作。

### 优化方向

- AI Usage 独立成治理页。
- Daily Workbench 只显示当前日期日报 Agent 用量。
- Feed 只显示“摘要可用/翻译可用/可重试”，不显示模型内部细节。

## 3. 当前最大风险排序

### P0 风险：必须先修

1. **正文可信层不足**
   影响 Feed、翻译、日报、评分解释、来源健康。

2. **Feed 主路径噪音过大**
   用户打开文章不能直接读，信任会持续下降。

3. **翻译动作无反馈或不完整**
   这是很强的“系统坏了”信号。

4. **日报结构字段没有稳定落库**
   前端设计再多，payload 不稳定也无法形成产品。

5. **当前大 diff 未收口**
   工作树太宽，继续开发会增加不可控回归。

### P1 风险：影响日常可用

1. 来源健康不能反控推荐和日报。
2. Article Agent 资产没有进入真实链路。
3. Daily / Feed / Sources 文件过大，维护风险高。
4. Dibao 对照还没有转成验收制度。

### P2 风险：影响长期产品化

1. embedding/个性化推荐还没有形成稳定策略。
2. 外部源接入多，但隐私和日报边界需要更硬。
3. AI 成本和失败率需要长期仪表盘治理。

## 阶段 1：内容可信层 P0 修复

## 5. 推荐执行顺序

当前最合理的顺序：

1. **先修 Feed 翻译和正文可信动作**
   这是用户最直接感知到的“系统有没有反应”。

2. **再收 Feed 主界面噪音**
   把主标签收成摘要/原文/翻译，其他全部放右侧工具。

3. **然后修日报 payload 落库和模块化生成**
   不先修 payload，前端日报页面继续会空。

4. **再让 Sources 健康反控 Feed 和日报**
   否则健康中心只是展示，不解决数据质量。

5. **最后整理大 diff 和提交**
   现在不能急着提交，必须先把主链路跑顺。

## 6. 最小可交付版本定义

信息中枢 V3 达到“我敢日常使用”的最低标准：

- Feed：
  - 10 个黄金样本中 8 个正文格式正确。
  - 翻译按钮有明确反馈。
  - 主阅读区不被诊断信息淹没。

- Sources：
  - 每个源能看懂抓取、正文、AI、日报覆盖状态。
  - 高质量源与低质量源不混评。

- Daily：
  - 最新日报有模块章节、重点文章、全池索引。
  - 至少引用 35 篇以上文章，且有编辑判断。
  - 日期切换、生成进度、失败阶段明确。

- AI Usage：
  - 日报用量和全系统用量分开。
  - 错误热点能定位到摘要、翻译、评分、日报 Agent。

- 工程：
  - 后端测试和前端构建通过。
  - Docker 页面验收通过。
  - 大 diff 被拆成可读提交，不混入无关记忆文件。
