# 信息中枢 V3 当前重点模块审计与优化计划

## 1. 结论先行

信息中枢 V3 当前的真实问题，不是“功能少”，而是“主链路太宽、真相层不硬、阅读层不收、日报层不深”。

今天按仓库真实状态复核后，这个判断没有变，但证据更明确了：

- 路由和页面已经很多，说明项目不是“功能缺失”，而是“能力分层失控”
- 数据合同已经开始成形，说明不是没底座，而是底座没有完全进入主路径
- 构建可以过，说明不是“跑不起来”，而是“用户看到的主体验还不可信”

从当前仓库状态看，它已经不是一个原型项目：

- 前端已经有 **16 个页面**
- 后端已经有 **25 个 API 路由文件**
- 运行态已经分成 **3 个核心服务**：`hub-engine`、`audio-service`、`scrapling-service`
- 后端已有 **80+ 个测试文件**
- `qa/` 下已有 **207 个测试/脚本文件**

这说明项目能力面已经足够大。现在真正要做的，不是继续扩页面，而是把最关键的 4 条主线收口：

1. **内容是不是可信**
2. **阅读是不是顺手**
3. **日报是不是像真正的编辑型产物**
4. **来源治理能不能反向控制 Feed 和日报**

如果这 4 条主线不收，继续扩输入、扩页面、扩 AI 能力，只会把复杂度继续堆高。

**这份文档现在应视为当前阶段的项目级审计真源。**
如果后续还要继续盘点重点模块、问题和优化顺序，优先回到这份文档更新，而不是继续新增同主题平行文档。

## 1.1 今天的代码级验证

本轮只做了“项目级审计”所需的最小验证，不做新的大改：

- `services/hub-engine npm run build`：通过
- `apps/web npm run build`：通过
- `services/hub-engine npm test`：跑到大量 collector / content / source-health / daily-report / article-assets / readability / workflow 测试持续通过，说明测试面已经很广；但整套执行时间与稳定性仍需继续收口，不能把“测试很多”等同于“主链路足够稳”

换句话说，当前项目的真实状态可以概括成一句话：

> **不是做不出功能，而是功能层已经长得太快，必须先做一次边界治理和主链路收口。**

换句话说，当前问题不是“代码完全不可用”，而是：

> **内部能力已经长出来了，但用户主路径仍没有把这些能力组织成可信产品。**

## 1.1.2 本轮审计的证据口径

本轮分析主要来自四类证据：

1. **仓库结构**
   - 前端页面、后端 routes、collector、outputs、lib、QA 脚本已经覆盖完整产品面。
   - 这证明当前不是“缺系统”，而是“系统能力未被组织成低噪声主路径”。

2. **当前 diff**
   - 变更集中在 Feed、Sources、Daily、items route、daily report、content extractor、reading context、source health。
   - 这说明当前最活跃的确是阅读可信、日报和治理三条线。

3. **文件规模**
   - 多个核心文件超过 1000-3000 行，已经影响迭代安全。
   - 大文件需要逐步按职责拆出，而不是继续在一个页面或 route 里补逻辑。

4. **用户反馈反复命中的问题**
   - 原文层不可信。
   - 翻译动作无反馈或不完整。
   - Feed 首屏被按钮、提示、诊断占据。
   - 日报不像信息雷达，证据密度和编辑判断不足。

这些证据共同指向同一个结论：

> **当前最优路线不是迁移整套第三方项目，也不是继续扩功能，而是先把“内容真相层、阅读主路径、日报编辑层、来源反控层”四条主线做硬。**

## 1.2.2 当前重点模块逐项判断

### 1. 采集与来源层

现状：

- RSS / RSSHub 是主体，当前 706 个 active 源中 RSS 类占绝大多数。
- `webpage_index`、`curated_index`、`email` 已经接入，但还不是主力。
- Dibao 侧车已经跑起来，可以做同源质量对照。

主要问题：

- 来源类型和条目类型仍容易混看：RSS 正文、网页快照、索引条目、榜单摘要在 Feed 中仍可能被用户当成同一类内容。
- Anthropic Newsroom、BestBlogs 这类索引源已经开始拆条目，但“原站正文补抓成功率”和“失败时的降级展示”仍不够稳。
- 来源健康尚未真正反向控制 Feed 推荐、日报候选和翻译策略。

优化方向：

- 每个来源必须明确 `sourceType + collectorType + sourceKind + contentStrategy`。
- 对索引源和榜单源强制区分“摘要可读”和“全文可读”。
- 用 Dibao 侧车作为抓取和阅读效果基准，而不是直接替换主系统。

### 2. 正文可信层

现状：

- 已引入 `@mozilla/readability`、`DOMPurify`、`linkedom`、`chardet`。
- 已有 `readabilityContent/readabilityStatus/readabilityReason` 字段。
- 已有 `contentReadiness/contentEvidence/translationCompleteness` 类型合同。

主要问题：

- 数据库实际 `readability_content` 覆盖率低，特别是高价值博客源覆盖不足。
- 一些条目仍会把短 `content/snippet` 当成可读正文，导致摘要和翻译基于错误材料。
- HTML/Markdown 保真仍不稳定，代码块、列表、公式、链接、图片在长文中容易失真。

优化方向：

- 对黄金样本源建立专项补抓策略：John D. Cook、Simon Willison、Daring Fireball、Anthropic、OpenAI、BestBlogs、TechCrunch、The Verge、36kr。
- 正文层必须统一成 `readabilityContent -> content -> snippet -> title`，且每一级都要标注可信等级。
- 所有摘要、翻译、问文章、日报引用都必须记录 basis，避免“看似 AI 结果，实际基于片段”。

### 3. AI 处理层

现状：

- 评分调用量大，近 7 天 `feed_scoring_skill` 和 `feed_scoring` 是主力场景。
- 摘要和翻译都有能力，`article_asset` 方向已经开始接入。
- AI 用量页面已经存在。

主要问题：

- AI 错误日志量很大，但用户主路径里看不到“失败在哪个阶段、能不能修、修了有没有效果”。
- 翻译覆盖太低，且之前已出现“长文 8000 字、译文 400 字却显示已完成”的问题。
- 中文改写、摘要、翻译、问文章之间的边界仍不够清楚。

优化方向：

- 翻译改为 job 化：补正文、分块翻译、合并、质量检查、失败阶段返回。
- 摘要和中文改写明确分工：摘要是事实压缩；中文改写是面向中文读者的重述/导读，不能复用同一段。
- Article Agent 的输出作为资产保存，不再散落在页面状态里。

### 4. Feed 阅读台

现状：

- 三栏结构已经成立：来源栏、文章队列、阅读详情。
- 文章详情已经有主 tab、扩展内容、工具诊断、阅读资产。
- 前端有 `feed-layout.test.ts` 约束部分阅读逻辑。

主要问题：

- 阅读详情首屏仍被状态条、提示、工具和诊断占据。
- 主 tab 仍有过多概念露出，用户实际只需要先看到：摘要、原文、翻译。
- 右下角悬浮组件和工具按钮仍可能遮挡长文阅读。
- sourceId 作为列表过滤上下文，仍可能让用户误以为文章来源错乱。

优化方向：

- Feed 详情首屏只保留“标题、来源、时间、打开原文、摘要/原文/翻译”。
- 其他内容全部进入右侧“资产与工具”抽屉：中文改写、问文章、转写、知识、日报解释、评分拆解、人类反馈、阶段修复。
- 文章正文采用阅读器排版：760-860px、17px、1.8-1.9 行高、代码/表格/图片特殊处理。
- 建立黄金样本 Playwright 检查：每次改 Feed 都抽测固定 10 条。

### 5. 日报工作流与正式日报

现状：

- `/daily/workbench`、`/daily/candidates`、`/daily/reports/latest`、`/daily/workflows` 已存在。
- 异步日报 job 和 generation progress 已经接上。
- 日报模块化、趋势、重点文章、覆盖索引已经有初步代码与 payload 概念。

主要问题：

- `/reports` 仍只是重定向到 `/daily/workbench`，说明正式日报入口边界不硬。
- 日报内容仍偏浅，缺少“信息雷达”级别的编辑判断、模块叙事和证据密度。
- 右侧目录不够稳定，滚动后不承担真正导航作用。
- 候选池、正式日报、运行分析、AI 用量的 KPI 仍容易混口径。

优化方向：

- 日报正式页单独产品化，不再让 `/reports` 指向工作台。
- 正文结构固定为：今日封面判断、目录、信息雷达总览、今日精选、模块日报、更多动态、深读、阅读顺序、下一步行动、全池摘要索引。
- 模块日报不再是卡片列表，每个模块要有 400-900 字编辑小节和 3-8 个链接。
- 生成链路分成 `editorialDigest -> moduleNarratives -> finalEditor -> deterministic appendix`，不要让一个 final prompt 吞掉所有材料。

### 6. Sources 健康治理中心

现状：

- `source-health.ts` 已有五段诊断：fetch、content、display、ai、report。
- Sources 页面也已经加入健康筛选和详情抽屉方向。

主要问题：

- 来源健康还没有变成“控制系统”，更多是“展示系统”。
- 发现源质量差后，Feed 和日报不一定自动降低权重或调整补抓策略。
- 来源级正文策略仍需要产品化：仅 RSS、智能补抓、强制全文、禁用全文。

优化方向：

- 来源健康输出直接参与 Feed 推荐权重和日报候选策略。
- 来源页给出来源级动作：补抓正文、重跑摘要、重跑翻译、暂停入报、改正文策略。
- 对低质量源不自动删除，但要明显标为“待观察/正文差/AI 卡住/影响日报”。

### 7. 外部源与 Reader Lab

现状：

- BestBlogs、邮箱、Reader Lab、Dibao OPML bridge 都已经接上。
- Dibao 侧车正在运行。

主要问题：

- BestBlogs Daily Brief 仍大量没有 `originalUrl` 或没有原站正文补抓。
- 邮箱源默认私密策略、日报入选策略和阅读展示还需要更硬边界。
- Reader Lab 还只是入口和对照方向，尚未沉淀正式质量报告流程。

优化方向：

- Reader Lab 的价值不是替代主系统，而是做质量基准：同源抓取、正文长度、可读性、格式保真、排序体验。
- BestBlogs 必须完成“榜单摘要可读、原站链接可补、补抓失败可解释”的闭环。
- 邮箱源只进个人阅读资产和覆盖索引，默认不进入公开日报主线。

### 8. 模型治理与 AI Usage

现状：

- AI Usage 页面已经存在。
- 后端有 `admin-ai-usage`、`ai_usage_logs`，可统计场景、模型、token、错误。

主要问题：

- 当前日志中 error 量大，说明模型稳定性不是边缘问题。
- 工作台曾经把全系统 24h 用量和日报 Agent 用量混在一起，容易让用户误解。

优化方向：

- AI Usage 继续做管理后台，不进入阅读主路径。
- Daily Workbench 只展示当前日期日报 Agent 用量，全系统用量放到模型用量总览。
- 高频错误要聚合成“可行动项”：模型配置问题、提示词质量问题、供应商 500、摘要中文化失败、翻译截断。

### 9. 音频、播客、导出与知识库

现状：

- 音频服务、转写 worker、PodcastHub、Export、Knowledge route 都存在。
- 这部分不是当前最痛主线。

主要问题：

- 如果继续同时优化，会分散当前最关键的阅读和日报收口。

优化方向：

- 短期只保持健康和不破坏。
- 等 Feed 与日报主链路稳定后，再把音频长文、播客摘要和知识库资产纳入同一阅读资产模型。

## 1.2.1 现在最该盯住的 4 条主线

虽然仓库表面上已经有十多个页面，但当前真正决定项目是否“可信可用”的，不是页面数，而是下面 4 条主线：

1. **正文可信层**
   - 决定用户看到的到底是全文、索引摘要、榜单摘要还是网页快照
   - 这是 Feed、翻译、摘要、日报共同底座

2. **Feed 阅读台**
   - 决定用户能不能稳定、连续、低噪声地读内容
   - 这是产品日常使用频率最高的面

3. **日报编辑层**
   - 决定系统有没有“信息雷达”价值，而不只是候选拼接
   - 当前内容偏浅、结构偏机器，是最核心的产品短板之一

4. **Sources 反控层**
   - 决定来源质量问题能不能反向影响 Feed 推荐、正文策略和日报覆盖
   - 如果这层不成立，系统就会持续把坏输入包装成复杂 UI

这个总表对应的执行原则很简单：

1. 先修 **正文可信层**
2. 再修 **Feed 阅读台**
3. 再把 **日报** 从流程页升级成编辑型产物
4. 最后让 **Sources 健康** 真正反向控制内容流向

## 2. 当前项目的真实规模与结构热点

## 2.1 服务与产品面

当前产品已经包含这些主要面：

- 阅读主入口：`/feed`
- 来源治理：`/sources`
- 日报工作台与正式日报：`/daily/*`、`/reports`
- 成长仪表盘：`/insights`

- 音频与播客：`/audio`、`/podcast`
- 模型治理：`/settings`、`/ai-usage`
- 外部对照：`/reader-lab`
- 导出：`/export`

这已经不是单一产品，而是一个“阅读器 + 情报加工台 + 管理后台 + 对照实验室”的复合系统。

问题在于：**这些能力都被放在同一个产品壳里，但主次关系还没有彻底分清。**

## 2.3 当前已经具备的好底座

这部分必须说清楚，否则后面的计划会误判成“推倒重来”。

当前仓库里，已经有几类值得保留并继续放大的基础能力：

1. **正文可信合同已经开始成形**
   - `originalUrl / curationUrl / curationSource / readabilityContent / readabilityStatus`
   - 说明系统已经知道“榜单摘要”和“原站正文”不是一回事

2. **阅读资产层已经有正式数据表**
   - `hub.item_reading_assets`
   - 说明摘要、翻译、问文章、改写并不一定要继续做成一次性状态

3. **日报生成进度已经有独立进度层**
   - `daily-generation-progress`
   - 说明“生成日报没有反馈”这个老问题，已经有了正确的技术支点

4. **来源健康中心已经不是纯想法**
   - `source-health.ts`
   - 说明系统已经能从“只展示来源列表”进入“来源级诊断”

5. **Reader Lab / Dibao 对照层已经接上**
   - 说明你现在不是只能盲修，而是可以做同源对照，区分“源问题”和“本系统问题”

所以当前策略不该是“迁移一切”，而是：

> **保留已长出来的底层合同，重做用户主路径的表达和行为。**

## 2.4 与 Dibao / QMReader 对照后的取舍

当前产品路径已经足够清楚，不需要“整套迁移”。
真正值得吸收的是两套不同能力：

1. **学 Dibao 的“读前排序治理”**
   - 推荐与最新双入口
   - 正文按源策略治理
   - 来源健康与排序解释可见
   - 任务进度和降级逻辑明确

2. **学 QMReader 的“读中沉浸 + 读后资产”**
   - 三栏阅读工作台
   - 阅读内容优先于系统诊断
   - 翻译、重写、问文章沉淀为阅读资产
   - 文章级 Agent 成为阅读辅助，而不是控制台功能

不建议照搬的部分也要明确：

- 不建议把 Dibao 的“只做 RSS 内推荐”直接搬进来
- 不建议把 QMReader 的“默认公开资产”直接搬进来
- 不建议为了 UI 好看就再扩一层壳，而不先修正文可信和日报证据密度

所以这条产品路线现在可以定成一句话：

> **上游学 Dibao 的排序与治理，下游学 QMReader 的阅读与资产，中间继续保留信息中枢自己的日报、来源健康和外部源能力。**

## 4. 当前存在的结构性问题

## 4.1 P0 问题：不解决会持续损伤信任

1. **内容真相层不彻底统一**
   - 用户分不清全文、片段、索引、榜单、快照
2. **Feed 阅读主路径仍太吵**
   - 正文不是绝对主角
3. **翻译与补抓动作不够闭环**
   - 用户点翻译时，不该自己猜“到底是没原文、无需翻译、还是模型失败”
4. **日报成稿深度不够**
   - 当前更像流程结果，不像成熟的编辑型日报

## 4.2 P1 问题：会持续拖慢产品体验

5. **阅读资产边界不清**
   - 摘要、改写、翻译、问文章之间重复感强
6. **Sources 诊断还未成为强约束**
   - 来源质量没有足够决定排序和入报行为
7. **项目职责过宽**
   - 阅读器、管理台、日报台、音频台都在一个壳里，但主次没彻底分清

## 4.3 P2 问题：会影响后续增长但不必先修

8. **外部源接入还停在桥接期**
9. **长期偏好、推荐解释、专题沉淀还不够强**
10. **Reader Lab 仍偏验证工具，而不是稳定的对照体系**

## 4.4 工程治理问题

除了产品问题，还有几个明显的工程问题，会持续拖慢后续迭代：

1. **大文件过多**
   - `feed/page.tsx`、`sources/page.tsx`、`items.ts`、`daily-report.ts` 都已经过重
   - 结果是任何一处小改都容易牵出一整页副作用

2. **文档与代码解释权漂移**
   - `docs/` 已经有很多轮计划、审计、路线图
   - 当前最大风险不是“没有文档”，而是“文档太多，谁是当前真源不够明确”

3. **脏 diff 很大**
   - 当前仓库已有大量未提交修改和新增文件
   - 这不一定是坏事，但说明后续必须按模块收口，不能再继续把不同主题的改动混在一起

4. **测试覆盖很广，但用户黄金路径回归仍不够聚焦**
   - 现在测试多，说明底层合同越来越完整
   - 但仍需要固定一组真实来源的“黄金样本矩阵”，持续验证：
     - 原文是不是对
     - 翻译是不是完整
     - 摘要是不是基于对的正文
     - 日报有没有引用进去

## 5. 优化计划

## 5.1 Phase A：可信底座收口

**目标**

先让系统“说真话”。

**重点任务**

1. 统一 `contentReadiness / readabilityStatus / originalTextStatus`
2. 让摘要、翻译、日报都显式绑定内容依据层
3. 统一翻译动作：
   - 有全文：一键翻译全文
   - 只有摘要但有原站：补抓原文并翻译
   - 没原站或抓取失败：明确失败原因与打开原文
4. 把 `webpage / webpage_index / curated_index / monitor` 的阅读合同彻底做实

**完成标准**

- 用户能明确知道自己当前看到的是什么内容层
- 翻译按钮不再静默失效
- 索引条目、榜单条目、快照条目不会再伪装成全文

## 5.2 Phase B：Feed 阅读产品化

**目标**

让 Feed 真正像长期阅读器，而不是系统控制台。

**重点任务**

1. 详情首屏只保留：
   - 来源
   - 标题
   - 时间
   - 评分/等级
   - 打开原文
   - 主标签 `摘要 / 原文 / 翻译`
2. 把 `改写 / 问文章 / 转写 / 知识 / 诊断 / 日报解释 / 阶段修复` 统一后移
3. 压缩顶部控制区和状态区
4. 把正文容器做成真正长文阅读器：
   - 宽度稳定
   - 留白更强
   - 字号与行高统一
   - 代码、列表、引用、图片正常阅读

**完成标准**

- 详情页默认只围绕“读”
- 正文成为主视觉
- 低频信息默认不打断阅读

## 5.3 Phase C：日报雷达产品化

**目标**

把日报从“流程产物”升级为“每日信息雷达”。

**重点任务**

1. 在候选池和 final 生成之间建立 `editorialDigest`
2. 稳定日报结构：
   - 今日封面判断
   - 信息雷达总览
   - 今日精选
   - 模块日报
   - 更多动态
   - 重点研究/深读
   - 阅读顺序
   - 下一步行动
   - 全池摘要索引
3. 把“重点文章、模块引用、更多动态、附录索引”明确分层
4. 把正式日报页的排版、目录、粘性导航、Markdown 结构做成熟

**完成标准**

- 日报不再只是机器摘要堆叠
- 有趋势判断、有模块叙事、有重点文章、有明确阅读建议
- 页面阅读体验达到可持续消费标准

## 5.4 Phase D：治理反控与外部源收口

**目标**

让来源治理真正控制内容流向，而不是只做诊断展示。

**重点任务**

1. 让 Sources 健康直接影响：
   - Feed 推荐
   - 默认正文策略
   - 日报入选与降权
2. 给外部源统一 provenance 展示
3. 用 Reader Lab 建立固定对照样本与月度回归

**完成标准**

- 来源质量不再只是“看得到”，而是“会改系统行为”
- 外部源不再像补丁接入

## 5.5 建议执行顺序

后续不要再按页面零散修。建议固定成 4 条并行但有先后关系的主线：

### 第一顺位：正文可信层

先解决“我现在看到的到底是不是原文”。

先做：

### 第二顺位：Feed 阅读台

### 2026-06-18 补充执行记录：日报候选覆盖

已修一个直接影响“日报雷达”厚度的默认配置问题：

- 默认工作流 `topN` 从 18 调整为 42。
- 默认 `perSourceLimit` 从 4 调整为 8。
- 新增回归测试 `keeps enough default high-score candidates for radar-style daily reports`，要求默认候选能保留 35+ 高分条目，并覆盖 5+ 分类、8+ 来源。

这个修复只扩大进入日报生成层的证据池，不等于放宽噪声准入；既有网页快照排除、金融行情噪声过滤、聚合源降权、未评分 Claude 热点兜底测试仍保持通过。

### 2026-06-18 补充执行记录：空日报兜底策略

只读核查本地数据库发现 2026-06-18 与 2026-06-17 的 full 日报都不是没有数据，而是：

- `scopeMatched` 分别有 65 / 71 条。
- `fallbackScoredCandidates` 都有 72 条。
- `finalCandidates` 却都是 0。

根因是旧策略把所有低置信兜底评分候选都排除出最终候选；当没有高分精选、可信复核或最新兜底时，系统直接生成空候选诊断日报。

已修复为：

- 单条低置信兜底仍不生成正式日报，避免把孤立弱信号包装成结论。
- 但当低置信复核池达到规模（默认至少 10 条，或达到 `topN` 半数阈值）且没有其它候选时，生成 `review` 口径日报。
- 新增回归测试 `uses substantial fallback-scored review pool instead of producing an empty daily report`。

这让“AI 评分链路不稳”不再直接导致日报空白；页面仍应把这类日报标成复核口径，而不是高分精选口径。

## 6. 我建议你后面只盯这 4 个指标

如果后续每轮都看很多散点问题，项目会继续失焦。建议统一盯这 4 个判断指标：

1. **正文可信率**
   - 当前读到的是不是我以为的正文
2. **阅读打断率**
   - 阅读首屏有没有被状态、按钮、诊断打断
3. **日报证据密度**
   - 每篇日报到底引用了多少有效文章、多少清晰证据
4. **来源反控率**
   - 低质量来源是否真的被降权、隔离或只进索引层

这 4 个指标一旦稳住，后续排序、资产、外部源、专题系统都会顺着长出来。

## 7. 最后判断

信息中枢 V3 现在已经过了“证明能做”的阶段，进入了“证明值得长期用”的阶段。

所以后面的原则应该固定：

- 不继续靠堆页面解决问题
- 不继续靠堆诊断解释产品
- 不继续把所有能力都放在主阅读链路

后续真正要做的是：

> **把真相层做硬，把阅读层做轻，把日报层做深，把治理层做强。**

这四件事做完，项目才会从“功能很多的系统”变成“真正可信可用的产品”。
