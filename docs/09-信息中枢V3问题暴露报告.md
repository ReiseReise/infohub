# 信息中枢 V3 问题暴露报告

## 0. 结论先行

这次暴露出来的问题，不是单个按钮、单个样式或单个页面的 bug，而是四层同时出现了断点：

1. **数据管线一致性断点**：同一条消息的过滤状态、过滤池归属、日报可用性之间没有保持一致，导致“有新增数据，但日报和成长仪表盘为空”。
2. **信息曝光层级断点**：Feed、成长仪表盘、过滤池都在展示很多系统能力，但主流程不够顺，用户不知道下一步该看哪里、点哪里、怎么加载更多。
3. **治理工作流断点**：信源分级、人工反馈、个人层/全局层、质量过滤这些概念都出现了，但没有形成可管理、可验证、可解释的闭环。
4. **中文化与界面密度断点**：页面里仍有大量英文/工程词，卡片信息过密，部分左右栏滚动耦合，造成“功能很全，但不好用”的整体感受。

优先级建议：**先修数据闭环，再修主阅读流，再修信源治理，最后统一中文化和样式密度**。否则继续堆功能，只会让系统更大、更难判断哪里坏了。

## 1. 排查口径

- 排查时间：2026-05-10。
- 排查方式：只读检查本地运行态、前端页面、接口代码、后端日报/过滤/优先级逻辑和本地验收库快照。
- 本报告不做代码修复，不改数据库，不导入新信源。
- 为避免在共享工作台写入敏感实体，本报告只使用“验收账号”“某高未读资讯源”等泛称，不写具体账号和不必要的外部主体名。

## 2. P0 问题：主流程数据闭环断裂

### P0-1 成长仪表盘和日报为空

**现象**

- 点击“生成日报”后，日报结构存在，但核心内容基本为空。
- 成长仪表盘里的认知、商业、表达、输出等模块没有形成有效内容。
- 用户体感是“系统抓了很多东西，但真正给我的洞察是空的”。

**只读证据**

- 本地验收库快照显示：最近 7 天消息总量有 385 条，今日新增有 48 条，但可进入成长仪表盘主视图的最近 7 天主流内容为 0。
- 今日消息中，有 43 条同时呈现 `is_filtered=true` 与 `filter_bucket=main`，另有 5 条在 `filter_bucket=filtered`。
- 最近生成的日报记录里，`item_count` 有值，但 `top_items` 和 `high_score_items` 长度为 0，并进入 fallback 状态。

**判断**

日报和仪表盘不是“没有数据”，而是“有数据，但状态字段让它们被排除在主流程之外”。这比单纯空状态更危险，因为用户会误以为系统没抓到内容，实际是内容在管线中被路由掉了。

**建议修复方向**

- 明确一个唯一可信的内容路由字段：建议以 `filter_bucket` 作为主归属，`is_filtered` 作为派生或同步字段。
- 日报生成前先给出数据漏斗：今日新增、可入报、已过滤、待复核、失败项。
- 当可入报内容为 0 时，不生成“假空日报”，而是生成“空日报诊断”：说明为什么空、哪些规则过滤最多、下一步该调整什么。

### P0-2 过滤字段不一致，导致内容两边都看不到

**现象**

- Feed 里看不到一部分内容。
- 过滤池里也看不到一部分应该被过滤的内容。
- 结果是消息既不像“主内容”，也不像“可复核的过滤内容”。

**只读证据**

- 后端优先级重算逻辑会把低分内容标记为 `is_filtered=true`，但没有同步把 `filter_bucket` 改为 `filtered`。
- 初始入库逻辑和后续重算逻辑对过滤字段的处理口径不同。

**判断**

这是本轮最核心的数据一致性问题。它会连锁影响 Feed、过滤池、日报、成长仪表盘、精选命中率统计和用户对系统可信度的判断。

**建议修复方向**

- 所有过滤入口统一调用同一段“路由状态写入”逻辑。
- 建立不变量：`is_filtered=true` 时，必须能在过滤池或待复核池找到；`filter_bucket=main` 时，必须能解释为什么仍可进入主流程。
- 增加一次性数据回补脚本，但执行前必须先 dry-run 输出影响行数。

### P0-3 过滤策略和人工反馈缺少生效证据

**现象**

- 页面里有过滤策略、个人层、全局层、反馈等概念，但用户看不到“它们到底有没有生效”。
- 个人层和全局层看起来几乎没有区别。
- 质量过滤相关的 AI 场景在界面上被提及，但当前没有形成真实闭环。

**只读证据**

- 验收账号下，人工反馈记录为 0。
- 偏好画像记录为 0。
- 质量检查记录为 0。
- 质量过滤 AI 场景未启用；页面也提示仍只保留硬规则过滤，不能产出 AI 质检解释。

**判断**

现在的“反馈净化”更像界面概念，还不是可被用户感知的产品能力。只要用户点了反馈后看不到反馈次数、画像更新时间、影响了哪些规则/分数，就会认为这是假的。

**建议修复方向**

- 过滤策略页必须显示三类状态：硬规则是否启用、AI 质检是否启用、人工反馈是否已进入画像。
- 个人层和全局层要有可见差异：个人层展示“我的偏好画像、我的覆盖规则、我的反馈影响”；全局层展示“系统默认规则、组织级阈值、公共黑白名单”。
- 每条反馈至少要能回看：反馈时间、反馈类型、影响对象、是否已参与下一次重算。

## 3. P1 问题：页面主流程和信息层级不顺

### P1-1 成长模块缺少可解释的数据映射

**现象**

- 认知、商业、表达、输出等模块看起来像四个重要能力区，但当前没有稳定内容进入。
- 用户无法判断这些模块是“没数据”“规则没配好”还是“功能还没做完”。

**只读证据**

- 本地验收源和消息的成长轴大量集中在“认知升级”。
- 其他轴没有看到明确、稳定的数据入口。
- 成长仪表盘条目点击后直接打开原文，而不是进入站内详情。

**建议修复方向**

- 给成长轴建立明确映射规则：信源默认轴、内容分类轴、人工修正轴的优先级要固定。
- 轴卡片必须显示“为什么归到这里”：例如命中的分类、信源层级、评分维度。
- 条目点击优先进入站内详情页，原文跳转作为二级动作。

### P1-2 Feed 的信源栏和加载方式让用户误判

**现象**

- Feed 上方/侧边把不同信源单独列出，但信源太多且没有展示全。
- 某高未读资讯源显示有几十条未读，点进去后向下滑动无法继续加载，用户认为抓取不到后续内容。
- 每条消息卡片信息较多，部分位置容易拥挤或交叠。

**只读证据**

- 当前 Feed 源栏只截取部分信源展示，不是完整信源管理入口。
- 消息列表默认 20 条一页，真实还有下一页，但分页按钮在列表滚动之外，用户在内部列表滑动时不会触发加载。
- 页面同时承担“读消息、筛信源、看统计、看详情”多种职责，信息密度偏高。

**建议修复方向**

- Feed 主入口只保留少量高价值筛选：全部、未读、精选、稍后读、收藏、按来源搜索。
- 信源列表从主阅读流中降级为“筛选抽屉”或“搜索选择器”，不再长期占据主层级。
- 消息列表改为明确的“加载更多”或真正的列表内无限加载；分页按钮必须贴近列表底部并保持可见。
- 卡片收敛为三层：标题/来源时间、推荐理由或摘要、必要标签；次要指标放进展开区。

### P1-3 过滤池左右栏滚动耦合

**现象**

- 左侧过滤列表很长，右侧预览也在同一个页面主体里。
- 左侧滚动会影响右侧预览位置，用户无法稳定对照某条消息的详情。

**只读证据**

- 过滤池页面主体高度接近整页长文，没有独立的左栏/右栏滚动容器。
- 当前页面滚动高度很大，列表和预览不是工作台式双栏体验。

**建议修复方向**

- 过滤池桌面端改成固定工作台高度。
- 左侧候选列表独立滚动，右侧预览独立滚动。
- 移动端可以保留自然纵向流，但桌面端必须左右分离。

### P1-4 信源管理缺少全览和批量编辑

**现象**

- 信源内容本身比较全，但用户无法方便地统一管理。
- 当前卡片式结构适合浏览单个源，不适合批量改等级、改类型、查异常、看命中率。

**建议修复方向**

- 增加“信源管理表格视图”：名称、类型、等级、权威权重、最近抓取、未读数、精选命中率、重复贡献度、健康状态。
- 支持批量操作：批量改等级、批量暂停、批量改抓取频率、批量打标签。
- 单个信源详情放入右侧抽屉，避免主页面同时展开过多编辑控件。

## 4. P1 问题：信源分级体系割裂

**现象**

- Sources 页面已经出现 `T1/T1.5/T2` 等分级。
- Rules、Insights、Filtered 等页面仍主要使用 `S/A/B/C/D`。
- 用户看到“个人 TIER”“全局层”等词时，不知道它们分别影响什么。

**判断**

这是概念模型不统一。信源治理、评分公式、精选阈值和页面展示如果使用不同枚举，会让用户认为系统没有被设计完整。

**建议修复方向**

- 统一分级体系。推荐保留 AIHOT 借鉴后的 `T1/T1.5/T2` 作为信源权威等级。
- 如果还需要 `S/A/B/C/D`，必须明确它是“质量策略等级”而不是“信源等级”，并在界面中文解释。
- 所有页面统一中文命名：例如“信源等级”“权威权重”“个人覆盖规则”“全局默认规则”。

## 5. P2 问题：中文化和样式密度

### P2-1 页面仍有大量英文/工程词

**现象**

用户明确反馈不希望看到 `Hi`、`single`、`Growth Console`、`Source Rail`、`Decision`、`Confidence` 等英文或工程词。

**建议修复方向**

- 除专有名词、模型名、技术协议外，页面文案全部中文化。
- 不直接展示数据库字段或工程枚举，统一转成用户能理解的中文。
- 对无法翻译的缩写增加轻量解释，例如 RSS、API 可保留，但不要把 `source_kind=rss` 直接抛给用户。

### P2-2 卡片层级和样式拥挤

**现象**

- Feed 卡片里标题、来源、时间、标签、分数、摘要、操作按钮都挤在一起。
- 过滤池和信源管理也有类似问题：信息都显示了，但主次不清。

**建议修复方向**

- 卡片默认态只展示决策需要的信息。
- 指标类信息统一进折叠区或详情栏。
- 移动端和窄宽度下减少徽标数量，避免标签把标题挤压变形。

## 6. 建议修复顺序

### 第一阶段：修数据闭环

目标：让系统至少做到“抓到、分流、可见、可解释”。

- 统一 `is_filtered` 与 `filter_bucket` 的写入逻辑。
- 日报生成前展示数据漏斗。
- 成长仪表盘和日报共享同一套可入选数据口径。
- 对历史错位数据做 dry-run 回补方案。

### 第二阶段：修主阅读流

目标：让用户能顺畅读完内容，而不是被信源栏和分页打断。

- Feed 改为内容优先，信源筛选降级到搜索/抽屉。
- 列表加载方式改为明确的“加载更多”或列表内无限滚动。
- 条目详情站内化，原文跳转作为次级动作。

### 第三阶段：修信源治理

目标：把“很多源”变成“可管理的源资产”。

- 新增信源表格全览。
- 批量编辑等级、类型、权重、状态。
- 显示精选命中率、重复贡献度、最近抓取健康度。
- 统一 `T1/T1.5/T2` 与其他质量等级的边界。

### 第四阶段：修过滤与反馈可信度

目标：让用户知道自己的反馈正在改变系统。

- 显示反馈计数、画像更新时间、最近影响的规则/分数。
- 明确个人层与全局层差异。
- 未启用的 AI 质检不要伪装成已启用能力。

### 第五阶段：中文化与样式收敛

目标：降低工程感，让系统像一个个人/小团队信息加工台。

- 全站中文文案扫描。
- 工程枚举转中文标签。
- 卡片、标签、按钮、状态文案统一。
- 桌面端双栏/三栏页面全部检查独立滚动。

## 7. 后续验收标准

1. 生成日报时，如果有可入选内容，日报必须至少包含标题、摘要、分类、推荐理由；如果没有可入选内容，必须显示空日报诊断。
2. 成长仪表盘四个模块必须能说明数据来源；没有数据时也要说明是“无匹配内容”，不是空白。
3. 过滤字段必须满足一致性检查：不存在 `is_filtered=true` 但无法在过滤池或待复核池找到的消息。
4. Feed 中某个高未读信源进入后，用户必须能通过滚动或明显按钮连续加载后续内容。
5. 过滤池桌面端左列表和右预览必须独立滚动。
6. 信源管理必须支持表格全览和至少一种批量编辑动作。
7. 过滤策略页必须显示硬规则、AI 质检、人工反馈三类能力的启用状态和最近生效证据。
8. 页面除专有名词外必须中文化，不直接暴露工程枚举给普通用户。

## 8. 修复时的防偏提醒

- 不要把系统改成公共热点站。信息中枢 V3 的核心仍然是个人/小团队信息加工台。
- 不要继续堆功能入口。先把“抓取 → 过滤 → 阅读 → 反馈 → 日报/沉淀”的主链路跑通。
- 不要把所有判断交给大模型。模型适合做语义感知，最终路由、阈值、分级、回补必须由确定性代码控制。
- 不要让“看起来很完整”的页面掩盖不可用流程。每个模块都要能回答：数据从哪里来、为什么出现、用户下一步做什么。
