# 信息中枢 V3 整体模块现状诊断与优化总计划

## 0. 2026-06-20 总控复核版

### 0.1 当前结论

信息中枢 V3 当前已经不是“缺功能”的项目，而是一个**功能面很宽、主链路还没有足够硬收口**的项目。后端已经有 RSS、网页、网页索引、邮箱、BestBlogs、Dibao 对照、Readability、Article Agent、日报生成进度、来源健康、AI 用量等模块；前端也已经有 Feed、Sources、Daily、Reports、Insights、AI Usage、Reader Lab 等入口。真正阻碍日常可信可用的是四个主矛盾：

1. **内容真相层不硬**：系统经常知道“有内容”，但没有稳定告诉用户这是全文、RSS 摘要、索引摘要、榜单摘要、网页快照还是片段。
2. **阅读主路径不克制**：Feed 三栏结构方向正确，但低频按钮、状态解释、资产、诊断仍会抢正文空间。
3. **日报产品形态不稳定**：日报有长报能力，但高质量日报、空诊断报告、候选预览和运行分析还没有严格分型。
4. **来源治理没有完全反控**：Sources 能展示健康，但还没有稳定影响 Feed 推荐、日报候选、补抓策略和源级降权。

一句话：**先把“读什么是真的”收硬，再把“怎么读”做顺，最后让日报成为信息雷达。**

### 0.4 当前最影响体验的问题

#### A. Feed 阅读的问题

用户看到的不是“读文章”，而是“读系统状态”。当前需要强制压缩：

- 顶部 Reading Desk 大块、刷新/采集/下一条/全部已读等按钮不应长期占据正文首屏。
- 过期源、补抓提示、阅读资产、日报解释、阶段修复、评分拆解、人类反馈等都应该默认收起。
- 主阅读区只保留三件事：**摘要、原文、翻译**。
- `中文改写 / 问文章 / 转写 / 知识 / 工具诊断` 放到右侧“资产与工具”抽屉。
- 对 `index_item / curated_summary / snapshot / snippet` 只用一行提示说明来源，不要铺成大诊断区。

#### B. 正文抓取的问题

需要按内容来源分治：

- RSS 长文：优先用 feed 中干净正文，避免网页补抓把广告、导航、赞助商抓进来。
- 网页索引源：必须拆单篇；没补到原文时只能标为索引摘要。
- BestBlogs：榜单摘要有价值，但无 `originalUrl` 时不能标全文。
- 36kr 短讯：应产品化为短讯/更多动态/趋势佐证，不应强行按深读文章处理。
- 技术博客：必须保留段落、列表、代码块、链接和图片上下文。

#### C. 翻译的问题

翻译不能再靠“状态标签”猜：

- 有可信全文：显示“一键翻译全文”。
- 只有索引/榜单且有原站链接：显示“补抓原文并翻译”。
- 补抓已失败或无原站链接：显示“打开原文”，不要再显示无效翻译按钮。
- 翻译失败必须显示阶段：正文补抓失败、模型失败、译文过短、配置缺失。

#### D. 日报的问题

日报必须从“候选摘要拼接”升级为“编辑型信息雷达”：

- 正式日报不应展示生成口径、评分阈值、机器入报原因。
- 有候选但高质量素材不足时，应显示“复核日报/素材不足报告”，不要包装成高质量日报。
- 高质量日报应包含：封面判断、目录、信息雷达总览、今日精选、模块日报、更多动态、深读研究、阅读顺序、下一步行动、全池索引。
- 每日报告应尽量覆盖 35+ 篇文章：精选深写 8-12 篇，模块引用 20+ 篇，更多动态 10+ 条。

### 0.5 优化执行计划

#### 第 1 阶段：内容可信合同收口

目标：每个 item 都能明确说明“当前展示的是哪一层内容”。

任务：

1. 固化 `ContentReadiness` 枚举和用户语言：全文可读、RSS 摘要、索引摘要、榜单摘要、网页快照、摘要片段、仅标题、抓取失败。
2. 统一 `readabilityStatus`、摘要 basis、翻译 basis、日报 basis 的门槛，不能各用一套长度标准。
3. 对历史脏正文继续小批量保守修复，优先 36kr 和已进入黄金样本的来源。
4. 所有修复后刷新黄金样本矩阵。

验收：

- 黄金样本矩阵至少 10/12 通过。
- 36kr 片段不再显示补抓已失败后的无效翻译动作。
- John D. Cook 这类代码长文保留代码块、列表和链接。

#### 第 2 阶段：Feed 阅读降噪

目标：Feed 成为阅读器，不再像后台诊断面板。

任务：

1. 顶部大块收缩为一行工具条，低频按钮进入更多菜单。
2. 主 tab 固定为 `摘要 / 原文 / 翻译`。
3. 扩展 tab 移到右侧抽屉：中文改写、问文章、转写、知识、日报引用、评分拆解、阶段修复、反馈。
4. 正文容器按 760-860px、17px、1.8-1.9 行高重排。
5. 翻译按钮点击必须有 loading、成功或可读失败原因。

验收：

- 抽查 10 条 Feed，首屏正文占比明显提高。
- 页面无横向溢出和右下角遮挡。
- 无 raw enum 出现在阅读主路径。

#### 第 3 阶段：日报雷达产品化

目标：日报能承担“今天信息雷达”的角色。

任务：

1. 固化 `DailyReportPayload`：`snapshot / editorialDigest / coverJudgement / radarOverview / moduleNarratives / moreDynamics / deepReads / coverageItems / final`。
2. 生成前先做 `editorialDigest`，把条目分为精选展开、模块引用、更多动态、深读研究、附录索引。
3. 模块独立生成，再由 final agent 做总编辑融合。
4. 页面右侧目录 sticky；Markdown 样式强化标题、引用、链接、列表、重点文章卡。
5. 低质量/空候选报告和高质量日报分类型展示。

验收：

- 高质量日报 6000-9000 中文字。
- 引用 35+ 篇文章，且链接可点击。
- 不出现 `uncategorized`、评分阈值、机器入报原因、裸 URL。

#### 第 4 阶段：Sources 反控

目标：来源健康不只是展示，而是影响系统决策。

任务：

1. 来源健康固定五段：抓取、正文、展示、AI、日报覆盖。
2. 源级策略可编辑：仅 RSS、智能补抓、强制全文、网页监控、停用观察。
3. 健康结果反控 Feed 排序和日报候选。
4. 高价值源失败进入日报覆盖诊断，低价值源噪声进入观察。

验收：

- Anthropic、OpenAI、BestBlogs、36kr、邮箱、低质源能得到不同诊断。
- 用户能知道“这个源为什么没进日报 / 为什么要补正文 / 为什么降权”。

#### 第 5 阶段：工程拆分与门禁

目标：降低继续迭代时的回归风险。

任务：

1. 拆 `feed/page.tsx`：FeedShell、SourceRail、ArticleQueue、ReaderHeader、ReaderTabs、AssetDrawer。
2. 拆 `daily-report.ts`：candidate、editorial-digest、module-narrative、final-synthesis、coverage-index。
3. 拆 `sources/page.tsx`：SourceList、SourceHealthDrawer、SourceActions、EmailIngestPanel、BestBlogsPanel。
4. 将黄金样本矩阵、Feed 页面 smoke、日报页面 smoke 加入固定 QA。

验收：

- 核心文件逐步降到 800-1200 行以下。
- 每次 P0 修复都有单测 + 页面验证 + 黄金样本刷新。

### 0.6 暂停线

在以下问题未收口前，暂停继续扩新功能：

1. 不继续盲目扩源。
2. 不继续新增日报页面形态。
3. 不把 Dibao 硬替代主系统。
4. 不先做复杂 embedding 推荐。
5. 不再把诊断卡片塞进阅读首屏。

### 0.7 当前推荐下一步

下一步直接做 **Feed 阅读降噪 + 翻译主动作固定**：

1. 主 tab 改为 `摘要 / 原文 / 翻译`。
2. `中文改写 / 问文章 / 转写 / 知识 / 诊断` 进入右侧抽屉。
3. 顶部提示压缩，正文首屏留给文章。
4. 对当前黄金样本里的 John D. Cook、OpenAI、36kr、BestBlogs 四类各抽 1 条做 Playwright 验收。

## 1. 一句话判断

信息中枢 V3 当前不是“没有能力”，而是**能力已经铺得很宽，但可信主链路还没有完全收口**。

系统现在已经能做采集、RSS/网页/索引源、正文抽取、摘要、翻译、评分、日报、来源健康、邮箱、BestBlogs、Reader Lab/Dibao 对照、Article Agent 和 AI 用量统计。但用户真正关心的主链路仍然不稳：

> 我每天打开它，能不能放心地读？能不能知道内容从哪里来？能不能翻译？日报能不能像信息雷达一样帮我判断今天发生了什么？

当前答案是：**基础设施在线，数据在流入，部分样本已可用；但内容可信层、Feed 阅读层、日报编辑层、来源反控层仍是核心瓶颈。**

| 外部源与 Reader Lab | BestBlogs/邮箱/Dibao 已接入 | 适合对照，不应替代主系统 | P2 |
| AI 用量与模型治理 | 有日志和统计 | 用量口径需和日报任务分清 | P2 |
| QA 与门禁 | 有单测、Playwright、黄金样本 | 尚未形成每轮必跑门禁 | P0 |
| 工程结构 | 功能集中、迭代快 | 核心文件过大，回归风险高 | P1 |

## 4. 当前最核心的问题

### 4.1 内容层：系统没有足够硬地区分“全文、摘要、索引、快照”

这是所有问题的源头。

现在数据库里 `items.content` 承载了很多不同东西：

- RSS 全文。
- RSS 摘要。
- 网页快照。
- 新闻索引摘要。
- BestBlogs 榜单摘要。
- 邮箱正文。
- 补抓后的 Readability 正文。
- 历史脏正文。

如果上层不知道它拿到的到底是什么，就会出现：

- 原文看起来乱。
- 翻译基于片段或失败。
- 摘要和改写内容差不多。
- 日报误把短讯当深读材料。
- 用户不知道“抓错了”还是“源本身只给摘要”。

根因判断：

- 不是单个 parser 坏了。
- 是内容模型没有把 `content_html / content_text / readability_content / source_summary / index_summary / snapshot` 清楚分层。
- 当前虽然已有 `readabilityContent` 字段，但历史数据、UI 和日报还没有完全围绕它收口。

### 4.2 采集层：RSS 仍是主力，但字段选择和源策略没有完全 Dibao 化

Dibao 对比报告已经证明：

- Dibao 解析更好，部分原因是它更依赖 feed 内的干净正文。
- 信息中枢曾经因为 Atom `summary` 未纳入候选，导致 Simon Willison 这类源退化到网页补抓，抓到 sponsor 或页面模板噪音。
- 信息中枢当前支持更多类型，这是优势，也是混乱来源。

现在最该做的是：

- RSS 走 feed-first。
- 网页补抓只作为增强，不要覆盖干净 feed 正文。
- 索引页、榜单页、网页监控必须用不同内容状态。

### 4.3 Feed：三栏对了，但阅读主视觉还没对

用户多次截图指出红框区域过大、按钮太多、正文少。这是事实。

当前 Feed 的问题不是没有三栏，而是：

- 搜索、筛选、过期源提示、状态行、资产卡、诊断卡、工具按钮仍然抢首屏。
- 用户最常用的其实只有三件事：看摘要、读原文、看翻译。
- 其他能力都应该收进右侧抽屉或更多菜单。

产品原则应该改成：

> 阅读区只服务阅读；诊断区只在用户需要排查时出现。

### 4.4 翻译：不是一个可靠功能，而是一个偶尔成功的动作

数据上，翻译 ready 只有 427 条，近 24h 只有 2 条新 ready。

用户看到的问题包括：

- 没有翻译按钮。
- 点击翻译无效。
- 不知道为什么没翻译。
- 摘要、中文改写、翻译看起来差不多。

正确产品合同：

- 如果有全文：显示“一键翻译全文”。
- 如果只有索引摘要但有原文链接：显示“补抓原文并翻译”。
- 如果补抓失败：显示“原文抓取失败，打开原文”。
- 如果原文已是中文：显示“原文已是中文，无需翻译”，但仍允许用户手动重新生成中文改写。
- 如果模型失败：显示模型阶段失败，不静默。

### 4.5 日报：不是数据量太少，而是素材分层与编辑层没有稳定工作

当前系统并不缺数据。问题是：

- 日报有时只取到少量 final candidates。
- 有时高分为 0 后变成空诊断。
- 有时 payload 结构完整但 summary 很短。
- 模块日报和更多动态没有成为稳定主输出。

日报要做成信息雷达，不能只靠 final prompt 一次性吞材料。

需要固定为三层：

1. 素材层：全池候选、补处理、内容 basis、来源健康。
2. 编辑层：精选展开、模块引用、更多动态、深读、附录索引。
3. 成品层：封面判断、目录、模块化长文、阅读顺序、行动建议。

### 4.6 Sources：健康中心还没有成为输入治理系统

现在 Sources 能展示健康，但还没有足够影响系统行为。

应该形成反控：

- 全文率低：Feed 降级为快扫，日报只进更多动态。
- AI 卡住：进入处理债，提示补处理。
- 高价值源抓取失败：日报覆盖诊断提醒。
- 噪声源：Feed 降权，日报不进主线。
- 官方源配置异常：显示配置检查。

### 4.7 工程结构：核心文件过大，已经影响质量

当前大文件：

- `services/hub-engine/src/outputs/daily-report.ts`：3416 行。
- `apps/web/src/features/feed/page.tsx`：2603 行。
- `apps/web/src/features/sources/page.tsx`：2305 行。
- `apps/web/src/pages/Daily.tsx`：2150 行。
- `apps/web/src/features/settings/page.tsx`：3319 行。

这不是审美问题，而是工程质量问题：

- 状态机难以看清。
- UI 变动容易互相污染。
- 测试很难覆盖到真实用户路径。
- 每次修一个按钮，都可能影响另一个模块。

## 5. 优化路线图

### P0-A：内容可信合同收口

目标：每条内容都能明确回答“我现在展示的是什么”。

任务：

1. 固化 `ContentReadiness`：
   - 全文可读。
   - RSS 摘要可读。
   - 索引摘要。
   - 榜单摘要。
   - 网页快照。
   - 仅片段。
   - 仅标题。
   - 原文补抓失败。
2. 统一 `readabilityStatus` 与 AI basis 门槛。
3. 对历史假 ready、36kr 短讯串台、空 readability 做保守修复。
4. RSS collector 继续向 Dibao 学习：feed-first，字段质量评分，避免网页补抓污染干净正文。
5. 索引源有 `originalUrl` 时优先补正文；无原站链接时明确降级。

验收：

- 黄金样本矩阵至少 10/12 通过。
- 36kr 短讯不再伪装成长文。
- Anthropic/OpenAI 官方新闻能区分索引摘要和原站正文。
- John D. Cook 这类技术长文保留列表、代码和链接。

### P0-B：Feed 阅读台降噪

目标：让 Feed 成为真正阅读器，而不是诊断面板。

任务：

1. 主标签只保留：
   - 摘要。
   - 原文。
   - 翻译。
2. 以下内容移入右侧抽屉：
   - 中文改写。
   - 问文章。
   - 转写。
   - 知识。
   - 阅读资产。
   - 日报引用。
   - 评分拆解。
   - 阶段修复。
   - 人类反馈。
3. 顶部状态行压缩为一行，不能大面积占用正文。
4. 右上角只保留常用动作：打开原文、更多菜单。
5. 正文排版：
   - 760-860px 阅读宽度。
   - 17px 左右字号。
   - 1.8-1.9 行高。
   - 代码块、列表、引用、图片、表格保留结构。
6. 翻译页签永远显示明确动作。

验收：

- 打开任意 Feed，首屏主要看到标题和正文，不被诊断卡淹没。
- 翻译按钮点击后有 loading、成功或明确错误。
- 页面无横向溢出、悬浮按钮不遮挡正文和控件。

### P0-C：日报雷达重建

目标：日报成为日更信息雷达，而不是候选池拼接或系统诊断。

任务：

1. 强制 `DailyReportPayload` 合同：
   - `snapshot`
   - `editorialDigest`
   - `coverJudgement`
   - `radarOverview`
   - `moduleNarratives`
   - `moreDynamics`
   - `deepReads`
   - `coverageItems`
   - `final`
2. 空候选、低置信复核、正式高质量日报分类型保存和展示。
3. 高质量日报结构固定：
   - 今日封面判断。
   - 目录。
   - 信息雷达总览。
   - 今日精选。
   - 模块日报。
   - 更多动态。
   - 重点研究/深读。
   - 阅读顺序。
   - 下一步行动。
   - 附录：全池摘要索引。
4. 模块独立生成，再由 final agent 统一编辑。
5. 更多动态用确定性模板覆盖短讯，避免 LLM 漏条目。
6. 运行分析、token、失败、候选漏斗不进入正文首屏。

验收：

- 正式日报 6000 字以上。
- 至少 35 个可点击链接。
- 精选深写 8-12 篇。
- 模块引用 20+ 篇。
- 更多动态 10+ 条。
- 右侧目录 sticky，日期切换正常。

### P1-A：Sources 健康反控

目标：来源健康不只是展示，而是影响系统。

任务：

1. 来源健康五段诊断：
   - 抓取。
   - 正文。
   - 展示。
   - AI。
   - 日报覆盖。
2. 源级策略：
   - 仅 RSS。
   - 智能补抓。
   - 强制全文。
   - 只监控。
   - 暂停观察。
3. Feed 排序读取来源健康。
4. 日报候选读取来源健康。
5. Source 页面提供“为什么”和“下一步动作”。

验收：

- Anthropic、OpenAI、BestBlogs、36kr、邮箱、低质源能给出不同健康结论。
- 用户能看懂一个源为什么没进日报、为什么只是短讯、为什么需要补正文。

### P1-B：Article Agent 产品化

目标：把读后理解沉淀成资产，而不是按钮噪声。

任务：

1. 固定五个文章问题：
   - 总结要点。
   - 证据清单。
   - 前提拆解。
   - 行动建议。
   - 选题角度。
2. 生成后保存为 `item_reading_assets`。
3. Feed 右侧抽屉展示资产。
4. 日报重点文章只引用资产的 1-2 句，不整段堆入。

验收：

- 生成、重新生成、失败原因、刷新后可见。
- 不干扰主阅读区。

### P1-C：工程拆分

目标：降低大文件回归风险。

任务：

1. 拆 `feed/page.tsx`：
   - `FeedSourceRail`
   - `FeedQueue`
   - `FeedReader`
   - `FeedReaderToolbar`
   - `FeedAssetDrawer`
   - `FeedTranslationPanel`
2. 拆 `daily-report.ts`：
   - `daily-candidate-pool`
   - `daily-editorial-digest`
   - `daily-module-narratives`
   - `daily-final-synthesis`
   - `daily-coverage-index`
3. 拆 `Daily.tsx`：
   - `DailyWorkbench`
   - `DailyReportReader`
   - `DailyCandidates`
   - `DailyRunAnalysis`
4. 每个拆分模块补单测或页面测试。

验收：

- 核心文件逐步降到 800-1200 行以内。
- 每个模块有独立测试。

### P2：推荐个性化、AI 用量、外部源增强

目标：在可信主链路稳定后，再做增强。

任务：

1. Feed 推荐/最新双队列。
2. 用户偏好画像反哺排序和日报。
3. AI 用量区分日报任务用量与全系统用量。
4. Reader Lab 继续做 Dibao 同源对照。
5. 邮箱、BestBlogs、网页监控继续纳入来源健康。

验收：

- 推荐解释能用一句人话说明。
- AI 用量口径不混。
- Dibao 对照能帮助归因：源问题、抓取问题、展示问题、AI 问题。

当前最该做的不是继续扩新功能，而是连续完成下面 10 件事：

1. 刷新并固定黄金样本矩阵，作为 P0 门禁。

## 7. 不建议继续做的事

1. 不继续盲目扩源。当前 706 个源已经足够，质量治理优先。
2. 不把 Dibao 直接替代主系统。它适合作为对照和借鉴，不承担日报和 AI 资产。
3. 不再把诊断信息堆在阅读主路径。
4. 不做复杂 embedding 推荐，直到内容可信和日报稳定。
5. 不把翻译失败包装成“待处理”而不提供动作。
6. 不把网页快照、索引摘要、榜单摘要伪装成全文。

## 8. 总体路线

推荐路线：

```text
内容可信层
  ↓
Feed 阅读降噪
  ↓
日报雷达稳定
  ↓
Sources 健康反控
  ↓
Article Agent 资产化
  ↓
推荐个性化与外部源增强
```

最关键的产品判断：

> 信息中枢不是要比 Dibao 更像 RSS 阅读器，也不是要比 Folo 更像消费级阅读 App。它的核心优势应该是：抓取足够广、内容足够可信、阅读足够顺、日报足够有判断、来源质量能反控系统。

只要这条主链路不收硬，继续加按钮、加源、加模型都会增加噪声；一旦这条链路收硬，现有的大量能力才会变成资产。

## 9. 下一轮建议执行顺序

下一轮建议直接进入 P0，不再开新大方向：

1. 先跑并刷新黄金样本矩阵。
2. 修 Feed 主标签和工具抽屉收敛。
3. 修翻译按钮合同和失败可见性。
4. 修日报正式/诊断分型和模块落库。
5. 用 Playwright 抽测 Feed 和日报页面。

这五步完成后，项目才适合继续进入 Sources 反控和 Article Agent 产品化。
